Web Vitals 三巨头：LCP · INP · CLS

各衡量什么 · 阈值与算法 · 测量（Lab vs RUM）· 优化清单 · 真实现场解读 · 追问链（面试向 · 图解版）

〇、30 秒电梯答案

Core Web Vitals 是 Google 提出的「以用户为中心」的三项体验度量， 对应用户提问的三个问题：

LCP（Largest Contentful Paint，最大内容绘制）——「页面多久看得见主要内容？」 衡量加载性能：视口内最大那块内容（图/大标题/视频首帧）画出来的时刻。

INP（Interaction to Next Paint，交互到下一帧绘制）——「操作多久有反馈？」 衡量响应性：一次交互从输入到下一帧呈现的完整耗时（2024 年起取代 FID）。

CLS（Cumulative Layout Shift，累积布局偏移）——「页面会不会乱跳？」 衡量视觉稳定性：意外布局偏移的累计分数。一句话记忆： LCP 管「快不快」，INP 管「跟不跟手」，CLS 管「稳不稳」——三者合成用户对「这个网站好不好用」的直觉。

🖼 LCP · 加载

视口内最大内容元素的绘制完成时刻。良好 ≤ 2.5s。对应「用户觉得内容出来了没有」。

⚡ INP · 响应

交互输入 → 下一帧呈现的耗时（取会话内最差的交互之一）。良好 ≤ 200ms。

📐 CLS · 稳定

未预期布局偏移的「影响分数 × 距离分数」累计。良好 ≤ 0.1。对应「点错按钮的恐惧」。

一、为什么是这三个：体验模型、阈值与时间线

页面性能指标一大堆（TTFB、FCP、TBT、TTI…），Core Web Vitals 选这三个是因为它们 直接对应人的体感，而且能在真实用户环境（RUM）里稳定测出来：

指标 体验维度 用户的问题 良好 需改进 差
LCP 加载性能 内容出来了没有？ ≤ 2.5s ≤ 4s > 4s
INP 响应性 点了有反应吗？ ≤ 200ms ≤ 500ms > 500ms
CLS 视觉稳定性 会不会乱跳点错？ ≤ 0.1 ≤ 0.25 > 0.25
考核口径：P75 真实用户数据看的是第 75 百分位——75% 的访问达到良好才算「良好」。 平均值会骗人（少数极慢会话被摊平）；Lab 单次跑分也不代表用户体验。 Google 搜索排名信号用的就是字段（field）数据的 P75。

1.1 三大指标在页面生命周期里的位置

点击图片可放大 · 三个指标分别盯住「加载 / 响应 / 稳定」三个体验轴

二、LCP：加载性能——「主要内容出来了没有」

2.1 定义与计时对象

  • 测什么：视口（viewport）内最大的内容元素的绘制完成时间。 候选元素类型：<img>、<svg> 内的 <image>、 <video> 的封面帧、带背景图的元素、块级文本元素（标题/段落）。
  • 取最终值：页面加载过程中 LCP 会随「更大的元素出现」不断更新， 最终 LCP 是用户首次交互（滚动/点击/按键）前的最后一次候选绘制—— 交互后不再更新（因为「加载中」的意义结束了）。
  • 不是：不是 FCP（第一块内容），不是 DOMContentLoaded，不是 onload——LCP 更接近「用户觉得主体内容到位了」。
用 PerformanceObserver 看 LCP 元素（排障第一手）
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  console.log('LCP:', last.startTime, '元素:', last.element, last.url);
  // 截图里的现场就是这么来的：LCP 元素 div#hp_top_cover.hp_top_cover
}).observe({ type: 'largest-contentful-paint', buffered: true });

2.2 LCP 慢的四大根因与对策

根因 表现 对策
慢的 TTFB HTML 本身来得慢（服务器/CDN/重定向） CDN 边缘缓存、服务端渲染/流式输出、减少重定向链、缓存 HTML
资源加载慢 LCP 图片没预加载、被 CSS/字体挡着 <link rel="preload" as="image">、优先级 fetchpriority=high、合理格式（webp/avif）与尺寸
渲染阻塞 同步 CSS/JS 卡住首次渲染，大标题迟迟不出 CSS 内联关键部分、JS 加 defer/async、减少阻塞资源
客户端渲染出数晚 SPA 空壳 → 等 JS → 拉接口 → 才有内容 SSR/SSG/流式渲染、骨架屏（注意骨架屏本身可能成为 LCP 元素！）、优先渲染主内容而非广告位
面试怎么讲：LCP 优化的思考顺序是「时间都花在哪一段」： TTFB → 资源下载 → 渲染 → 字体/脚本阻塞。先用 DevTools Performance 面板看 LCP 标记落点和瀑布图， 再对症下药。我现场那个例子（div#hp_top_cover）LCP 只有 0.31s——说明主视觉块 基本首屏即出，这一页的加载侧可以打满分，注意力应转到 CLS。

三、INP：响应性——「点了多久有反馈」

3.1 定义：一次交互的完整旅程

INP 观察页面上几乎所有的点击、触摸、键盘交互，对每次交互记录：

一次交互 = 三段耗时
[ 输入延迟 ]          [ 事件处理 ]           [ 渲染/呈现 ]
用户点按钮            JS 跑 handler         样式计算+布局+绘制
→ 浏览器开始处理      → 业务逻辑/状态更新    → 下一帧（next paint）可见
─────────────────────────────────────────────────────────────
INP = 整段的「输入 → 下一帧绘制」总时长
  • 取值策略：通常报告整个页面生命周期里最差（或接近最差）的那次交互（排除极端离群值）—— 一次卡死的点击就足以毁掉 INP，这与 LCP 的「关键时刻」截然不同。
  • 与 FID 的区别：FID（First Input Delay）只测「输入被处理前的排队延迟」，不含处理与渲染； INP 测完整旅程，更能反映「卡不卡」的体感。2024 年 3 月起 INP 取代 FID 进入 Core Web Vitals。
  • 无交互时：没有交互就没有 INP（你截图里的「—」就是这个状态）—— 这时要主动去点几下才能测出数。

3.2 INP 慢的三大根因与对策

根因 典型现场 对策
输入延迟段长 主线程被长任务（打包进来的巨型 JS、同步计算）占住，点击排队 拆长任务（scheduler.yield() / setTimeout 切片）、代码分割、降低首屏 JS 体积
事件处理段长 handler 里同步算大量数据、强制同步布局（读写 DOM 交错） 算法降复杂度、Web Worker 算、防抖/节流、批量 DOM 更新
渲染段长 一帧里改几千个节点、巨量样式重算、复杂动画 虚拟列表、CSS containment、transform/opacity 动画、content-visibility
长任务是 INP 的头号敌人 Performance 面板里 >50ms 的 Long Task 就是嫌疑犯。 面试金句：「INP 不是『接口快就行』——接口慢通常只贡献输入延迟段， 而真正的杀手是主线程上的长任务：它让点击排队、让 handler 推迟、让下一帧迟到。」

四、CLS：视觉稳定性——「会不会乱跳」

4.1 分数怎么算：影响分数 × 距离分数

每一次非用户触发的布局偏移记一个「布局偏移分数」，CLS 是页面生命周期内 意外偏移的累计（用「会话窗口」方式累计：连续偏移间隔小于 1s 且窗口不超过 5s 记作一串）。

点击图片可放大 · 截图里「最糟糕的集群 偏移 2 次」就是一次会话窗口内连续发生了两次这样的记账

4.2 CLS 常见来源与对策

来源 现场 对策
图片/视频无尺寸 加载完才把下面内容顶下去 写死 width/height 或 CSS aspect-ratio（浏览器可预留空间）
动态注入广告/embed 上方插入 iframe/广告条，整页下移 为动态内容预留固定高度容器；插到底部/侧栏而不是内容流中间
字体 FOIT/FOUT webfont 到货替换回退字体，文本变宽变窄导致换行变化 font-display: optional/swap + size-adjust 匹配回退字体度量、预加载关键字体
骨架屏/加载态高度不匹配 骨架 40px、真内容 120px，出现时一跳 骨架高度对齐真实内容；或用 min-height 占位
迟到插入的 banner/提示条 Cookie 条、运营弹层把顶部内容推下 预留位置、浮层用 position: fixed 不占文档流
面试怎么讲：CLS 优化的总纲是「给一切迟到的内容留位子」—— 图片给尺寸、广告给容器、字体给度量、骨架给高度。 本地那张截图 CLS=0.16、最糟糕集群偏移 2 次——典型的「两次小跳」场景： 优先去 Performance 的 Layout Shift 区域看具体是哪两个元素在动（工具里「偏移 2 次」可以点开看）， 而不是猜。0.16 处在「需改进」区间（0.1–0.25），把这两次偏移消掉基本就能进绿色。

五、怎么测：Lab 与 RUM，两套口径

Lab（实验室/本地）——可控、可复现

  • 工具：Lighthouse、DevTools Performance、web-vitals 扩展、WebPageTest。
  • 特点：固定环境/网络/设备（可节流 4G + 4x CPU），跑分稳定，适合回归对比与 CI 门禁。
  • 局限：没有真实用户网络/设备/交互分布；INP 在 Lab 里往往测不出（没人点页面）—— 你截图里的 INP「—」就是这个原因。
  • 适合回答：「这次改动有没有把指标改坏？」

RUM（真实用户监控）——分布、真相

  • 工具：web-vitals 库上报 + 自建后端、Chrome UX Report（CrUX）、各 RUM 平台。
  • 特点：按 P75 看分布；能看到「哪类设备/页面/交互在差」。
  • 局限：受广告拦截/浏览器差异影响；需要采样与聚合成本。
  • 适合回答：「用户真实体感如何？搜索排名信号健不健康？」
用 web-vitals 库采集（RUM 的标准姿势）
import { onLCP, onINP, onCLS } from 'web-vitals';

function report(metric) {
  // metric: { name, value, rating, id, entries, ... }
  // 上报到自己的后端 / 第三方 RUM；注意用 metric.id 做去重（指标值会更新）
  analytics.sendVitals(metric);
}
onLCP(report);
onINP(report);   // 需要真实交互才会产生值
onCLS(report);   // 会随偏移持续更新，会话窗口内累计
Lab 与 RUM 打架怎么办 「Lighthouse 100 分但用户说卡」是经典案情——Lab 只模拟了加载，没模拟真实交互与弱机。 原则：Lab 做回归门禁，RUM 做体感真相；考核用 RUM 的 P75，调优用 Lab 复现。 两者数据要能对上话：Lab 发现的长任务、布局偏移元素，要在 RUM 分布里找到对应的差页面/差设备。

「读数 → 行动」的答题模板（面试可直接套）
1. 现象：本地面板 LCP 0.31s（良好），CLS 0.16（需改进，最糟糕集群偏移 2 次），INP 未产生
2. 定性：加载侧已达标；问题是「两次突发布局偏移」；响应性还没测
3. 定位：打开面板的偏移详情/Performance 的 Layout Shift 轨道，锁定移动的元素对
4. 处方（按命中概率）：
   - 图片/视频 → 补 width/height 或 aspect-ratio
   - 动态横幅/广告 → 预留容器高度，或改为 fixed 浮层
   - 字体替换 → font-display + 回退字体度量对齐（size-adjust）
   - 骨架/加载态 → min-height 对齐真实内容
5. 验证：本地重跑 CLS 进绿（≤0.1）；RUM 上看 P75 分布是否同步改善
6. 顺便：点几个按钮把 INP 测出来，确认没有 >50ms 的长任务
面试怎么讲：「我优化性能不从『分低』出发，而从读数语义出发： LCP 元素是谁（工具直接给出）、CLS 是哪几次偏移（集群可下钻）、INP 是哪次交互最差。 本地指标是线索，P75 字段数据才是判卷。 这个现场 LCP 0.31 恰好说明『不是所有性能问题都要优化』—— 把力气花在红黄灯上，绿灯别过度治疗。」

指标 高杠杆手段 验证手段
LCP CDN/缓存 HTML，压缩 TTFB（含 302 重定向链清理） DevTools 网络瀑布图：HTML 行的等待时间
关键图 preload + fetchpriority=high + 现代格式/合适尺寸 LCP 元素的请求优先级与加载时间
JS defer/async，CSS 去阻塞；避免大同步脚本挡住首绘 Performance 面板里的「渲染阻塞」标记
SPA 走 SSR/流式输出，骨架屏但高度对齐 LCP 元素从「骨架」变「真内容」的时刻
INP 拆长任务（>50ms），yield 给主线程喘息 Performance 长任务轨道 + Long Animation Frames
事件 handler 减负：Worker 计算、批量 DOM、防抖 交互录制定位 handler 耗时
首屏 JS 减重、代码分割、非关键交互延迟绑定 入口 bundle 体积 + TBT（Lab 代理指标）
CLS 一切媒体给尺寸（width/height/aspect-ratio） Layout Shift 区域下钻「偏移的元素对」
动态内容预留位 / 浮层用 fixed；字体度量对齐 CLS 会话窗口曲线（哪一时刻在跳）

优先级心法 先看红黄灯、再看杠杆：TTFB 和长任务是 LCP/INP 的共同杠杆（动一处赚两处）； CLS 九成靠「留位子」的工程习惯，技术含量不高但纪律性要求高—— 写代码时每次插入动态内容都问一句「它会挤走谁」。

八、面试追问链

Q1 · LCP、INP、CLS 分别衡量什么？（必考）

答：LCP 衡量加载性能——视口内最大内容元素绘制完成的时刻，良好 ≤2.5s，回答「内容出来了没有」； INP 衡量响应性——从输入到下一帧呈现的完整耗时（取会话内最差交互），良好 ≤200ms，回答「点了有反应吗」； CLS 衡量视觉稳定性——意外布局偏移（影响分数×距离分数）的累计，良好 ≤0.1，回答「会不会乱跳」。 三个合起来就是用户对快不快、跟不跟手、稳不稳的直觉。

Q2 · INP 和 FID 有什么区别？

答：FID 只测首次输入的「延迟段」（点击到 handler 开始跑），不含处理和渲染； INP 测完整交互（输入延迟 + 事件处理 + 下一帧渲染），且覆盖几乎全部交互、取最差值， 更能反映真实卡顿。2024 年 3 月起 INP 取代 FID 成为 Core Web Vitals 正式指标。

Q3 · CLS 怎么计算？什么不算偏移？

答：单次布局偏移分数 = 影响分数（受影响视口面积占比）× 距离分数（最大移动距离/视口最大边）； CLS 是生命周期内意外偏移的会话窗口累计（窗口 ≤5s、间隔 <1s 连成串）。 用户触发的偏移不计分——点击展开、路由跳转后的重新布局、「意料之中」的动画都不算； 算的是「突然出现把内容挤走」这类无预期位移。

Q4 · Lab 分数和真实用户体验为什么不一致？

答：Lab 是固定环境单次跑分：设备好、网络可配置、没人交互——所以 INP 常无值、 弱机上的长任务也测不到。真实用户是设备/网络/交互的分布，考核看 P75。 我的做法：Lab 做回归门禁（改动别把分打坏），RUM 做体感真相（按页面/设备定位差群体）， 两边用同一套 web-vitals 定义，数据才能对话。

Q5 · 给你一个 CLS 0.16 的页面，你先干什么？

答：先下钻再动手。0.16 在「需改进」区间，工具显示「最糟糕集群偏移 2 次」—— 说明是两个突发挤动而非持续漂移。第一步打开偏移详情看移动的元素对； 第二步按嫌疑链排查：晚到图片/动态横幅/字体替换/骨架高度； 第三步对症给位子（尺寸、固定高度、fixed 浮层、font-display）； 第四步本地复跑进绿 + RUM 看 P75 是否同步掉下来。没有定位的「优化」都是碰运气。

Q6 · 怎么把性能指标变成 CI 门禁？

答：用 Lab 的可复现性。Lighthouse CI / WebPageTest 脚本在 PR 上跑固定场景， 对 LCP/CLS 设预算阈值（比如 LCP≤2.5s、CLS≤0.1），超预算就挂掉 MR； 同时跑 bundle 体积预算。注意 Lab 测不了 INP——交互响应性靠「长任务预算」（TBT/Long Tasks ≤X） 做代理指标，真实 INP 留给 RUM 报警。门禁管「别改坏」，RUM 管「真的好」。

九、一页速记卡

  1. 一句话：LCP 管「快不快」（≤2.5s），INP 管「跟不跟手」（≤200ms），CLS 管「稳不稳」（≤0.1）；考核看 P75。
  2. LCP：视口最大内容的绘制完成时刻；候选 = 图/视频首帧/大文本块；交互后不再更新。优化：TTFB、preload 关键图、去渲染阻塞、SSR。
  3. INP：输入→事件处理→下一帧呈现 的完整耗时，取会话内最差；2024 起取代 FID。优化：拆长任务、handler 减负、首屏 JS 减重。
  4. CLS：影响分数×距离分数，会话窗口累计；用户触发的偏移不计分。优化：给一切迟到内容留位子（尺寸/高度/fixed/字体度量）。
  5. Lab vs RUM：Lab 可复现做门禁（INP 测不出要主动交互）；RUM 真实分布做真相（P75 判卷）。
  6. 读数方法：LCP 看元素是谁、CLS 看偏移集群的元素对、INP 看最差交互的长任务——先定位后动手。
  7. 真实现场：LCP 0.31 绿灯（不过度治疗）；CLS 0.16 两次偏移（下钻元素对→留位子）；INP 「—」= 未考（去点几下）。
  8. 公共杠杆：TTFB（LCP）与长任务（INP）是高杠杆；CLS 靠工程纪律「插入前问会挤走谁」。
  9. 门禁：Lighthouse CI + 体积/时长预算管「别改坏」；RUM 报警管「真的好」。
  10. 金句：「性能指标不是分数游戏——LCP 元素、偏移集群、最差交互，每个数字都指着一个具体的元素和一段具体的代码。」
收尾金句 「LCP、INP、CLS 分别是加载、响应、稳定三面镜子：照见的不是『快不快』的抽象分数， 而是某个 hero 图没预加载、某个 handler 跑了 300ms、某个横幅把按钮顶走了—— 会读数的人，从指标一路走到代码。」
