首屏优化四件套

首屏加载 · JS 包体积 · 路由懒加载 · 图片优化——四条杠杆如何拧成一根绳 · 关键路径图解 · 实操清单 · 追问链（面试向 · 图解版）

〇、30 秒电梯答案

这四件事不是并列的四个技巧，而是一条链上的四个杠杆： 「首屏加载」是目标（用户多久看到可用的主体内容）， JS 包体积、路由懒加载、图片优化是三大主杠杆—— 分别砍掉「不该来的字节」「现在用不到的字节」「过重的视觉字节」。

① 首屏加载：先画清关键路径（HTML → 关键 CSS → 首屏 JS → 数据 → 渲染）， 找出「谁在挡着第一屏」；② JS 包体积：用 bundle 分析找出胖子， 靠 tree-shaking、依赖治理、压缩现代语法减重；③ 路由懒加载： 按路由把代码切成按需块，首屏只付「当前路由」的钱；④ 图片优化： 换现代格式、按屏给尺寸、非首屏懒加载——但首屏 LCP 图恰恰不能 lazy。

与 LCP/INP/CLS 的关系：这四件事主要服务 LCP（还有 TBT/FCP）， 顺带通过「更少主线程工作」改善 INP。 一句话：首屏优化 = 删掉不需要的 + 延后不着急的 + 压缩必须留的 + 让最重的图先走。

🎯 首屏加载

目标：关键路径最短。先测量再动手——关键资源、阻塞点、数据瀑布。

📦 JS 包体积

目标：入口字节最少。分析（bundle analyzer）→ 治理（tree-shaking / 依赖替换）→ 门禁（体积预算）。

🗂 路由懒加载

目标：按需付费。动态 import() 按路由切块 + 预取策略，公共依赖提为共享 chunk。

🖼 图片优化

目标：视觉字节最小且不挡 LCP。格式/尺寸/懒加载三板斧——首屏图反着来：preload、别 lazy。

一、首屏加载：用关键路径思维找「谁在挡路」

「首屏慢」是结果，不是原因。正确姿势是把首屏拆成关键路径上的串行环节， 看每个环节耗时和依赖关系——优化就是把串行改并行、把必须的提前、把不必须的挪走。

1.1 首屏关键路径全景

点击图片可放大 · 橙色两段（CSS/JS 阻塞）通常是 SPA 首屏的主犯，正是后文三件套的战场

1.2 首屏的「可用」比「全出」更重要

  • 骨架屏/渐进渲染：先出结构（标题、导航、卡片框），再填数据——用户感知的「快」来自早期可读。
  • 关键内容优先：主内容区先渲染，评论区/侧栏/推荐位延后——别让「最后 10% 的内容」拖住前 90%。
  • 与指标对齐：首屏优化的主要目标是 LCP（还有 FCP/TBT）；顺带减主线程压力利好 INP。
一句话 首屏优化的第一步永远是测量关键路径，而不是上手段。 「JS 太大」「图片太重」是诊断结果——先在瀑布图上看到它挡在关键路径上，才值得砍。

二、JS 包体积：找出胖子，再谈减重

2.1 先看清：体积都花在哪（分析工具）

三板斧分析
# ① 构建产物统计（webpack/vite/rollup 都有对应插件）
npx vite-bundle-visualizer        # vite: rollup-plugin-visualizer
npx webpack-bundle-analyzer dist  # webpack 生态

# ② 看「谁引入了它」——体积问题八成是依赖问题
npx source-map-explorer dist/assets/*.js
# 或用包体积检查工具（对第三方库选型很管用）
npx bundlephobia lodash-es       # 查一个包的 min+gzip 体积

# ③ 浏览器侧：DevTools → Network（JS 过滤）+ Coverage（未执行代码占比）
# Coverage（Ctrl+Shift+P → Coverage）能直接看到「下载了但没跑」的字节——懒加载的靶子

2.2 减重手段（按杠杆从大到小）

手段 做什么 收益量级
路由级代码分割 动态 import() 按路由/按组件切块（见第三章） 极大——入口包常常直接减半
依赖治理 换轻量库（moment→dayjs、lodash→按需引入）、删幽灵依赖、阻断巨型间接依赖 大——一个 moment 就 ~70KB gzip
Tree-shaking 真生效 ESM 产出、sideEffects 声明正确、避免 import 整个库的副作用入口 中大——取决于库的导出质量
组件级懒加载 弹窗/图表/编辑器等「点开才需要」的组件动态加载 中——echarts/md-editor 这类动辄几百 KB
压缩与现代语法 minify + target 现代浏览器（es2020+）、brotli/gzip 预压缩 中——brotli 比 gzip 再省 15–20%
外部化大依赖 CDN external（vue/react 走 CDN 长缓存）——要权衡缓存与安全（SRI） 中——省重复下载，不省解析执行
Vue / React 按需引入的对比
// ❌ 整库引入：打包器摇不掉未使用的（若库有副作用/非纯 ESM）
import _ from 'lodash';
import moment from 'moment';

// ✅ 按需/替代
import debounce from 'lodash-es/debounce';   // lodash-es 是 ESM，可 tree-shake
import { format } from 'date-fns';           // dayjs/date-fns 体积小一个量级

// ✅ 大组件动态加载
const ECharts = defineAsyncComponent(() => import('./ECharts.vue'));  // Vue
const Chart = lazy(() => import('./Chart'));                          // React
面试怎么讲：包体积我按「分析 → 治理 → 门禁」三步走： analyzer 找 Top 贡献者（通常是 1–2 个巨型依赖或全量引入的库）； 治理优先做「换/删/分割」而不是「压缩」——优化压缩比省 10% 小事，砍掉一个 300KB 的库是大事； 最后上 size-limit / bundlesize 体积预算进 CI，防止回潮。 我做组件库时还有一层：库本身走 ESM + sideEffects 声明 + 子路径导出， 让下游 tree-shaking 能生效——体积优化要考虑「我产出的东西让别人摇不摇得掉」。

三、路由懒加载：让首屏只付「当前路由」的钱

路由懒加载的本质是把「进入应用要下载什么」改成「进这个页面要下载什么」—— 用动态 import() 让打包器按路由切出独立 chunk，进入哪个路由才拉哪个。

3.1 标准姿势

Vue Router / React Router
// Vue：组件直接 () => import(...)，构建器自动分块
const routes = [
  { path: '/',           component: () => import('./views/Home.vue') },
  { path: '/dashboard',  component: () => import('./views/Dashboard.vue') },
  { path: '/report/:id', component: () => import('./views/Report.vue') }
];

// React：lazy + Suspense
const Settings = lazy(() => import('./pages/Settings'));
<Suspense fallback={<Skeleton />}>
  <Settings />
</Suspense>

3.2 切完之后的三件事（很多人只做了第一步）

事项 做法 为什么
① 公共依赖抽离 构建器配置 manualChunks/splitChunks：vue/react、工具库提为共享 chunk；避免 A、B 路由各打一份 防止「切了 N 个包，体积反而更大」
② 预取（prefetch）下一跳 路由切换间隙用 requestIdleCallback 预取高频下一跳； 或 webpackPrefetch 注释 / <link rel="prefetch"> 懒加载把「打开时的成本」挪走了，预取把它「抢跑」回来——用户点进去秒开
③ 首屏路由别懒 落地页/首页 chunk 直接进主包或 preload；加载态骨架屏与真实布局对齐 首屏路由再 lazy 就是「为懒而懒」——多一次网络往返还拖 LCP
预取与分块配置示例
// Webpack 魔法注释：预取下一跳（浏览器空闲时加载）
const Home = () => import(/* webpackPrefetch: true */ './views/Home.vue');

// Rollup/Vite 手动分块：框架与大依赖独立长缓存
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ['vue', 'vue-router', 'pinia'],   // 变动少 → 长缓存
          charts: ['echarts']                        // 大块单独放，按需才进
        }
      }
    }
  }
}
懒加载的常见翻车 ① 切得太碎：一个按钮一个 chunk，HTTP 请求数爆炸——粒度按「路由/大功能」就够； ② 循环依赖导致 chunk 拆分异常，公共代码重复；③ 动态 import 失败没有兜底（网络抖动白屏）—— 要有加载失败重试与错误边界； ④ 忽略执行成本：拆包解决「下载」，巨量计算依然卡 INP——那是长任务问题，另一战场。
面试怎么讲：路由懒加载我会讲完整闭环：切块（import）→ 抽公共（manualChunks） → 抢跑（prefetch）→ 守住首屏（首页不懒）。效果用 Coverage 面板验证： 进入首页时「未使用的字节」应显著下降。再补一句边界认知： 懒加载优化的是网络与解析，不解决主线程长任务——与 INP 的优化要分开汇报。

四、图片优化：格式 · 尺寸 · 时机（三板斧 + 一个反常识）

图片常常是页面里最重的字节，也是 LCP 的头号嫌疑人。 优化分三个维度：送什么格式、送多大、什么时候送。

4.1 格式：能小则小，能现代则现代

格式 适用 相对 JPEG 体积
AVIF 照片/复杂图；兼容性已达主流 约小 50%（但编码慢，生产建议 CDN/构建期转）
WebP 通用场景的默认选择 约小 25–35%，兼容性很好
SVG 图标、插画、logo（矢量） 视复杂度；文本可压缩、可样式化
JPEG/PNG 回退格式（<picture> 提供） 基准
按能力协商格式（<picture>）
<picture>
  <source type="image/avif" srcset="hero.avif" />
  <source type="image/webp" srcset="hero.webp" />
  <img src="hero.jpg" alt="主视觉" width="1200" height="630" />
</picture>

4.2 尺寸：按屏给图，别用桌面图怼手机

srcset + sizes（浏览器选最合适的）
<img
  src="hero-800.jpg"
  srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1600.jpg 1600w"
  sizes="(max-width: 640px) 100vw, (max-width: 1024px) 80vw, 1200px"
  alt="主视觉"
  width="1200" height="630"
/>
<!-- 要点：
  1. width/height（或 CSS aspect-ratio）必须给——防 CLS，浏览器可预留空间
  2. 尺寸裁剪在服务端/构建期做（CDN 图片处理 / sharp），别让浏览器下载大图再缩
  3. DPR 2x 屏要考虑 srcset 密度 -->

4.3 时机：懒加载 vs 首屏预载（反常识点）

非首屏图：懒加载

  • loading="lazy" 原生属性，简单有效（列表长图、下半屏内容）。
  • 更精细：IntersectionObserver 自定义占位/渐显。
  • 注意：lazy 图会给 CLS 风险——占位高度要预留。

首屏 LCP 图：反着来！

  • 不能 lazy——lazy 会推迟它，直接拖垮 LCP。
  • <link rel="preload" as="image" href="hero.avif"> 提前抢带宽。
  • HTML 属性 fetchpriority="high"；CSS 背景图尽量换成 <img>（可被 LCP 追踪/预载）。
图片优化与 CLS 的交叉点 上一节 CLS 的头号来源就是「图片没写尺寸」——图片优化天然顺手修 CLS： width/height（或 aspect-ratio）永远是图片标签的必填项， 它同时服务于「布局稳定」和「浏览器预留空间」。
面试怎么讲：图片我按「格式（AVIF/WebP 前置 + 传统回退）、尺寸（srcset/sizes + 真实裁剪）、 时机（非首屏 lazy、首屏 preload + fetchpriority）」三板斧展开，并强调反常识点： LCP 图与 lazy 是死对头。验证方式：Network 里看图片实际下载的字节数与解码时间， LCP 元素是否就是这张图、它的请求有没有被排到前面。

五、四件事合起来：一次首屏优化的作战顺序

步骤 动作 产出
1. 测 Performance 瀑布图 + LCP 元素 + Coverage + bundle analyzer 「谁在关键路径上、多少字节、多少未使用」清单
2. 砍 删/换重依赖；未用代码消灭（tree-shaking、按需引入） 入口包变薄——先做减法再谈切分
3. 切 路由懒加载 + 公共 chunk 抽离 + 非关键组件动态加载 入口只付首屏钱；Coverage 未使用字节大降
4. 图 格式转换/压缩、srcset、首屏 preload、非首屏 lazy、补宽高 LCP 图字节变小且更早到；CLS 顺手变好
5. 并 资源并行（preconnect/preload）、数据并行（SSR/防瀑布）、延后非关键脚本 关键路径串行段变短
6. 守 体积预算 + Lighthouse CI + RUM 监控 不回潮——优化是工程不是运动
杠杆排序经验 对典型 SPA：「路由懒加载没做」>「巨型依赖全量引入」>「图片未压缩」>「压缩算法调优」。 先问「哪些字节根本不该现在到」（切/延后），再问「剩下的字节能不能更小」（格式/压缩）， 最后才抠 HTTP 层的花活。顺序反了就是白忙。

六、度量与门禁：让优化活过下个迭代

度量对象 工具 门禁方式
首屏指标（LCP/FCP/TBT） Lighthouse CI / WebPageTest PR 上跑固定场景，阈值超标挂 MR
入口包体积 size-limit / bundlesize / CI 脚本比对 gzip 体积 「入口 ≤ N KB」写进 CI，超预算失败——最有效的一条
chunk 结构健康 analyzer 快照 / 自动 diff 资产清单 chunk 数量与重复模块告警
图片资产 构建期图片体积检查（无 alt/无宽高/超尺寸告警） lint 插件 / CI 脚本
真实用户体感 web-vitals RUM（LCP/INP/CLS P75） 报警而非门禁——门禁管「别改坏」，RUM 管「真的好」
体积预算示例（size-limit 风格）
// 例：「主入口 gzip 后不超过 150KB」——具体数字按业务定，但要有数字
{
  "path": "dist/assets/index-*.js",
  "limit": "150 KB",
  "gzip": true
}
// CI：npx size-limit
// 体积预算是「团队契约」：新增依赖必须过问——它逼所有人思考「值不值这些字节」

七、面试追问链

Q1 · 首屏加载慢你怎么排查？（必考）

答：按关键路径拆段：DNS/TCP → TTFB/HTML → 解析与关键 CSS → 首屏 JS 执行 → 数据 → 渲染。 用 Performance 瀑布图看谁在关键路径上、谁在阻塞；用 Coverage 看下载未用的字节； 用 analyzer 看包的构成。定位到段之后对症：TTFB 用 CDN/SSR，阻塞用 defer/内联关键 CSS， JS 胖做分割与依赖治理，图重做格式与 preload。先测量后动手是不变的原则。

Q2 · 怎么控制 JS 包体积？

答：分析（analyzer/source-map-explorer/Coverage）→ 治理 → 门禁。 治理按杠杆排序：路由级分割 > 依赖治理（换轻量库、按需引入、删幽灵依赖）> tree-shaking 生效 （ESM + sideEffects）> 组件懒加载 > 压缩与现代语法 > CDN 外部化。 最后用 size-limit 类体积预算进 CI 防回潮。注意区分「下载体积」与「执行成本」——后者是 INP 问题。

Q3 · 路由懒加载要注意什么？

答：完整闭环是切块 + 抽公共 + 预取 + 守首屏。 切块用动态 import；公共依赖用 manualChunks/splitChunks 防重复； 空闲时 prefetch 高频下一跳（把懒的延迟抢回来）；首屏路由不要懒（别为懒而懒）。 还要防切太碎（请求爆炸）、加载失败兜底、骨架屏高度对齐。懒加载只解决下载与解析，不解决长任务。

Q4 · 图片优化有哪些手段？首屏图和普通图有什么不同？

答：三板斧——格式（AVIF/WebP + picture 回退）、尺寸（srcset/sizes、服务端裁剪、给宽高）、 时机（非首屏 loading=lazy，首屏 preload + fetchpriority=high）。 关键反常识：LCP 图绝不能 lazy，否则直接拖垮 LCP；CSS 背景大图尽量换成 img 以便预载与追踪。 宽高必填还是 CLS 的预防措施——一石二鸟。

Q5 · 怎么证明你的优化有效？

答：前后对比三层证据——① Lab 复现：同场景 Lighthouse/Performance 跑分 （LCP、TBT、FCP 数值变化）；② 产物证据：入口 gzip 体积、chunk 数量、Coverage 未使用字节占比； ③ RUM 证据：真实用户 P75 的 LCP/INP/CLS 分布改善。三层缺一不可： 只有跑分没 RUM 是「实验室冠军」，只有 RUM 没复现路径是「不知道为什么好」。

Q6 · 首屏优化和 LCP/INP 优化是一回事吗？

答：高度重叠但不相等。首屏优化是工程视角（关键路径、字节、切分）， 主要作用于 LCP/FCP/TBT；INP 是交互视角——懒加载减轻解析与主线程占用对 INP 有帮助， 但 INP 的主敌是长任务与 handler 耗时，要单独诊断。 CLS 则主要由图片宽高、动态插入、字体替换驱动——图片优化会顺手改善 CLS，但布局稳定性另有纪律。

八、一页速记卡

  1. 总纲：首屏是目标；JS 体积、路由懒加载、图片是三大杠杆——删不需要的、延后不着急的、压缩必须留的、让 LCP 图先走。
  2. 首屏：关键路径六段（DNS→HTML→CSS→JS→数据→渲染）；先测量定位最肥的一段；「可用」优于「全出」。
  3. JS 体积：分析（analyzer/Coverage）→ 治理（分割>换库>tree-shaking>懒加载>压缩）→ 门禁（size-limit）。
  4. 路由懒加载：动态 import 切块 + manualChunks 抽公共 + prefetch 抢跑 + 首屏路由不懒；防切太碎与加载失败。
  5. 图片：格式 AVIF/WebP + picture 回退；尺寸 srcset/sizes + 真实裁剪；时机非首屏 lazy、首屏 preload——LCP 图与 lazy 死对头。
  6. 一石二鸟：图片必给 width/height——同时防 CLS 并帮浏览器预留空间。
  7. 作战顺序：测 → 砍 → 切 → 图 → 并 → 守；顺序反了白忙。
  8. 度量三层：Lab 跑分（复现）+ 产物证据（体积/未用字节）+ RUM P75（真相）；体积预算进 CI。
