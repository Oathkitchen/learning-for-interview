〇、先给结论：30 秒电梯答案

两者的根本差异不是"谁写得快"，而是"什么时候把代码变成浏览器能跑的东西"：

  • Webpack（Bundle 型）：启动时就必须从入口递归遍历整个依赖图， 用 loader 转换 + plugin 处理，把全部模块打包成少数几个 chunk，再交给 dev server。 所以冷启动成本 = 整个项目的构建成本，项目越大越慢。
  • Vite（Bundle-free Dev）：只把 index.html 和浏览器真正请求到的模块 用原生 ESM 按需编译返回。启动时只做两件事——起服务 + 预构建依赖。 所以冷启动成本 ≈ 常量，与业务代码规模几乎无关。
  • 代价（Vite ≤ 7 的经典模型）：Vite 把"打包"推迟到了生产构建 （默认交给 Rollup），于是天然出现 dev 与 build 两条不同管线， 这是它绝大多数诡异 bug 的根源——而这条代价正在被 Vite 8 收回，见第十一章。
先划版本边界（很重要，别说错） 本文第二~第九章讲经典模型（Vite 2~7）：dev 用原生 ESM 不打包、 esbuild 做转译与依赖预构建、build 交给 Rollup。这套叙述至今仍是绝大多数存量项目的事实， 也是面试官心里的默认答案。但请同时记住 2026 年的三个变化，它们改写了其中一半结论：
① Vite 8（2026-03）：esbuild 与 Rollup 双双退出，统一为 Rust 内核 Rolldown；
② Vite 8.1（2026-06）：实验性 bundledDev 让 dev 也可以打包，正面解决"dev 与 build 不一致"；
③ VoidZero 于 2026-06 加入 Cloudflare，并在 2026-09 发布 Vite+ 1.0——把 Vite / Vitest / Rolldown / Oxlint / Oxfmt / tsdown 打成一个统一工具链。详见第十一章。
面试加分表述 一句话升级版：「Webpack 是先编译后服务，Vite 是先服务后编译； Vite 用浏览器的 ESM 替换了 bundler 的模块图遍历，用 esbuild 替换了 最耗时的依赖转换环节，用 Rollup 保留了产物的可控性——本质上它是一次 把"打包"从开发环节解耦出去的架构选择，而不只是"用 Rust 重写一遍"。」
（这段描述的是 Vite 2~7 的架构。Vite 8 之后第三、四小节要换成 "用 Rolldown 一个内核同时承担转译与打包"，别照背。）

一、Webpack 为什么必须打包：一条完整的编译流水线

Webpack 出生时（2012）浏览器没有可靠的模块化方案（ESM 直到 2015 才定稿、2017 年后才普遍支持）， 所以它的设计目标是「把任何模块格式编译成浏览器可执行的静态文件」。 这个前提决定了它的流程：必须先看到全部模块，才能生成完整产物。

冷启动的三个耗时来源

① 全量模块图遍历 parse + AST 解析是 CPU 密集且必须串行于依赖关系。 你没访问的那个页面，它的 500 个模块也照样被解析了。
② loader 链在 JS 运行时 babel / ts-loader / css-loader 全是 Node 单线程执行， 大项目里 node_modules 中未预编译的产物（ESM/CJS/JSX）都要现编一遍。
③ seal 阶段的产物优化 tree-shaking、作用域提升、chunk 分组都要在完整模块图上做，规模一大就是分钟级。
缓解手段：缓存 Webpack 5 cache.type='filesystem' 能把模块解析结果落盘， 二次启动提速明显——但首次启动和 CI 冷跑依然无解。

二、Webpack 的两类扩展点：loader 与 plugin

上一章的流水线里有两个"可插拔"的位置，面试时经常被混为一谈，其实职责完全不同：

  • loader = 文件翻译官：一个纯函数，输入单个模块的原始内容， 输出合法的 JS 源码。它看不到模块图、看不到 chunk，只管"这一个文件"。
  • plugin = 流程订阅者：一个带 apply(compiler) 的对象，通过 tapable 钩子挂在编译生命周期的任意节点上， 能读改模块图、chunk、产物和统计信息。

判断标准一句话：这件事只依赖当前文件内容 → 写 loader；需要跨模块或改产物 → 写 plugin。

最小 loader：5 行就能跑

loader 的契约只有一条：入参是上游给的文件内容，返回值会被当成 JS 源码继续解析。 注意最后一行——webpack 会去 import() 你的返回值，所以纯文本必须先包成模块。

loaders/upper-loader.js —— 把 .txt 变成导出字符串的模块
// 最小可用 loader：没有任何依赖
module.exports = function (source) {
  // source 是文件原始内容（string）。转大写后包成 ESM 默认导出
  return `export default ${JSON.stringify(source.toUpperCase())}`
}
webpack.config.js —— 注册并按 query 命中
const path = require('node:path')

module.exports = {
  module: {
    rules: [
      {
        test: /\.txt$/,
        // 只有带 ?upper 的请求才走这个 loader，避免误伤普通文本
        resourceQuery: /upper/,
        use: {
          loader: path.resolve('loaders/upper-loader.js'),
          options: { keepTail: true },   // 通过 this.getOptions() 读取
        },
      },
    ],
  },
}
业务代码里直接使用
import notice from './notice.txt?upper'
// notice === 'SYSTEM WILL MAINTAIN AT 22:00'

稍真实的 loader：异步、options、错误处理

一旦要做"转换前先读别的文件 / 调外部工具"，就必须切到异步模式： 调用 this.async() 拿到 callback，此后返回值失效， 只能用 callback(err, code, map) 交付结果。

loaders/wrap-loader.js
const fs = require('node:fs/promises')
const path = require('node:path')

module.exports = function (source) {
  const done = this.async()            // ① 声明异步：必须调用 done 才算完成
  const options = this.getOptions()    // ② webpack 5 内置，替代旧版 loader-utils.getOptions

  // ③ 让 webpack 参与依赖追踪：这个文件变了会触发本模块重新构建
  this.addDependency(path.resolve(__dirname, '../templates/wrap.html'))

  return fs
    .readFile(path.resolve(__dirname, '../templates/wrap.html'), 'utf8')
    .then((tpl) => {
      const html = tpl.replace('<slot/>', source)
      // 第二参数是 source map；没有就传 null，别传 undefined 之外的脏值
      done(null, `export default ${JSON.stringify(html)}`, null)
    })
    .catch((err) => {
      // ④ 第一个参数非空 → 编译失败，webpack 会把错误定位到当前文件
      done(err)
    })
}

写 loader 的五个高频坑 ① 忘了 this.async() 就直接 return promise → 产物里出现 [object Promise]； ② 返回纯文本没包成模块 → 报 Module parse failed: Unexpected token； ③ 二进制没设 module.exports.raw = true → 内容被按 UTF-8 解码损坏； ④ 转换后不返回 source map，导致调试时源码对不上； ⑤ 在 loader 里同步读大量文件（readFileSync）又不 addDependency，watch 模式下改了模板却不触发重建。

最小 plugin：往产物里多塞一个文件

plugin 的骨架只有两层：外层拿 compiler（一次编译的总控）， 内层拿 compilation（每次构建的快照，watch 下会重建）。 tap 的第一个参数是插件名，用于调试与去重。

plugins/build-info-plugin.js —— 输出 build-info.json 并给 JS 产物加 banner
class BuildInfoPlugin {
  constructor(options = {}) {
    this.options = options
  }

  // webpack 只做一件事：把 compiler 交给你
  apply(compiler) {
    const NAME = 'BuildInfoPlugin'
    const { Compilation, sources } = compiler.webpack   // webpack 5 推荐从 compiler.webpack 取

    compiler.hooks.thisCompilation.tap(NAME, (compilation) => {
      compilation.hooks.processAssets.tap(
        {
          name: NAME,
          // stage 决定先后：改产物必须选对阶段，太早会被后续插件覆盖，太晚则错过优化
          stage: Compilation.PROCESS_ASSETS_STAGE_ADDITIONS,
          // 只关心 js，减少无谓遍历
          assets: (asset) => asset.name.endsWith('.js'),
        },
        (assets) => {
          // ① 给每个 js chunk 头部注入 banner
          for (const name of Object.keys(assets)) {
            const asset = compilation.getAsset(name)
            compilation.updateAsset(
              name,
              new sources.ConcatSource(`/*! built by ${this.options.team ?? 'team'} */\n`, asset.source),
            )
          }

          // ② 额外产出一个文件（loader 做不到，因为它没有"产物"概念）
          compilation.emitAsset(
            'build-info.json',
            new sources.RawSource(
              JSON.stringify(
                { hash: compilation.hash, time: new Date().toISOString(), ...this.options },
                null,
                2,
              ),
            ),
          )
        },
      )
    })
  }
}

module.exports = BuildInfoPlugin
注册，以及一个异步钩子的写法
const BuildInfoPlugin = require('./plugins/build-info-plugin')

module.exports = {
  plugins: [
    new BuildInfoPlugin({ team: 'infra', env: process.env.BUILD_ENV }),
    {
      // 不想单独建类？匿名对象也行，只要有 apply
      apply(compiler) {
        compiler.hooks.afterEmit.tapAsync('ReportPlugin', (compilation, callback) => {
          const stats = compilation.getStats().toJson({ all: false, assets: true })
          fetch('/api/build-report', { method: 'POST', body: JSON.stringify(stats) })
            .then(() => callback())     // ★ 必须调用 callback，否则编译永远挂住
            .catch(callback)            //   传错则让构建失败
        })
      },
    },
  ],
}
compiler vs compilation compiler 全局唯一，保存配置与 watch 实例； compilation 每次构建新建一个，包含本次的模块图与产物。 90% 的插件写错是因为在 compiler 级钩子里缓存了 compilation 数据。
为什么 loader 必须输出 JS webpack 的解析器只认 JS：所有非 JS 文件都要先被翻译成 export default ... 形式，才能进入依赖分析。 这就是 css-loader 存在的原因——它把 CSS 变成"导出字符串的 JS 模块"。
tap / tapAsync / tapPromise 三种订阅方式：tap 同步、tapAsync 回调、 tapPromise 返回 Promise。 异步钩子里忘调 callback 是最经典的"构建卡死不动"事故。
processAssets 的 stage PROCESS_ASSETS_STAGE_* 是一串有序常量 （ADDITIONS → OPTIMIZE_SIZE → SUMMARIZE …）。 HtmlWebpackPlugin 在 ADDITIONS 注入 script 标签，压缩插件在 OPTIMIZE_SIZE 改内容—— 选错 stage 就会出现"我加的 banner 被压缩掉了"。
映射到 Vite：这两类扩展点变成了一种 Vite 里没有 loader 这个概念，它的职责被插件的 load(id)（替代"读原始文件"）和 transform(code, id)（替代"单文件翻译"）两个钩子吃掉； plugin 的职责则对应 config / configureServer / buildStart / generateBundle 等 Rollup 钩子。 实际迁移时的体感差异有三点： ① loader 是配置项（字符串 + options，按 test 自动匹配）， Vite 插件是代码对象（自己判断 id）； ② loader 链顺序靠数组位置，Vite 靠 enforce 与返回 null 表示不处理； ③ webpack 的 module.rules 精细匹配（resourceQuery / oneOf / issuer） 在 Vite 里都要手写条件判断，这也是复杂 loader 迁移成本被低估的地方。

三、Vite 的原理：把「模块图」这件事外包给浏览器

Vite 的洞察是：现代浏览器已经实现了 ESM， 那么「按 import 语句解析依赖并逐个拉取」这件事， 浏览器自己就能做，dev server 只需要充当一个按需转译的文件响应服务。 于是"必须先构建全部"的前提被抽掉了。

这个模型带来了什么，又放弃了什么

得到的

  • 启动无需遍历业务代码：项目从 200 个模块涨到 2000 个，冷启动几乎不变。
  • HMR 与规模解耦：只重新请求改动模块（详见第五章）。
  • 天然支持 TS/Vue/JSX：不用配 babel 链，开箱即用。
  • 错误定位直观：source map 对应真实文件路径，不是 bundle 里的偏移行号。

放弃的

  • 瀑布式请求：ESM 必须先拿到父模块才知道子依赖，深依赖链 = 多轮 RTT。
  • dev 请求数爆炸：几百上千个小文件，HTTP/1.1 下 6 连接会打满。
  • dev 无全局视野：没有完整模块图，就做不了跨模块优化（tree-shaking 应用码、chunk 划分、模块预加载分析）。
  • dev/build 双份现实：两者产物结构不同，构建期才暴露的问题会延迟出现。
Vite 如何补救瀑布问题 两个手段：① 依赖预构建把 node_modules 里的几百个小文件合并成单文件， 一次性消灭最大的请求源；② 建议 dev server 开 HTTP/2（多路复用）， 让几百个小请求并行而非排队。剩下长尾的源码请求，靠 ETag/304 让刷新页面时几乎零传输成本。

HMR 边界：Vite 的"能热就热，不能热就刷"

Vite 的更新逻辑是沿 importer 链向上冒泡，直到找到第一个 调用过 import.meta.hot.accept() 的模块（HMR 边界）：

  • .vue / React 组件：框架插件自动注入 accept → 原地替换，状态保留。
  • 纯 CSS：不产生新模块，直接替换 style 标签。
  • 普通 JS 模块被改：自己没有 accept，向父级冒泡；父级也没有 → 触发页面级 reload。
  • index.html 或依赖预构建结果变化：直接 full reload。
手写一个可热更新的模块（面试常考「Vite 的 HMR API」）
// stores/ui.ts —— 没有框架插件帮忙，就得自己声明边界
export const state = { sidebarCollapsed: false }

export function toggle() {
  state.sidebarCollapsed = !state.sidebarCollapsed
}

if (import.meta.hot) {
  // accept 自身：改动本模块时不刷新页面，用新实例替换并手动重放副作用
  import.meta.hot.accept((mod) => {
    if (!mod) return
    // 保留旧状态，避免热更后 UI 闪回默认值
    mod.state.sidebarCollapsed = state.sidebarCollapsed
  })

  // 也可以接受别的模块的变化：import.meta.hot.accept('./dep.ts', cb)
  // 主动通知依赖自己的父级：import.meta.hot.invalidate()
  // 需要整页刷新时：import.meta.hot.fullReload()
}
对比细节：为什么 Vite 的 HMR 更"干净" Webpack 的 module.hot.accept 是 callback API，模块状态在新旧实例间迁移要靠开发者自觉； Vite 的 accept 回调直接给你新模块对象， 并且因为是原生 ESM，没有 webpack require 缓存层带来的 "旧闭包引用旧变量"这一类隐蔽问题。当然，副作用型模块（注册路由、挂载全局）在两边都需要手动清理 （import.meta.hot.dispose / module.hot.dispose）。

六、esbuild 的角色：为什么 Vite（2~7）不用它打包生产

esbuild 是 Go 写的，官方基准里"处理 100MB React 代码"耗时是 JS 系 bundler 的 数十到上百倍量级。Vite 在 dev 里让它做三件事： 依赖预构建、TS/JSX transform、CSS/JS minify （Vite 3+ 默认 minifier 就是 esbuild）。 但生产 bundling 默认仍是 Rollup，这是刻意取舍。

本节讲的是 Vite 2~7 的引擎分工。下表最后一列给出 Vite 8（2026-03 起）的对应变化： esbuild 已被完全移除，Rollup 也被替换，两者由 Rolldown 一个内核接管。

dev 源码转译（TS/JSX/Vue） esbuild（+ 框架插件） transform 是单文件无状态操作，正好避开 esbuild 的 bundle 短板。 Oxc（Rolldown 的解析/转译前端）

② 类型与语法的保守策略 esbuild 的 TS 处理是纯擦除：不查类型、不解析 const enum跨文件用法、不跑装饰器元数据（早期）、不处理 import type 之外的类型依赖。这既带来速度，也带来"必须单独做类型检查"的义务。
③ 插件生态是护城河 Vite 插件系统直接兼容 Rollup 钩子 （transform、resolveId、generateBundle 等）， 所以能立刻用上大量 Rollup 插件；若换 esbuild 内核，等于生态清零。 这也是 Vite 8 敢换内核的前提——官方明确 Rolldown 沿用同一套插件 API，因此"换引擎"对外表现为性能变化而非 API 变化。
④ 循环依赖与副作用 Rollup 对 ESM 循环依赖的 TDZ 处理更严谨，产物可读性也更好， 出问题容易 diff——库构建场景尤其看重这点。

Vite 8 换内核后这条结论依然成立：Oxc 同样是"转译器"而非类型检查器， 类型检查仍然必须独立跑。

插件写法对比：同一个需求的两种表达

Webpack：tapable 钩子

// 需要在编译生命周期上挂多个点
class BannerInjectPlugin {
  constructor(text) { this.text = text }
  apply(compiler) {
    compiler.hooks.thisCompilation.tap('Banner', (compilation) => {
      compilation.hooks.processAssets.tap(
        { name: 'Banner', stage: compilation.PROCESS_ASSETS_STAGE_ADDITIONS },
        (assets) => {
          for (const file of Object.keys(assets)) {
            const asset = compilation.getAsset(file)
            compilation.updateAsset(file,
              new RawSource(`/*! ${this.text} */\n` + asset.source.source()))
          }
        })
    })
  }
}

Vite：Rollup 钩子 + 模块语义

// 一个普通对象即可；apply 控制只在 dev 或 build 生效
function bannerInject(text: string): Plugin {
  const banner = `/*! ${text} */`
  return {
    name: 'banner-inject',
    apply: 'build',
    // 转换单个模块（id 为解析后的绝对路径）
    transform(code, id) {
      if (!id.endsWith('.js')) return
      return { code: `${banner}\n${code}`, map: null }
    },
    // dev 专属：直接往 dev server 挂中间件 / ws
    configureServer(server) {
      server.middlewares.use('/__health', (_req, res) => res.end('ok'))
      server.ws.on('connection', () => server.ws.send({ type: 'full-reload' }))
    },
    // 产物级别：遍历最终 chunk
    generateBundle(_opts, bundle) {
      for (const item of Object.values(bundle)) {
        if (item.type === 'chunk') item.code = `${banner}\n${item.code}`
      }
    },
  }
}
顺带一个高阶问题：Vite 的钩子顺序 Vite 插件按 pre / 正常 / post 三阶段排序（对象上写 enforce: 'pre'），框架插件（vue/react）通常在 pre 阶段把 .vue 变成 JS，后续插件才能处理。而 transform 中返回 null 表示"不处理"，返回 { code, map } 才覆盖—— 丢了 map 会让整条链的 source map 断掉，这是新手最常见的插件 bug。

八、Vite 的结构性代价：dev 与 build 是两套语义

这是评价 Vite 时最该被提到的一点，也是区分「用过」和「踩过坑」的标志。 Webpack 只有一条管线，dev 和 build 的差异主要是配置开关； Vite 的 dev（不打包，esbuild）与 build（打包，Rollup）在模块语义层面就不同。

差异点 dev 表现 build 表现 真实事故长什么样
Tree-shaking 不摇树（按需加载已近似） Rollup 摇树，未引用导出被删 dev 好好的，build 后副作用型导入被删（polyfill、注册型 import 未标 sideEffects）
模块格式 严格 ESM，浏览器执行 Rollup 会把 CJS 依赖转 ESM（@rollup/plugin-commonjs） "does not provide an export named 'default'"：CJS 包在 dev 被 esbuild 处理、build 时经 Rollup 推导命名空间不同
全局脚本 / IIFE 拼接 各模块独立求值，顺序由 ESM 图决定 多个依赖被拼进同一 chunk，共享顶层作用域 老地图/SDK 类库靠全局变量互相注册，dev 正常，build 报 xxx is not defined（需 optimizeDeps.include 或改 import 方式）
路径与外部文件 /@fs/ + server.fs.allow 可跨目录 依赖必须被打包，跨 workspace 引用未编译包易报错 monorepo 里改了 sibling 包源码，dev 立即生效、build 用的却是 dist 旧产物
环境变量 import.meta.env 由 dev server 注入 构建期静态替换（字面量内联） 动态访问 import.meta.env[key]：dev 有值、build 变 undefined（只能静态属性访问）
CSS 产物 style 标签注入，不做拆分也不合并 抽出为 chunk 对应 CSS，顺序由 Rollup 决定 build 后样式优先级变了导致覆盖失效（cssCodeSplit / 导入顺序 / @layer）
模块求值时机 import 即请求，异步边解析边执行 同步的 bundle 运行时 依赖"谁先 import 谁先跑"的注册逻辑偶发失效；异步循环依赖表现不同
结论性表述（值得背下来） 「Vite 用 dev/build 语义不一致换来了开发体验的量级提升。 因此凡是用 Vite 的团队，都必须把 vite build + 预览构建产物 （vite preview）纳入 CI， 并把「本地能跑」和「构建后能跑」当成两个不同的验证目标—— 否则这个 trade-off 就会变成线上事故。」
2026 更新：Vite 正在亲手拆掉自己这个短板 上面整节的差异，本质都来自"dev 不打包"这一个决定。Vite 8.1（2026-06）给出了官方解法—— 实验性 bundledDev：dev 阶段也走真正的打包管线， 向浏览器提供预打包产物而不是几百个源文件， 同时保留 HMR 的即时性。官方口径是「combining the best of both worlds」。

九、从 Webpack 迁到 Vite：真实踩坑清单

迁移的难点从来不是装 vite，而是把 Webpack 允许的"非标准写法"改成 ESM 标准写法。 下面这些是最高频的对照项。

Webpack 写法 Vite 对应 说明
require.context('./views', true, /\.vue$/) import.meta.glob('./views/**/*.vue') Vite 用显式 glob API 替代 webpack 专有的 context 模块； eager 选项对应同步导入
process.env.NODE_ENV / VUE_APP_* import.meta.env.MODE / VITE_* 只有 VITE_ 前缀的变量才会暴露给客户端，这是安全默认值
__dirname / __filename（配置里） import.meta.dirname（Node 20.11+）或 fileURLToPath(new URL('.', import.meta.url)) Vite 配置文件在 ESM 下加载，没有 CJS 全局
<%= require('raw-loader!./x.svg') %>、内联 loader 语法 import x from './x.svg?raw' 内联 loader 是 webpack 专有能力，Vite 用查询参数表达
module.rules 里的自定义 loader 改写成 Vite/Rollup 插件（transform + resolveId） Vite 有兼容层但覆盖不全，复杂 loader 建议直接重写
resolve.alias: { '@': resolve('src') } 同名字段保留；推荐改用 tsconfig paths + vite-tsconfig-paths 避免 TS 与构建两处别名不一致
HtmlWebpackPlugin 多页面注入 rollupOptions.input 多入口 + 内置 HTML 处理 Vite 以 HTML 为入口，MPA 需列出所有 html 路径
DefinePlugin 常量注入 define 选项 注意 Vite 的 define 是文本替换，字符串值要自己带引号
externals / CDN 外链 build.rollupOptions.external + output.globals；或 vite-plugin-html、systemjs-imports dev 下 externals 处理是迁移里最容易漏的一环
IE11 / @babel/preset-env targets @vitejs/plugin-legacy + build.target，需 terser 产物体积翻倍（modern + legacy 两份），预算要重估

迁移节奏建议（我们踩过的顺序） ① 先并行：新页面/新项目单独用 Vite，验证插件与构建产物； ② 再收简单工程（内部工具、文档站、组件库 playground）； ③ 大型业务最后动，且必须先解决三件事： 统一环境/构建命令、CI 加 vite preview 冒烟、 把 require 类遗留写法清理成标准 ESM。 不要指望"改个 config 就跑起来"——真实项目卡点几乎都在依赖与 loader 上。

十、面试追问链：把这题聊到加分

下面按"面试官真实追问顺序"整理，点击展开答案。 每一层都往下多答一层，是这类开放题拿分的关键。

Q1：Vite 和 Webpack 最本质的区别是什么？
答：模块解析主体不同。Webpack 在 Node 侧构建完整依赖图并输出 bundle，浏览器只加载几个大文件； Vite dev 把依赖解析交给浏览器的原生 ESM，服务端只做"请求 → 按需转译 → 返回单模块"。 由此推出三个后果：冷启动从 O(项目) 降到近似常量、HMR 更新单位从 chunk 变成模块、 以及 dev/build 分裂成两条管线。（说出"后果"比只说"一个打包一个不打包"高一个档次）
Q2：Vite 一定比 Webpack 快吗？
不一定，要分场景：
  • 冷启动 / HMR：Vite 明显赢，尤其大型项目。
  • 首屏加载：Vite 有 ESM 瀑布问题，模块层级深时首个可用页面可能反而慢；依赖多时预构建本身要几秒。
  • 生产构建：Vite 的 bundle 走 Rollup（单线程、无模块级持久缓存），超大项目可能比 Webpack 5 + filesystem cache 更慢。
  • 依赖-heavy 的场景（大量 CJS 老包）：esbuild 预构建会频繁重跑，体验打折。
诚实的结论：Vite 优化的是开发反馈回路，不是所有阶段的构建性能。
Q3：那为什么 Vite 生产不继续用 esbuild，非得多一层 Rollup？
因为打包这一步需要的能力，esbuild 当时并不齐：成熟的 code splitting 与 chunk 划分控制、 CSS 随 chunk 拆分、更彻底的 tree-shaking、 ESM 循环依赖处理，以及最重要的——复用 Rollup 插件生态（Vite 插件直接实现 Rollup 钩子）。 所以 Vite 的做法是"把 esbuild 用在它最擅长的环节"：依赖预构建、语法转译、代码压缩。

2026 年这条边界已经被抹掉了：Vite 8（2026-03）宣布以 Rolldown 作为唯一内核，esbuild 与 Rollup 同时退出默认链路，转译与压缩由 Oxc / lightningcss 承担。 之所以现在敢换，是因为 Rolldown 复用了 Rollup 的插件 API， 生态不用清零。也就是说：这道题的"标准答案"讲的是历史取舍， 而现状是"一个 Rust 内核同时负责 dev 与 build"—— 能把这个演进讲清楚，比背老答案强很多。
Q4：为什么改了个组件，Vite 瞬间就好了，改个 utils 却整页刷新？
因为 HMR 边界。框架插件（@vitejs/plugin-vue / React Refresh） 会给组件模块注入 import.meta.hot.accept，改动时它能自接受更新，原地替换、状态保留； 普通模块没有 accept，更新请求会沿 importer 链向上冒泡， 一路冒到 main.ts 都没人接受，就只能 full reload。 两种例外必须刷新：改动 index.html；依赖预构建结果变化 （browserHash 变了，所有依赖 URL 失效）。 解法：给状态容器/配置模块手写 accept，或注册为 store 边界。
Q5：Vite 的依赖预构建解决了什么问题？不做会怎样？
三件事：① 格式统一——CJS/UMD 依赖转成浏览器可用的 ESM； ② 请求合并——像 lodash-es 这种由几百个极小文件组成的包， 不合并会产生几百个 304 请求，即使 HTTP/2 也照样拖慢首屏； ③ 稳定 HMR——依赖被固化为带 hash 的强缓存文件，业务改动不会牵动依赖， 同时避免"依赖被多次实例化"。 不做的直接后果：import _ from 'lodash' 这种 CJS 会在浏览器里 报 does not provide an export named default，且首屏请求数失控。
Q6：Vite 项目里 TypeScript 类型报错为什么开发时看不到？
因为 dev 走 esbuild，它是纯转译（type erasing）： 不做类型检查，也不生成类型信息。 必须在 CI（和本地 pre-commit）单独跑 tsc --noEmit / vue-tsc --noEmit， 或用 IDE 的语言服务。Webpack 项目里 ts-loader（或 fork 出去的 checker 插件） 会把诊断显示到 dev overlay——这是 Vite 用"速度"换来的体验项，不是 bug。
Q7：微前端 / 老浏览器兼容，你会选哪个？
Module Federation 相关的架构：选 Webpack（或它的兼容替代 Rspack），因为这是原生一等能力，Vite 侧方案仍不成熟。 IE11 必须支持：也倾向 Webpack——Vite 的 dev 依赖原生 ESM， 老浏览器连开发调试都开不起来；build 侧虽然能靠 plugin-legacy 出双产物， 但体积和运行时注入的复杂度都要重估。 一句话原则：需求落在 Vite 的"原生 ESM + Rollup"假设之外的，就用 Webpack。
Q8：Webpack 5 加了持久化缓存，还有必要迁移吗？
缓存只解决二次启动，且 CI 无缓存 / 缓存卷失效 / 依赖变更时都会退化； 它无法改变"必须先构建全部模块"这一结构性成本。所以：
  • 如果团队痛在 HMR 慢（改一行等 3 秒）→ 迁移收益直接、可量化。
  • 如果痛在 构建产物体积 / 精细优化 / 私有 loader → 这些不是 Vite 的优势区，留在 Webpack 或考虑 Rspack。
  • 新项目 + 主流框架（Vue/React/SSR 生态已转向 Vite）→ 默认选 Vite，没有反例就别逆着生态走。
Q9：如果让你量化"值不值得迁移"，你测什么？
测四个数，别拿感受说话： ① cold dev start（清 node_modules/.vite 与 webpack cache 后到首屏可交互）； ② HMR latency（挑 3 个代表性文件：页面组件、公共组件、store，取中位数）； ③ CI build duration（含安装、类型检查、构建，迁移后总和不要只看 bundle）； ④ 隐性成本：迁移工作量 + 构建产物 diff（体积、chunk 数、样式覆盖回归）+ 需要重写的 loader 数量。 经验：①②通常是数量级改善，③可能持平，④才是决策关键—— 一个有 40 个自定义 loader 的老工程，迁移几乎一定不划算。
Q10：Webpack 的 loader 和 plugin 有什么区别？各写一个最小的。
答：loader 是"单文件翻译函数"，输入模块原始内容、输出 JS 源码， 在模块构建阶段生效，看不到模块图和产物； plugin 是"生命周期订阅对象"，通过 apply(compiler) 挂 tapable 钩子，能改模块图、chunk、产物和统计。 选择标准：只依赖当前文件内容就写 loader，需要跨模块或改产物就写 plugin。 最小 loader 三行： module.exports = (src) => `export default ${JSON.stringify(src)}`； 最小 plugin 是 apply(compiler) 里 compiler.hooks.thisCompilation.tap() → compilation.hooks.processAssets.tap() → compilation.emitAsset()。 两个必答细节：① loader 的 use 数组 normal 从右往左、pitch 从左往右； ② plugin 要区分 compiler（全局一次）与 compilation（每次构建），watch 模式下后者会反复重建。 完整 demo 见第二章。
Q11：2026 年了，Vite 生态发生了什么？（这题能明显拉开差距）
四条主线，按时间说：
  • 2026-03 Vite 8：Rolldown 成为唯一内核，esbuild + Rollup 双双退出； 官方称内部基准 10~30 倍，并给出 Linear / Ramp / Beehiiv 等落地数据。
  • 2026-06 VoidZero 加入 Cloudflare：官方口径是 "joining"， 团队与治理保留、MIT、vendor-agnostic，另设生态基金。
  • 2026-06 Vite 8.1：实验性 bundledDev， dev 也打包，正面解决 dev/build 不一致。
  • 2026-09 Vite+ 1.0：Vite 8 + Vitest 5 + Rolldown + Oxlint + Oxfmt + tsdown + 任务缓存，一条 vp 命令统一工具链。
结论性表述：「Vite 已经从"一个 dev server"长成"一套工具链"， 方向是用 Rust 单内核消除双管线，并把 lint / format / test / build 的 配置与缓存统一起来。所以"要不要选 Vite"这个问题， 2024 年比的是启动速度，2026 年比的是你是否愿意把整条工具链押在同一套内核上」。

# 已公布的 roadmap：分布式缓存网络、workspace 级诊断、vp release、vp docs
怎么理解这波整合（面试可直接用） 以前一个现代前端仓库要维护 vite.config + vitest.config + eslint.config + prettier + tsup/rollup 五套配置， 它们的 parser、缓存、workspace 解析各写一遍， 于是要么 lint 慢、要么缓存命中率低。 Vite+ 的思路是共享同一份 AST 与任务图：一次解析，供打包、测试、 lint、格式化复用，并把构建结果做成可分发缓存。 代价是供应商集中度上升——工具链从"可自由拼装"变成"整体升级"， 这也是评估时最该权衡的一点。
版本事实要写准（面试官很在意） 可以直接引用的硬事实：Vite 8 于 2026-03-12 发布，默认内核为 Rolldown，esbuild 已移除；Node 要求与 Vite 7 一致 （20.19+ / 22.12+）；提供兼容层自动转换旧的 esbuild / rollupOptions 配置；包体积上涨约 15MB（Rust 二进制 + 内置 CSS 压缩器）；官方 React 插件 不再依赖 Babel。Vite 8.1（2026-06-23）引入实验性 bundledDev。Webpack 侧 5.x 仍是长期主线。
官方引用的落地数据（10~30 倍内部基准之外）：Linear 构建降至约 6 秒、 Ramp 约 -57%、Mercedes-Benz.io 最高 -38%、Beehiiv 约 -64%。 这些是厂商口径，写进方案前请自己在目标仓库复测。
