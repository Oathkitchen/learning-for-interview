〇、30 秒电梯答案

三层测试不是「把同一件事测三遍」，而是用不同成本买不同保险：

单元测试解决「逻辑对不对」——纯函数、解析器、状态机的边界条件， 毫秒级反馈，便宜到可以写很碎；它防的是「算错了」。

组件测试解决「交互契约对不对」——props/slots/事件、 用户点了之后组件的可观察行为是否符合约定；它防的是「接口对不上、行为被改坏」。

E2E 测试解决「真实链路通不通」——真实浏览器、真实路由、 真实接口（或稳定 mock）下用户旅程能否走完；它防的是「缝合处坏了、配置错了、集成炸了」。 一句话记忆：单元买「正确性」，组件买「契约」，E2E 买「真实感」——买的越高层越贵， 也越接近用户的抱怨。

🧪 单元测试

对象：函数/模块。断言：输入→输出。速度：毫秒。防：逻辑错误、边界遗漏、回归。

🧩 组件测试

对象：一个组件。断言：渲染 + 交互 → 可观察行为（DOM/事件）。防：契约破坏、交互回归。

🎯 E2E 测试

对象：用户旅程。断言：真实系统里的关键路径。防：集成缝、环境/配置、跨模块协作。

⚖️ 选层原则

能下放就下放：能在单测里锁死的别靠 E2E 撞大运——E2E 是保险不是主力。

一、为什么要分层：一条 bug 的成本曲线

规律很残酷：缺陷发现得越晚，修复成本指数级上升——写完当场发现是改一个字符， 集成后发现是改一个模块，上线后发现是改一个事故报告。测试分层的本质是 用便宜的检查去堆密度，用昂贵的检查去守底线。

点击图片可放大 · 左图决定「一层」的成本属性；右图决定「各写多少」的形状

形状之争怎么答（面试加分） 金字塔（经典，微服务/后端语境重）强调「单测数量最多」；测试奖杯（Kent C. Dodds） 针对现代前端说「组件测试性价比最高」——DOM 环境（jsdom）已经足够便宜，组件层能覆盖大量以前要单测+集成测的场景。 我的实践偏奖杯：库函数解析器用单测锁死，UI 组件用 @vue/test-utils 测行为，E2E 只守关键旅程。 形状不重要，「反馈快的层多写、反馈慢的层少写」的原则才重要。

二、单元测试：解决「逻辑正确性」

2.1 它到底在买什么保险

  • 边界与分支：空值、非法输入、极值、并发乱序——人脑记不全，用例表能记全。
  • 回归锁定：修过的 bug 补一条用例，防止未来改回去。测试是写给未来的自己的。
  • 重构信心：有单测兜底，改内部实现敢下手——这是提高代码演进速度的基础设施。
  • 可执行文档：parseMessage 的用例就是协议文档，比 wiki 永不过期。
真实单元测试（我项目的 SSE 消息解析器）
import { parseMessage } from '../src/message-parser'

describe('解析消息', () => {
  it('可以解析思考事件', () => {
    const result = parseMessage('{"type":"thinking","text":"让我想想..."}')
    expect(result).toEqual({ type: 'thinking', text: '让我想想...' })
  })
  it('可以解析 [DONE] 结束标记', () => {
    expect(parseMessage('[DONE]')).toEqual({ type: 'done' })
  })
  it('可以将纯文本当作内容事件', () => {
    // 协议兼容：非 JSON 字段按内容兜底——边界写进用例，协议行为被锁死
  })
})
面试怎么讲：这个解析器是 SSE 协议的边界，输入是字符串流、输出是结构化事件—— 典型的「单测最佳对象」：纯、快、边界多。[DONE] 哨兵、非 JSON 兜底这些 协议边角全用用例钉住，后面任何人改解析器都会被测试拦住。

2.2 单测的「不」：三件不该干的事

该测

  • 公共接口的输入→输出（行为契约）。
  • 边界、错误分支、协议兼容（旧格式还能解析）。
  • 修 bug 时：先写复现用例再改代码（TDD 的最小应用）。

不该测 / 测了就脆

  • 实现细节：内部私有函数、调用顺序、内部状态结构——一重构全红，测试变成负担。
  • 框架本身：Vue 的响应式、数组 map——那是框架的测试。
  • 一行断言十件事：一个用例一个行为，红了才知道是哪个契约破了。
一句话 单元测试的对象是「可以脱离框架独立成立的逻辑」。写之前先问： 这段代码如果搬到 Node 裸跑还需要什么？依赖越多，它越不「单元」，越该考虑组件/集成层。

三、组件测试：解决「交互契约」

组件测试的对象是「一个组件对外的可观察行为」：给定 props/slots/初始状态， 渲染出什么、用户操作后发出什么事件、DOM 怎么变。它处在单测与 E2E 之间的甜点区—— 比单测真实（真的渲染、真的事件），比 E2E 快（jsdom 内跑，不启浏览器）。

真实组件测试（我项目的 AiButton，@vue/test-utils + vitest）
import { mount } from '@vue/test-utils'
import AiButton from '../../src/primitives/ai-button/AiButton.vue'

describe('AiButton', () => {
  it('渲染按钮元素', () => {
    const wrapper = mount(AiButton)
    expect(wrapper.element.tagName.toLowerCase()).toBe('button')
  })
  it('点击时触发 click 事件', async () => {
    const wrapper = mount(AiButton)
    await wrapper.trigger('click')
    expect(wrapper.emitted('click')!.length).toBe(1)
  })
  it('disabled 时不触发 click 事件', async () => {
    const wrapper = mount(AiButton, { props: { disabled: true } })
    await wrapper.trigger('click')
    expect(wrapper.emitted('click')).toBeFalsy()
  })
  it('loading 状态时渲染 spinner', () => {
    const wrapper = mount(AiButton, { props: { loading: true } })
    expect(wrapper.find('.ai-btn__spinner').exists()).toBe(true)
  })
  it('渲染 slot 内容', () => {
    const wrapper = mount(AiButton, { slots: { default: '确认' } })
    expect(wrapper.text()).toContain('确认')
  })
})

3.1 组件测试的「契约清单」

契约维度 测什么 对应上面例子
渲染契约 基础元素/结构是否成立（button 还是 a，关键 class） 渲染按钮元素、variant 类名
交互契约 用户操作 → 可观察结果（事件、DOM 变化） 点击触发 click、disabled 不触发
状态契约 loading/disabled/错误态的表现与限制 loading 显示 spinner 且拦截点击
内容契约 slots / 文本 / 可访问性名（aria-label） 渲染 slot 内容「确认」

3.2 测试哲学：Testing Library 口径

  • 以用户视角查询：优先 getByText / getByRole，少用 .find('.ai-btn') 扛 className——class 一改名测试全红，而用户从来不知道 class。
  • 测行为不测实现：断言「点了之后 toast 出现」，而不是「内部 state.step 变成 2」。
  • 快照测试要克制：snapshot 适合稳定的小结构（配置对象、图标），大 DOM 快照会变成「更新快照」仪式——那是假覆盖。
组件测试的边界 它测不了：真实布局/样式计算（jsdom 无布局引擎）、跨路由整页协作、真实网络时序、浏览器兼容。 这些是 E2E 和视觉回归的领地——别指望 mount 一次组件就覆盖「看起来对不对」。

四、E2E 测试：解决「链路真实性」

E2E（端到端）在真实浏览器里驱动完整应用走用户旅程： 打开页面 → 登录 → 搜索 → 提交 → 看到结果。它回答的问题只有一个： 「用户用起来，这条关键路径是通的吗？」

4.1 它独有的保险（其他层买不到）

  • 集成缝：前端路由 ↔ 后端接口 ↔ 鉴权 ↔ 网关——单测组件各自绿、拼起来红的典型区域。
  • 真实环境差异：构建产物、环境变量、接口地址、CORS、Cookie——「本地是好的」专治现场。
  • 多模块协作：购物车→下单→支付状态流转，跨页面的状态与数据一致性。
  • 发布信心：上线前 smoke 一跑绿，才敢点部署——E2E 是「敢上线」的心理依据。

4.2 代价与反脆手法

代价 表现 缓解
慢 分钟级起步，全量套件半小时不罕见 只测关键旅程（登录/主流程/付费路径）；并行执行（Playwright workers）
脆 等待时机、动画、异步竞态导致「偶发红」 用自动等待的查询（getByRole）、避免 sleep、测试数据隔离
贵 要环境、要数据、要维护，失败排查慢 失败自动截图/trace/视频；E2E 失败先看产物再猜代码
覆盖面幻觉 以为 E2E 绿 = 质量好，其实边界分支全没走到 边界交给单测/组件测试——E2E 不追覆盖率数字
工具与现代姿势
Playwright（当前主流）  多浏览器、自动等待、trace 排障、并行 worker
Cypress                 开发体验好、时间旅行调试；多标签/跨域历史包袱

反脆三原则：
1. 按「用户可见文本/角色」定位，不按易变的 CSS 选择器定位
2. 测试数据独立可重置（每个 worker 一套账号/数据）
3. 关键路径优先：登录 → 核心任务 → 付费/发布 之外的用例下放到组件层
面试怎么讲：E2E 的定位是「守门员不是主力前锋」—— 一个 200 条用例的 E2E 套件不如「30 条关键旅程 + 扎实的组件测试」。 我会用 trace/失败录像把「偶发红」变成「可诊断」；接口层用稳定的 mock 或 测试环境固定数据，把「环境脆」从 E2E 里剥离出去。

维度 单元测试 组件测试 E2E 测试

六、一条用例放哪层？决策表

实战里最常问的不是「要不要测」，而是「这玩意儿该放哪层」。按被测对象的性质分诊：

你想验证的东西 放哪层 例子
纯函数/解析器/算法的输入输出 单元 parseMessage 解析 SSE 帧、format-stat-value 数值格式化、BEM 类名拼接
「给这个 prop，组件该渲染/发出什么」 组件 AiButton disabled 不发 click、AiChart 收到数据后生成 option
多个组件 + 状态管理协同（页面级小组件） 组件（挂父组件）或集成测试 输入框 + 历史记录面板的组合行为
「用户登录后能不能走完下单」 E2E 登录 → 选品 → 支付 → 订单列表出现
构建产物/环境变量/路由配置是否正确 E2E 或部署后 smoke 「生产包里 feature flag 生效」
视觉长相（间距、主题切换观感） 视觉回归（截图对比），不是 E2E 断言 主题切换后按钮对比度达标
修了一个线上 bug 哪层能最薄地复现就在哪层（优先下放） 解析 bug → 单测；点击没反应 → 组件；整页白屏 → E2E
决策口诀 「能单测不组件，能组件不 E2E；能 E2E 的只留关键路径。」 下放的标准是「这条断言是否需要真实浏览器/真实路由/真实接口」——不需要就往下沉。 每条 E2E 用例都该能回答：「它守的这个风险，为什么组件层守不住？」答不上来就下放。

七、真实实践：vitest 体系与测试门禁

我的组件库 monorepo 用 vitest 一套打穿单测与组件测试，E2E 交给关键旅程：

工具栈与命令（真实 package.json）
{
  "scripts": {
    "test": "vitest run",
    "test:coverage": "vitest run --coverage",
    "test:ui": "vitest --ui --coverage",
    "build": "pnpm test && vue-tsc --noEmit && vite build"
  },
  "devDependencies": {
    "vitest": "4.1.10",
    "@vue/test-utils": "^2.4.6",
    "jsdom": "^29.0.2",
    "@vitest/coverage-v8": "4.1.10"
  }
}
层 我项目的落点 例子（真实文件）
单元 协议解析、工具函数、composables 纯逻辑 ai-chat/__tests__/message-parser.test.ts、stream-reader.test.ts、format-stat-value.test.ts
组件 primitives / blocks / scenes 三级组件，mount + trigger + emitted ui/__tests__/primitives/AiButton.test.ts、blocks/ai-chart-block.test.ts、scenes/ai-chat.test.ts
协议/集成 用 vitest 做跨包协议兼容验证（不启浏览器的「准 E2E」） chat-vue/__tests__/protocol-compat-e2e.test.ts
E2E 示例应用关键旅程（ai-test-app 联调路径） 登录/AI 对话主流程（Playwright 类工具）
门禁：测试不是可选项
① build = pnpm test && vue-tsc && vite build   —— 测试不过就构建失败，坏产物出不去
② pre-commit 跑 pnpm test:core                —— 提交前核心包测试拦截（simple-git-hooks）
③ CI 全量 vitest + coverage                   —— 覆盖率报告跟 MR 走
④ 测试规范（GOLDEN_RULES）：公共 API 必须有单测；
   测试放 __tests__/，命名 <module>.test.ts     —— 组织约定进契约文档
面试怎么讲：我们不是「为了覆盖率写测试」，而是把测试焊进交付链： build 前置测试、pre-commit 拦核心包、CI 全量。分层策略上—— SSE 解析器这种协议边界用单测穷举；组件库每个 primitive/block 测「交互契约」 （点击、disabled、loading、slot）；跨包协议兼容用集成级用例守； 整页旅程交给示例应用的 E2E。每层各守各的风险，不越权也不漏守。
覆盖率怎么看 覆盖率是「缺测地图」不是「质量 KPI」：100% 覆盖率也可以全是断言一行的假测试。 我看三个信号：① 新公共 API 的测试是否随代码一起进 MR（测试是交付的一部分）； ② bug 修复是否带回归用例；③ 覆盖率骤降的模块是否被解释。行为契约的数量，比行覆盖的百分比诚实。

八、面试追问链

Q1 · 单元测试、组件测试、E2E 分别解决什么问题？（必考）

答：单元测试解决「逻辑对不对」——函数/模块的边界与分支，毫秒反馈，防算错与回归； 组件测试解决「交互契约对不对」——props/slots/事件与可观察行为，秒级反馈，防接口改坏； E2E 解决「真实链路通不通」——真实浏览器里的用户旅程，分钟级反馈，防集成缝与环境问题。 一句话：单元买正确性、组件买契约、E2E 买真实感；越往上越贵，所以能下放就下放。

Q2 · 测试金字塔和测试奖杯有什么区别？你站哪边？

答：金字塔强调单测数量最多、E2E 最少；测试奖杯（Kent C. Dodds）针对现代前端， 认为 jsdom 让组件测试足够便宜，「组件层最厚」性价比最高。我实践偏奖杯： 协议/算法用单测锁死，UI 组件测行为契约，E2E 只守关键旅程。形状是表象， 内核原则一致——反馈快的层多写，反馈慢的层少写且只守底线。

Q3 · 组件测试怎么写才不脆？

答：三条。① 按用户视角查询（getByRole/getByText），少依赖 className； ② 测可观察行为（DOM/事件），不测内部实现（state 结构、私有方法）； ③ 一个用例一个契约。快照测试只用于稳定小结构，大 DOM 快照会退化成「一键更新」的假覆盖。 我们 AiButton 的用例就是契约清单：渲染、点击、disabled 拦截、loading 拦截、slot—— 重构实现只要契约在，测试就不动。

Q4 · E2E 又慢又脆，怎么管理？

答：少而精 + 反脆设计。只测关键旅程（登录/主流程/付费），其余下放； 定位用用户可见文本而非易变选择器；测试数据隔离可重置；失败产出 trace/截图/视频保证可诊断； 并行执行摊薄时间。每条 E2E 都要能回答「为什么组件层守不住」——答不上来就下放。 E2E 偶发红要当事故修，不能习惯性重跑——「重跑就绿」是测试体系的癌。

Q5 · 覆盖率多少合适？

答：覆盖率是缺测地图不是 KPI。与其定「80% 行覆盖」， 不如定「公共 API 必须有用例、bug 修复必须带回归」这类行为规则—— 我项目 GOLDEN_RULES 就是这么写的。看数字也看三件事：新 API 是否测试随行、 bugfix 是否带用例、骤降模块是否被解释。100% 覆盖率的假测试比 60% 的真测试危险。

Q6 · 测试应该谁写？TDD 怎么看？

答：测试是交付的一部分，写功能的人写测试（谁生产谁负责）， review 里测试和实现同权——没有测试的 MR 我们会打回。TDD 我按场景用： 协议解析、算法这类「输入输出明确」的地方，先写用例很舒服（也是最好的边界清单）； 探索型 UI 交互先实现再补契约测试更顺。不搞形式主义 TDD，但修 bug 必须「先复现再修」。

九、一页速记卡

  1. 一句话：单元买「正确性」，组件买「契约」，E2E 买「真实感」——越往上越贵越慢越接近用户抱怨。
  2. 单元：函数/模块的输入→输出；防边界遗漏与回归；不测实现细节、不测框架本身。
  3. 组件：props/slots/事件 → 可观察行为；测试四契约（渲染/交互/状态/内容）；按用户视角查询，测行为不测 class。
  4. E2E：真实浏览器里的用户旅程；防集成缝/配置/跨模块；少而精，反脆三原则（用户定位、数据隔离、失败可诊断）。
  5. 形状：金字塔（单测最多）vs 测试奖杯（组件层最厚）；原则只有一个——快层多写、慢层守底线。
  6. 决策口诀：能单测不组件，能组件不 E2E；E2E 每条用例要能回答「为什么下放不了」。
  7. 快照：只适合稳定小结构；大 DOM 快照 = 假覆盖。
  8. 覆盖率：缺测地图不是 KPI；公共 API 有用例、bug 修带回归，比百分比诚实。
  9. 真实工程：vitest + @vue/test-utils + jsdom 打穿单测/组件层；build = test && tsc && build；pre-commit 拦 test:core。
  10. 金句：「E2E 是守门员不是前锋——它保证球进不了门，但进球靠的是前场（单测/组件）的日常训练。」
收尾金句 「测试分层不是仪式，是成本会计：用毫秒级的检查去买密度，用分钟级的检查去买信心—— 密度靠单测和组件测试，信心靠 E2E；账要算在风险上，不是行数上。」
