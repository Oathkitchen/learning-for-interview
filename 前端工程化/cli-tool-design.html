〇、30 秒电梯答案

CLI 设计的本质是把一个工具的能力，组织成「可发现、可组合、可脚本化」的命令面。 我把它拆成五层，面试按这个顺序讲就稳：

① 分发层：bin + shebang + npx，让任何机器一条命令装上、跑起来； ② 命令层：子命令 / 选项 / 默认值 / --help，决定「怎么用」； ③ 交互层：交互式问答补全缺失参数，同时保留纯参数的「脚本友好」路径； ④ 执行层：版本门禁、错误处理、进度反馈、退出码——决定「敢不敢在 CI 里用」； ⑤ 模板/插件层（脚手架类）：模板来源、生成流程、可扩展性。 我做过一个真实脚手架 ncp-cli（commander + inquirer + npm 模板包）， 下面结合 vue-cli、create-vue、vite 等开源标杆展开。

📦 分发：bin + npx

package.json 的 bin 字段把文件映射成全局命令；npx 则免安装直接跑——这是 CLI 的「上架通道」。

⌨️ 命令面：可发现

子命令 + 长短选项 + 示例级 help。用户不看文档也能靠 --help 摸出门道。

💬 交互与脚本双轨

参数给全了就静默执行；给不全就问答补全。两条路都要通，否则 CI 用不了。

🛡 门禁与退出码

Node 版本检查、失败即非零退出、进度可见——工程化的底线，也是我 ncp-cli 里真实做了的事。

一、分发与入口：bin、shebang、npx——一条命令怎么来的

用户敲下 ncp create my-app 之前，工具得先「上架」。这层的全部机关就三样东西：

1.1 三件套

机关 干什么 我在 ncp-cli 里的写法
shebang 文件第一行 #!/usr/bin/env node，告诉 Unix「用 node 跑我」；Windows 上 npm 会生成 .cmd/.ps1 垫片，行为对齐 bin/index.js 第一行原样写了
bin 字段 package.json 里 {"ncp": "bin/index.js"}：安装时把这个文件链接到全局/node_modules/.bin，命令名就是 key "bin": { "ncp": "bin/index.js" }
files 白名单 发布到 registry 时只带上需要的目录，npm 包体积小、边界清晰 "files": ["bin", "util"]

1.2 shebang 是什么：内核为什么认得 #!

先从一个你肯定见过但没细想的现象说起：一个 .js 文件，凭什么能像程序一样被「执行」？ JavaScript 又不是机器码，系统内核更不认识什么 console.log。答案就藏在文件第一行那两个字符 #! 里。

名字的来历：pound + bang

  • # 在英文圈叫 pound（也叫 sharp，吉他升号同款）；! 叫 bang（惊叹号的行话）。
  • #! 连读就是 shebang（也写作 sha-bang、hash-bang、pound-bang——发音和「容器 shebang」同一个词）。
  • 它是一行魔法注释：对普通解释器（node、python、sh）来说，# 开头就是注释，无害； 但对操作系统内核来说，它是「请用这个解释器来跑我」的执行委托书。

点击图片可放大 · 内核只做「转手」：拆行 → 找解释器 → 把原文件路径和参数原样递过去

自己动手验证（30 秒）
# 写一个最小脚本
cat > hi.sh << 'EOF'
#!/usr/bin/env bash
echo "hello from $0"
EOF

chmod +x hi.sh   # 加执行权限——没有 x，直接执行会 Permission denied
./hi.sh          # 内核读第一行 shebang，用 env 找 bash 来跑 → 成功
sh hi.sh         # 绕过 shebang，手动指定解释器 → 也能跑（shebang 被当成注释）

# Node 的同款对照：
# 有 shebang 时：./bin/index.js 直接执行 → 内核委托给 node
# 没有 shebang：Linux 会报 bash: ./bin/index.js: cannot execute binary file
#               （或 Permission denied）——文件「存在」不等于「可执行」

为什么用 /usr/bin/env node，而不是写死 #!/usr/bin/node？

  • #!/usr/bin/node 是绝对路径：机器上 node 不在那个位置（nvm/fnm/volta 装的都在 ~/.nvm/… 或 ~/.local/…）就直接失败。
  • env node 是间接层：env 拿着 node 去 PATH 里现查——你用 nvm 切到 v18，它就找到 v18 的 node。
  • 「跟人走而不是跟路径走」——多版本管理器时代，env 是唯一稳的写法。所有现代 CLI 的标准姿势。

Windows 上 shebang 失效怎么办？

  • Windows 内核不解析 #!——那套 execve 约定是 Unix 的。
  • 解法：npm 安装时替你生成垫片：在 node_modules/.bin（以及全局 bin 目录）里生成 ncp.cmd（cmd 用）、ncp.ps1（PowerShell 用）、以及 bash 的 ncp 脚本； 垫片内容就是「找到 node，跑这个 js 文件，转发参数」。
  • 所以 package.json 的 bin 只写一个 JS 文件，三平台都能跑——跨平台是 npm 替你抹平的，不是 shebang 的功劳。
你其实早就见过它 .husky/pre-commit、.git/hooks/*.sample 第一行的 #!/usr/bin/env sh——git hooks 就是靠 shebang 决定钩子用什么 shell 跑。 Linux 服务的 /etc/init.d/ 脚本、Python 爬虫的第一行，全是同一个机关。 一句话：shebang 是「可执行脚本」和「普通文本」之间的界碑。
面试浓缩版 「shebang 是文件第一行的 #!解释器 委托书：Unix 内核发现目标不是二进制时， 会读第一行，把解释器路径和脚本路径拼起来执行——所以 ./cli.js 本质是 env node /path/cli.js，Node 收到的 argv 里脚本占 argv[1]，用户参数从 argv[2] 起， commander 解析的就是这一段。现代 CLI 一律写 #!/usr/bin/env node 而非绝对路径， 是为了让 nvm 这类 PATH 切换的多版本管理器生效。Windows 不解析 shebang， npm 通过给每个 bin 生成 .cmd/.ps1 垫片来对齐——所以一份 bin 配置三平台通用。」
用户视角的三种使用方式（全都要支持得好）
# ① 全局安装——老用户 / 固定工具人
npm install -g ncp
ncp create my-app

# ② npx 免安装——一次性 / 尝鲜（create-* 家族的标准姿势）
npx ncp create my-app
# 开源对照：npm create vite@latest my-app  ≡  npm exec create-vite@latest my-app

# ③ 本地开发自测——npm link，把本地包链到全局
npm link        # 在 CLI 仓库里
ncp create demo # 直接就是你刚改的代码
npx 的本质（面试常考） npx 做三件事：找到可执行文件（本地 node_modules/.bin 优先，没有就临时下载这个包）→ 拼上参数执行 → 结束后不污染全局。所以 npm create vite 只是 npm exec create-vite 的语法糖（把 create-x 自动补出来）。 脚手架命名成 create-* 就是为了吃到这个糖——这是「产品命名服从于分发机制」的典型例子。
发布侧：registry 与引擎声明（ncp-cli 真实配置）
{
  "name": "ncp-cli",
  "bin": { "ncp": "bin/index.js" },
  "files": ["bin", "util"],
  "publishConfig": {
    "registry": "http://内网nexus/repository/npm-snapshots/"
  },
  "engines": { "node": ">=10.0" }
}
面试怎么讲：三个细节说明我考虑过生产：① files 白名单控制 tar 包内容； ② publishConfig.registry 指向内网私服（和外网公共包隔离）； ③ engines 声明 Node 下限——它不只是文档，我的入口代码会拿它做运行时校验（见第四章）。

二、命令与参数：命令面怎么设计

命令面（command surface）= 用户能敲出来的所有合法形态。设计目标三个词： 可发现（discoverable）、可组合（composable）、可脚本化（scriptable）。

2.1 解析库选型

库 风格 谁在用 适合
commander 声明式：.command().option().action()，子命令树清晰 我的 ncp-cli、create-next-app 等大量脚手架 多子命令的「工具箱」型 CLI
cac 轻量、链式、启动快 vite / vitest / vueuse 的 CLI 单命令 + 少量选项，追求冷启动速度
yargs 功能最全：校验、中间件、自动生成 help eslint（历史）、pm2 等 复杂配置校验、插件化的老工具
手写 process.argv 零依赖 极小型脚本 别为 3 个选项引入框架——但超过就换库

2.2 选项设计的「军规」

  • 长短并存：-t, --template <type>——短的给高频手敲，长的给脚本可读（脚本里永远用长选项）。
  • 给默认值，可覆盖：默认路径 ./、默认模板——能一条命令跑通的，绝不逼用户答题。
  • 布尔开关用「开/关」对：--install / --no-install；否定式 --no-* 是 commander 的惯用法。
  • help 里放例子：用户忘语法时第一反应是 --help，不是翻文档。
  • 版本出口：-v/--version 输出版本——排障第一问「你用的哪个版本」。
ncp-cli 的命令面（真实代码）
program
  .version(pkg.version, '-v, --version', '输出版本号')
  .helpOption('-h, --help', '帮助查看信息，使用命令行等操作。')
  .usage('<command> [projectName]')
  .on('--help', () => {
    console.log('执行命令:');
    console.log('  ncp create projectName 创建工程模板');
  });

program
  .command('create [projectName]')                       // 子命令 + 可选位置参数
  .option('-t, --template <templateType>', '指定模板工程，例如："vue-seed"、"hsa-seed"等')
  .description('初始化一个模板项目')
  .action((name, cmd) => { /* 参数齐了走快捷路径，缺了走交互路径 */ })
  .on('--help', () => {
    console.log('例如：');
    console.log('  ncp create');                                  // 全交互
    console.log('  ncp create projectName -t hsa-seed');          // 全参数，可进脚本
  });

program.parse(process.argv);
面试怎么讲：这里的关键设计是位置参数 + 选项都可选—— ncp create 进交互问答，ncp create my-app -t vue-seed 一步到位。 同一命令的「探索模式」和「脚本模式」并存，help 里两种示例都写。这是我对 create-vue / create-next-app「flags + prompts 混合」模式的实践。
开源标杆的进阶玩法 create-vue（Vite 官方脚手架）的选择题（Router/Pinia/测试/ESLint…）本质是把「选项」搬进交互界面； 同时每个能力都有对应的 --router / --pinia 等 flag， 在 CI 或预设脚本里一键生成。交互面 = flag 面的可视化，两面必须一致——不一致就是文档事故。

三、交互体验：问答、反馈、观感

CLI 的 UX 也有设计。原则一句话：不问已经知道的，不问能推断的，问的时候给校验和默认值。

3.1 问答：只问缺的那块拼图

ncp-cli 的动态 prompts（真实代码逻辑）
// 已知的不再问：给了项目名就不问名字；给了 -t 就不问模板
if (!name) {
  prompts = nameInit.concat(descriptionInit);
  if (!paramObj.templateType) prompts = prompts.concat(tempTypeChange);
} else {
  if (!paramObj.templateType) prompts = descriptionInit.concat(tempTypeChange);
  else prompts = descriptionInit;
}
inquirer.prompt(prompts).then(answers => { /* 开始创建 */ });
每个问题自带校验（util/repl.js）
{
  name: 'projectName',
  type: 'input',
  message: '请输入项目名称：',
  validate(input) {
    if (!input.length) return '项目名不能为空，请输入项目名称！';
    if (fs.existsSync(input)) return '当前目录已经存在同名项目，请换一个项目名！';
    return true;
  }
}
面试怎么讲：问答不是「把配置念一遍」，而是补全缺口： 位置参数/flag 已给出的字段直接跳过；每个问题在 validate 里做「空值、重名」检查， 报错就地重输而不是启动后炸——错误修复成本越早越低。

3.2 三类反馈：进度、成功、失败

反馈 做什么 工具
进度 下载模板、装依赖这种「要等」的步骤必须有 spinner/进度，否则用户以为死了 ora（现代）、clui（我 ncp-cli 用的 Spinner）
成功 告诉用户「下一步干嘛」：cd my-app && npm run dev——出口要有行动指引 console.log 配颜色（picocolors / chalk）
失败 说清楚哪一步、为什么、怎么救；然后非零退出 catch 里结构化输出，不裸吞
颜色库换代小知识 chalk 是老将，但 ESM/CJS 兼容折腾过一轮；现代 CLI（vite/create-vue 一族）多用 picocolors（零依赖、极小）。选型时「轻、稳、无告警」比「功能多」重要—— CLI 的冷启动时间是体感的生死线。

3.3 脚本友好：CI 怎么用你

  • 检测 process.env.CI 或 --yes/-y / --defaults：跳过问答、全用默认值。
  • 非 TTY 环境（管道/CI）自动降级：关掉 spinner 动画、用纯文本输出。
  • 交互是加速器，不是必经之路——任何能力都要有纯参数表达。

四、健壮性：门禁、错误、退出码——敢进 CI 的底线

4.1 版本门禁（我的真实实现）

bin/index.js 开头就拦
const requiredVersion = pkg.engines.node;   // ">=10.0"，单一事实来源
function checkNodeVersion(wanted, id) {
  if (!semver.satisfies(process.version, wanted)) {
    console.log(chalk.red(
      'You are using Node ' + process.version + ', but this version of ' + id +
      ' requires Node ' + wanted + '.\nPlease upgrade your Node version.'
    ));
    process.exit(1);   // 不匹配就别跑，错误信息给出「当前 vs 需要」
  }
}
checkNodeVersion(requiredVersion, 'ncp-cli');
面试怎么讲：两个点：① 版本下限写在 engines，读也在代码里—— 配置和校验同源，不会漂移；② 失败信息把「你的版本 / 需要的版本」都打印出来，用户不需要猜。 这是 vue-cli 时代就被验证的标准姿势。

4.2 退出码与错误处理公约

公约 含义 反例（别这么干）
process.exit(0) 成功——或者干脆正常走完 成功了也 exit(1)，CI 直接红
process.exit(1) 失败——参数错、目录冲突、下载失败、装依赖失败 我的 ncp-cli：同名目录、模板下载失败、install 失败全部 exit(1)
错误信息三要素 哪一步 + 为什么 + 怎么办 catch(e) { console.log('error') }——什么线索都没有
异常不裸吞 Promise 要有 .catch；shell 调用要看 code 不处理 rejection → Node 打一屏警告，用户更懵

4.3 执行子进程的姿势

我用 shelljs（可行），更现代的对照
// ncp-cli：shelljs 调 npm（简单直接）
shell.exec(`npm i ${pkgName}`, { async: true }, (code) => {
  if (code === 0) resolve(1);
  else { shell.echo('模板下载失败！'); shell.exit(1); }
});

// 现代标杆更常用 execa：拿 stdout/stderr、抛异常、更好跨平台
// import { execa } from 'execa';
// await execa('npm', ['i', pkgName]);   // 失败自动 throw，退出码自然传下去
跨平台提醒 别拼 rm -rf 这类 shell 秀逗语法：Windows cmd 不认。路径用 path.join、删除/复制用 fs-extra 或 Node 原生 fs.cp（16.7+）， 子进程优先 execa/child_process 传参数数组而不是字符串命令——顺带防命令注入。

五、脚手架模式：模板从哪来、怎么生成

脚手架类 CLI（create-* / init）多一个核心问题：模板的来源与生成流水线。

5.1 模板来源四方案

方案 做法 优点 代价
npm 模板包（我的 ncp-cli） 模板发成 npm 包，CLI 里 npm i 模板包 再拷出来 走 registry、有版本、可私有源托管；团队模板即私有包 多一次 install 开销（我在创建末尾还要再装一次项目依赖）
git 仓库 clone/download tarball（vue-cli 早期模板、degit） 模板作者友好，不限语言 依赖 git/网络；私有仓库要鉴权；缓存要自己管
本地内嵌模板 CLI 包里直接塞 template/ 目录（create-next-app 部分场景） 零网络、最快、最稳 模板更新 = 发布 CLI；包体积变大
生成器插件 模板 = 代码生成逻辑（vue-cli 的 plugin 体系、create-vue 的 feature 拼装） 可组合、可改配置、能按选项拼装 实现复杂，抽象成本高

5.2 生成流水线（脚手架的标准五步）

点击图片可放大 · 五步流水线是所有脚手架的最大公约数

5.3 生成的两种哲学：拷贝 vs 插件生成

拷贝 + 重写（ncp-cli / create-next-app）

  • 模板就是成品文件，拷出来再改 name/description。
  • 实现简单、行为可预测、好排障。
  • 改动模板 = 发模板新版本。
  • 适合：内部种子工程、形态固定的技术栈。

插件/生成器（vue-cli / create-vue）

  • 用户勾选能力（Router/测试/ESLint），生成器按需拼文件、写配置。
  • 灵活、组合爆炸的可控性好。
  • 实现与测试成本高，模板逻辑也是一套代码要维护。
  • 适合：生态型脚手架、选项组合多的场景。

六、真实解剖：我的 ncp-cli，和开源标杆差在哪

6.1 ncp-cli 全流程（一个命令的生命周期）

ncp create my-app -t vue-seed 发生了什么
1. 门禁    checkNodeVersion(engines.node) → 不满足直接 exit(1)
2. 解析    commander 解析 create/my-app/-t vue-seed
3. 防呆    fs.existsSync('my-app') → 同名目录存在则退出
4. 交互    已给 name 与 -t → 只问 description（缺什么问什么）
5. 拉模板  远程 template.config.json 查 vue-seed → npm i 模板包
6. 搬运    shell.cp 模板包内容（含 .*）→ 项目根
7. 本地化  重写 package.json：name/description，剔除 _ 开头的字段
8. 装依赖  npm install（带 spinner）
9. 收尾    「创建项目成功，请进入项目目录开始工作吧！」
模板清单是远程配置（内网服务），模板本体是 npm 包
// util/template.service.js —— 业务线动态维护模板映射
const url = 'http://内网/document/ncp/.../template.config.json';
// 返回形如 [{ templateType: 'vue-seed', templateName: '@xxx/vue-seed' }, ...]
// CLI 不用发版即可上新模板——这是「配置与代码分离」的小实践
面试怎么讲：我的设计取舍：① 模板清单放远程 JSON——运营/平台方加模板不用发 CLI； ② 模板本体走 npm 私服——有版本、可回滚；③ 流程六步全链路带失败退出； ④ 已知参数跳过问答。如果重做，我会把 shelljs 换成 execa/fs-extra、加上 --yes CI 模式、生成失败时清理半成品目录、把本地模板缓存下来加速二次创建。

七、面试追问链

Q1 · 一个 npm 包怎么变成全局命令的？

答：三件套——目标文件第一行 shebang #!/usr/bin/env node 声明解释器； package.json 的 bin 字段把命令名映射到该文件；npm i -g 时 npm 把它链接进全局 bin 目录 （Windows 生成 .cmd/.ps1 垫片）。npx 则先找本地 node_modules/.bin，没有就临时下载执行，不污染全局。

Q2 · 你的 CLI 为什么要检查 Node 版本？engines 不是已经声明了吗？

答：engines 默认只是「安装时的软约束」（npm 可以装得上），运行时不保证安全。 所以我在入口用 semver 对 process.version 做硬校验，不匹配就打印「当前 vs 需要」并 exit(1)—— 配置与校验同源（都读 engines.node），不会漂移。这是把「文档约束」升级成「运行时门禁」。

Q3 · 交互式 CLI 怎么兼容 CI？

答：双轨设计。所有问答项都要有对应的 flag/位置参数表达；检测到 CI 环境变量或 --yes/--defaults 时跳过问答走默认值；非 TTY 环境关掉 spinner 动画、用纯文本。 原则是「交互是加速器不是必经之路」——create-vue/create-next-app 都是这个模式。

Q4 · 脚手架生成到一半失败了怎么办？

答：要「原子性」。先在临时目录生成完再移入，或失败时回滚删除半成品目录； 错误信息说清是哪一步（下载模板/写文件/装依赖）；exit code 非零让上层脚本能感知。 我早期版本没做回滚，失败会留残骸目录——这是我面试里可以主动说的改进点。 另外依赖安装可以做成可选（--no-install），把网络失败面收窄。

Q5 · 模板放 npm 包和放 git 仓库有什么区别？你为什么选 npm？

答：npm 包自带版本语义与 registry 分发，公司有私服时天然可托管、可审计、可回滚； git 仓库胜在不限语言、模板作者门槛低，但要处理鉴权、浅克隆和缓存。 我的场景是公司内多条业务线的种子工程——模板清单由平台方远程配置维护（加模板不用发 CLI）， 模板本体发私有 npm 包，兼顾「热更新清单」与「版本可控」。

Q6 · 如何让 CLI 的冷启动变快？

答：① 依赖瘦身：解析用 cac/commander 而不是全家桶，颜色用 picocolors 级别的零依赖库； ② 入口先解析再懒加载重模块（交互库、网络模块按需 require）； ③ 发布 files 白名单减小安装体积；④ 网络请求并行/缓存。 CLI 的体感生死线是「敲下回车到出第一行字」的间隔——vite 系 CLI 就是靠 cac + 懒加载撑起来的。

八、一页速记卡

  1. 五层模型：分发（bin/shebang/npx）→ 命令面（commander/cac + 选项军规）→ 交互（补缺 + validate）→ 健壮性（版本门禁/退出码/子进程）→ 脚手架（模板来源 + 五步流水线）。
  2. 命名服从分发：create-* 吃 npm create 的语法糖；bin 的 key 就是命令名。
  3. 选项军规：长短并存、给默认值、help 放例子、脚本里永远用长选项。
  4. 交互原则：缺什么问什么、问则校验、脚本路径永远通；CI 检测 CI / --yes。
  5. 健壮性底线：engines + semver 运行时门禁；失败 exit(1)；错误信息「哪一步/为什么/怎么救」；子进程优先参数数组（execa）。
  6. 脚手架五步：收集输入 → 拉模板 → 渲染落盘（重写 package.json）→ 装依赖（可 --no-install）→ 交接指引（下一步命令）。
  7. 模板来源：npm 包（版本/私服）/ git（灵活）/ 内嵌（最快）/ 生成器插件（可组合）——按团队约束选。
  8. 我的 ncp-cli：commander + inquirer + 远程模板清单 + npm 模板包 + engines 门禁 + Spinner；改进方向：execa、clack 观感、--yes、失败回滚。
  9. 与 create-vue 差距：观感（clack）、CI 完备性、原子生成、插件化扩展——能说出差距的候选人更可信。
  10. 金句：「好的 CLI 是可发现的命令面 + 可脚本化的接口 + 可预期的失败——交互只是加速器。」
收尾金句 「CLI 设计不是把功能翻译成子命令，而是把工具的边界画清楚： 什么该问用户、什么该有默认、什么必须拒绝执行——一个好用的命令面， 是这个工具的第二份文档。」
