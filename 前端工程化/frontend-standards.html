规范为何难落地 · 组件库 + 模板 + Lint 三板斧 · 门禁与度量 · AI 时代的契约层（AGENTS.md / skills）· 真实实践解剖 · 追问链（面试向 · 图解版）

〇、30 秒电梯答案

规范落地的本质：把「团队品味」翻译成「机制」，让正确的事最容易做，让错误的事根本做不了。 口头约定必然衰减，文档必然过期——只有被工具自动执行的规范才活着。我把落地拆成四层：

① 物化层：组件库 + 模板页——把规范做进「积木」和「起点」，写对的成本低于写错； ② 工具层：ESLint / Prettier / TS / commitlint——机器自动检查与修复； ③ 闸门层：husky / pre-commit / CI——不过不让走； ④ 契约层（AI 时代新增）：AGENTS.md / skills / rules——把同一套规范写成智能体也能读懂并遵守的契约， 对人和 AI 一视同仁。我过往的实践是「组件库 + 模板 + lint」三板斧，现在加上 AGENTS.md 这一层， 规范的受众从「团队成员」扩展到了「团队成员 + 会写代码的智能体」。

🧱 物化：做成积木

组件库 + 模板页让「合规范」成为最省力的路径——用对的 Button 比自己写一个还快。

⚙️ 工具：做成机器

ESLint / Prettier / tsc 把「风格与质量」从 code review 的口水战里拿出来，交给确定性程序。

🚧 闸门：做成强制

pre-commit + CI：不过不给过。规范最怕的不是「不知道」，而是「知道但来不及」。

📜 契约：对人和 AI 同款

AGENTS.md / skills 把品味规则写进智能体的上下文——AI 写的代码也必须过同一道 lint 门禁。

一、规范为什么难落地：死掉的三种姿势

先承认一个事实：大部分团队不缺规范文档，缺的是让规范生效的机制。规范文档最常见的三种死法：

死法 现场 根因
写完即巅峰 立项时激情输出 50 页规范 wiki，三个月后无人打开，新人靠口口相传 规范只存在于「文档层」，没有任何东西引用它、强制它
review 打架 「这里要不要拆组件」「注释用中文还是英文」在 MR 里吵十轮，最后看谁资深 该进机器的规则留在了人的品味裁决里——主观的事没有客观裁判
紧急豁免 「今天先这样，上线后重构」——重构永远在明天，破例成了新规范 没有闸门，规范是「建议」而不是「约束」；人有 deadline 时建议必输

1.1 落地公式

规范落地 = 能物化的物化 + 能自动的自动 + 能拦截的拦截 + 剩下的写成契约。 判断一条规范怎么落地，就问三个问题：① 能不能做成「用它就自然合规范」的组件/模板？ ② 能不能写成 lint 规则/脚本？③ 不能自动化的，能不能让「不合格就无法提交/合并」？ 三个都做不到的规范，大概率会死——要么删掉，要么写进 AI/人的契约层并配 review 清单。

点击图片可放大 · 越往下越是「硬约束」，落地强度：组件 < lint < 门禁 < 契约+门禁

二、传统三板斧：组件库 + 模板页 + Lint（我的实践起点）

这三样分别命中规范落地的三个痛点：复用、起点、底线。

2.1 组件库：把规范做成「积木」

它自动带来什么规范

  • 视觉规范：间距、圆角、字号、色板——用组件就是用设计令牌。
  • 交互规范：loading 态、空态、错误态、防重复提交——组件内置，业务不用各自发明。
  • 可访问性：aria、键盘操作——集中在组件库修一次，全站受益。
  • API 纪律：受控/非受控、事件命名、插槽设计——组件库定了，业务代码自然同构。

踩过的坑（组件库不等于万能）

  • 组件库覆盖不到的「页面级」问题（布局、数据流、错误处理）没人管——所以要有模板。
  • API 设计不好 → 业务方绕过组件库裸写样式，规范反而被绕开。
  • 升级成本高：组件库发大版本，所有业务方跟着改——要版本策略（peerDependencies、changelog）。

2.2 模板页：把规范做成「起点」

组件库管「零件」，模板页管「整机」——列表页、详情页、表单页、登录后的布局骨架。 新页面从模板复制/生成而不是从空白开始，路由约定、状态管理接法、请求层封装、错误边界、权限点挂载 全部在模板里示范过一次。这其实就是脚手架思想在业务开发里的应用（和 CLI 那页的「模板流水线」一脉相承）。

判断模板好坏的标准 新人不用问「这里该怎么做」，照着模板抄就对了——如果模板里还要口头补三句「我们一般这样……」， 说明模板没把规范物化完整，那三句话就该进模板或进契约文档。

2.3 Lint：把规范做成「机器裁判」

Lint 是三板斧里唯一的强制力：风格（格式、命名）交给 Prettier/ESLint 自动修， 质量（any、未使用变量、错误的相等比较）交给 ESLint/TS 报错拦下。 核心收益是把 code review 从「争论风格」解放出来，让人只看逻辑与设计。

真实规则片段（我项目的 eslint.config.mjs，flat config）
rules: {
  // 禁止 any——使用 unknown + 类型守卫
  '@typescript-eslint/no-explicit-any': 'error',
  // 优先使用 type-only import
  '@typescript-eslint/consistent-type-imports': ['error', { prefer: 'type-imports' }],
  // 禁止 require
  '@typescript-eslint/no-require-imports': 'error',
  'no-console': ['warn', { allow: ['warn', 'error'] }],
  eqeqeq: ['error', 'always'],
  'prefer-const': 'error',
  'no-var': 'error',
}
面试怎么讲：规则不是随手抄的 lint 全家桶，而是团队品味的机械化—— 「禁止 any」对应「严格类型」这条品味；「consistent-type-imports」对应「导出纪律」。 每条规则都能回答「它在防什么事故」，答不上来的规则就该删。lint 配置是团队约定的可执行版本。

三、工具层细看：Lint 体系怎么分层

不要把所有规则塞进一个 ESLint。按「谁的职责」分层，冲突最少、升级最稳：

层 工具 管什么 失败时
格式 Prettier（+ editorconfig） 缩进、引号、分号、换行——纯风格 保存时自动修 / lint --fix
语言质量 TypeScript（strict）+ typescript-eslint 类型、any、断言风格、type-only import error，编译/提交失败
代码坏味道 ESLint（含 no-var/eqeqeq/no-console…） 低级错误、不推荐写法 error/warn 分级
框架约定 eslint-plugin-vue / react-hooks 等 组件写法、hooks 依赖、模板约束 error
样式 stylelint（有 CSS 体系时） 选择器、命名（BEM）、颜色字面量 error
提交信息 commitlint Conventional Commits（feat/fix/chore…） 拒绝 commit
架构约束 dependency-cruiser / eslint-plugin-boundaries / 自写 CI 脚本 包间依赖方向、禁 import 层、文件行数上限 error（CI 拦截）
分级的用意 error = 机制拦截（不过不给过），warn = 文化提醒（review 时看一眼）。 全部设成 error 会导致「warning 疲劳」之后的「error 疲劳」，团队开始写 eslint-disable—— 那是规范失效的前兆。定期统计 disable 数量，比统计代码行数有意义。

四、闸门层：pre-commit 与 CI——「不过不让走」

工具层解决「能不能检查」，闸门层解决「检查了但有人想跳过」。规范的公信力全在这一层。

4.1 闸门的三个位置（越早越省，越晚越全）

位置 跑什么 特点
保存时（编辑器） format on save、ESLint fix on save 反馈最快，规范「长在手上」；依赖编辑器配置（.vscode/settings.json 进仓库）
pre-commit lint-staged（只查改动文件）+ 关键测试（如 test:core）+ typecheck 秒级拦截低级错误；要快——钩子超过 10s 就有人研究怎么跳过
CI / MR 全量 lint + typecheck + 测试 + 架构检查 + （可选）AI review 最终防线，慢一点没关系；分支保护强制 CI 绿才能合并
我项目的提交门禁（真实做法）
# GOLDEN_RULES 第 8 条：提交前必须通过
pnpm test && pnpm typecheck && pnpm lint

# 落地方式：simple-git-hooks 的 pre-commit
# 1. 根 package.json 的 prepare 脚本在 pnpm install 时自动安装钩子
# 2. 钩子执行 pnpm test:core（核心三包 chat / chat-vue / ui 的测试门禁）
# 3. build 脚本内部也前置了测试：pnpm test && tsup——坏产物出不了仓库
# 4. 紧急逃生口：SKIP_SIMPLE_GIT_HOOKS=1（显式、可审计，比 --no-verify 的「隐式跳过」更诚实）
面试怎么讲：门禁设计我抓住三点：① 钩子自动安装（prepare 脚本）—— 不依赖同事记得手动 setup；② 关键路径三保险——pre-commit 测试、build 前置测试、CI 全量， 单点绕过仍有兜底；③ 逃生口要显式——允许极端情况跳过，但要求写环境变量这个「故意的动作」， 而不是大家默默学会的 --no-verify。
反模式提醒 ① 钩子跑全量测试 → 一次 commit 等 5 分钟 → 全员研究跳过方法，门禁名存实亡； ② CI 只跑 lint 不跑测试 → 类型和规范的错拦住了，逻辑错照样上线； ③ 「规范」和「工具配置」两套真相 → wiki 说中文注释，eslint 没配对应规则 → 注释语言全靠缘分。 每条规范都必须能指向它的机械化检查点——指向不了的规范要补机器或删条文。

五、AI 时代的契约层：AGENTS.md / skills / rules

AI 写代码改变了规范落地的受众结构：以前规范读者只有「会来问你的同事」， 现在还有「读上下文、生成整文件的智能体」。智能体不看 wiki、不参加宣讲会—— 它只看得到喂给它的上下文。所以规范要再物化一层：写成智能体加载的契约文件。 我项目 GOLDEN_RULES 开头那句话就是这层的纲领：「这些规则代表团队的品味偏好， 通过 lint 规则和 CI 机械化执行。对人和智能体一视同仁。」

5.1 AGENTS.md：智能体的「新人入职手册」

AGENTS.md 是放在仓库根（或子目录）的 Markdown，主流 AI 编程工具（Claude Code、Codex、 Cursor 等）会自动读取。它不是写给人看的 README——README 讲「这是什么项目」， AGENTS.md 讲「在这个仓库干活的规矩」。

我项目的 AGENTS.md 骨架（真实结构）
# AGENTS.md

## 仓库概览        # 语言/包管理/构建/测试/规范——让 AI 选对工具链
## 快速导航        # 指向 ARCHITECTURE / DESIGN / GOLDEN_RULES / 执行计划
## 包结构          # monorepo 各包职责表——避免 AI 乱建文件、乱放代码
## 常用命令        # pnpm test / build:libs / typecheck / lint / release:*
## 关键约束        # ⭐ 规范的浓缩条款：
#  1. 零 HTTP 客户端依赖（请求层注入）
#  2. 包间零耦合
#  3. 类型优先 + JSDoc
#  4. 提交门禁（test:core + typecheck）
#  5. 单文件 ≤ 300 行（Markdown 不限）
#  6. 禁止尾随逗号
面试怎么讲：AGENTS.md 的设计原则：① 只写「干活需要知道的」—— 架构详情外链到 docs/，别把 50 页规范糊进去（上下文窗口贵，AI 也会失焦）； ② 约束要可判定——「单文件不超过 300 行」比「保持良好结构」有效一万倍； ③ 命令可直接复制——AI 读到就能跑，跑完就有反馈。

5.2 三层契约的分工

载体 适合放什么 生命周期
AGENTS.md（仓库级） 工具链、命令、目录职责、关键约束、禁区——每个任务都需要的背景 随仓库演进，MR 里和代码一起改
skills / 专项指令（.mimocode/skills、.claude/skills 等） 可复用工作流：「怎么发版」「怎么写组件」「怎么跑视觉回归」——按需加载的作业指导书 沉淀高频操作，比在对话里重复叮嘱稳定
rules（.cursor/rules、.editorconfig…） 格式、目录级差异约定、生成代码的风格 工具专用，进仓库共享
lint + CI（仍然兜底） 一切能自动判定的——AI 写完照样过同一道门禁 机器裁决，不信任任何生成物
核心心法：契约层不替代门禁层 AGENTS.md 是「预防」，lint/CI 是「拦截」。AI 偶尔仍会违规——这时靠的是 pre-commit 和 CI 把它拦下来， 报错信息再把 AI 拉回正轨（好的报错文案 = 给智能体的第二份文档）。 给 AI 的规范必须是「可执行的偏好」，给人的规范必须有「强制的闸门」——两层缺一不可。

5.3 AI 时代的两个新实践

  • 把报错写成人和 AI 都能读懂的「修复指引」：CI 脚本失败时打印「违反了哪条规则 → 怎么改 → 依据文件」， 智能体下一轮就能自愈，人类也省了查文档。
  • 用 AI 反哺规范：review 时发现 AI 反复犯的同一类错，要么加 lint 规则（能自动判）， 要么写进 AGENTS.md（需要语境判断）——AI 的错误分布是规范缺口的热力图。

六、真实实践解剖：品味规则的机械化

我项目里有一份 docs/GOLDEN_RULES.md——它不是「规范文档」，而是 每条品味都标注了检查方式的「可执行契约」。挑几条看它怎么被落地：

品味规则（GOLDEN_RULES） 机械化检查点 拦截层
① 零外部运行时依赖（库包 dependencies 必须为空） CI 扫 packages/*/package.json 的 dependencies 字段 CI 脚本
② 严格类型：禁 any，公共 API 显式返回类型 @typescript-eslint/no-explicit-any: error + tsconfig strict ESLint + tsc
③ 单文件 ≤ 300 行 CI 脚本扫文件行数（Markdown 豁免） CI 脚本
④ 导出纪律：index.ts 只 re-export code review 清单 + （可加）ESLint no-restricted-syntax review / 可再机械化
⑤ 命名约定（kebab-case 文件、create 前缀工厂） 部分可 ESLint（naming-convention），部分 review 混合
⑧ 提交门禁：test + typecheck + lint simple-git-hooks pre-commit + build 前置测试 + CI 钩子 + CI 双保险
⑨ 包间隔离：禁止反向 import、循环依赖零容忍 dependency-cruiser / 自写依赖图检查 CI 脚本
⑩ 禁止尾随逗号 Prettier 配置与规则一致（trailingComma: "none"） Prettier 自动修
⑪ 注释用简体中文 review + AGENTS.md 明示（AI 与人同款要求） 契约层 + review
这张表的价值（面试直接展示） 一眼看出规范的「覆盖率」：哪些进了机器（绿）、哪些还在 review、哪些还是人治。 规范落地的迭代方向就是把人治的行往左迁——迁不动的才留在契约层和 review 清单。

6.1 组件库 + 模板 + Lint + AGENTS 的全景分工

手段 解决的规范问题 失效信号
组件库 视觉/交互/API 的「零件级」规范 业务方大量写内联样式、fork 组件改内部
模板页 页面骨架/数据流/错误处理的「整机级」规范 新页面结构五花八门、新人要问「标准写法」
Lint + 门禁 风格/质量/架构约束的「底线级」规范 eslint-disable 暴涨、钩子被频繁跳过
AGENTS.md / skills 上下文/流程/品味的「认知级」规范（人 + AI） AI 反复犯同一类错、文件越写越长没人提醒

七、闭环：让规范不变成文档债

规范是活物，落地只是开始。保持它活着的最小闭环：

  1. 写下「为什么」：每条规范带一句防的事故（GOLDEN_RULES 的写法）——没有 rationale 的规范无法说服人遵守。
  2. 挂上检查点：能 lint 的 lint，能脚本的脚本，能钩子的钩子；暂时不能的，明确写「由 review 负责」。
  3. 度量违例：eslint-disable 数量、门禁跳过次数、review 中同类意见出现频率——数字比感觉可信。
  4. 定期删改：季度 review 规范本身。过时的规范比没有规范更糟——它教会所有人「规范可以不遵守」。
  5. AI 错误回流：把智能体反复犯的错固化成 lint 规则或 AGENTS.md 条款，契约层跟着长。
一句话 规范落地的终点不是「人人背诵规范」，而是「人人（和每个 AI）在无感知中被规范护着写出了对的代码」。

八、面试追问链

Q1 · 你们的前端规范是怎么落地的？（必考，答不出细节就露馅）

答：四层。① 物化——组件库 + 模板页，让合规范的写法最省力； ② 工具——ESLint（strict TS、禁 any）+ Prettier + tsc 自动检查； ③ 闸门——simple-git-hooks 的 pre-commit 跑核心测试，build 前置测试，CI 全量 + 分支保护； ④ 契约——GOLDEN_RULES + AGENTS.md，把品味规则写成「可判定条款」，对人和智能体一视同仁。 每条规范都能指向它的检查点，指向不了的会补机器或删条文。

Q2 · 规范写了没人遵守怎么办？

答：先分诊。能自动判定的 → 加 lint/脚本，从「呼吁」变「拦截」； 不能自动但可以阻断的 → 进 pre-commit/CI 门禁； 都不行的 → 砍掉或收窄成 review 清单里的一条。关键是别让规范停在「建议」—— 建议在 deadline 面前必输。另一个抓手是成本不对称设计：组件库/模板让「写对」更快，违规反而更费劲。

Q3 · ESLint 规则是不是越多越好？

答：不是。每条规则要能回答「防什么事故」，答不上来就删。 error/warn 分级：error 给必须拦的（any、eqeqeq），warn 给文化提醒。 全 error 会引发 disable 泛滥——我会监控 eslint-disable 数量作为规范健康度指标。 我们也不抄 lint 全家桶：规则集是团队品味的映射，比如「consistent-type-imports」对应导出纪律。

Q4 · AGENTS.md 和 README 有什么区别？写什么、不写什么？

答：README 面向「想了解项目的人」，AGENTS.md 面向「要在这个仓库干活的智能体/新人」： 工具链、常用命令、目录职责、关键约束、禁区。写法三条：只写干活需要的（详情外链 docs/）、 约束必须可判定（「单文件 ≤300 行」优于「保持良好结构」）、命令可直接复制执行。 它替代不了 lint——AGENTS.md 是预防，门禁是拦截，AI 写的代码照样过同一道 CI。

Q5 · AI 写的代码怎么保证符合团队规范？

答：两头夹。生成前：把规范写进上下文（AGENTS.md/skills），让智能体知道品味与约束； 生成后：不信任任何生成物，pre-commit + CI 用和人类完全相同的 lint/测试/类型门禁拦截。 再加一个反哺回路：AI 反复犯的错 → 能自动判的升级成 lint 规则，需要语境的写进 AGENTS.md—— AI 的错误分布就是规范缺口的热力图。我们 GOLDEN_RULES 明确「对人和智能体一视同仁」，就是这个意思。

Q6 · 怎么衡量规范落地的效果？

答：看违例而不是看文档。① 违例率：eslint-disable 数量、门禁跳过次数； ② review 质量：风格类评论占比下降、设计类讨论占比上升； ③ 交付一致性：新人首个 PR 的返工次数、同类事故是否重复发生； ④ 契约健康度：AI 相关返修是否收敛。数字下降说明机制在起作用，否则就是规范与工具脱节了。

九、一页速记卡

  1. 本质：把团队品味翻译成机制——写对比写错省力，错误根本过不去。
  2. 三种死法：写完即巅峰（无引用）、review 打架（主观无裁判）、紧急豁免（无闸门）。
  3. 落地公式：能物化的物化 + 能自动的自动 + 能拦截的拦截 + 剩下的写成契约。
  4. 三板斧：组件库（零件级规范）→ 模板页（整机级规范）→ Lint（底线级规范）。
  5. Lint 分层：格式（Prettier）/ 语言（tsc+ts-eslint）/ 坏味道（ESLint）/ 框架 / 架构（依赖边界）；error=拦截，warn=提醒。
  6. 闸门三位置：保存时 < pre-commit（要快！）< CI+分支保护；逃生口要显式（SKIP_…）不要隐式（--no-verify）。
  7. AI 契约层：AGENTS.md（干活的规矩）/ skills（可复用作业指导书）/ rules（格式与风格）——可判定、可复制、只写干活需要的。
  8. 一视同仁：AI 写的代码过同一道 lint/测试门禁；契约是预防，门禁是拦截，两层缺一不可。
  9. 真实工程：GOLDEN_RULES 11 条各带检查方式（禁 any→ESLint error、300 行→CI 脚本、零依赖→CI 扫 package.json）；pre-commit 跑 test:core。
  10. 闭环：写清为什么 → 挂检查点 → 度量违例（disable 数/跳过数）→ 定期删改 → AI 错误回流成规则。
收尾金句 「规范落地的终点不是人人背诵规范，而是人和智能体在无感知中被规范护着，写出了对的代码—— 能自动的交给机器，不能自动的写成契约，契约之外的交给闸门。」
