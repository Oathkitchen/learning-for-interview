〇、先给结论：30 秒电梯答案

pnpm 解决的是「装」的问题：包内容先放进全局的内容寻址存储（content-addressable store），再用硬链接接到 node_modules/.pnpm 虚拟存储、用符号链接暴露给项目——同一份文件物理上只存一份，所以快、省磁盘；同时 node_modules 严格按照 package.json 构建，依赖声明了才可见，天然没有幽灵依赖。

workspace 解决的是「连」的问题：根目录一个 pnpm-workspace.yaml 声明哪些目录是包，包与包之间用 workspace:* 协议互相引用——本地装依赖时是链接到仓库内的包，发布到 registry 时自动替换成真实版本号。

monorepo 解决的是「管」的问题：多个相关包放一个仓库，换来原子提交、跨包重构、共享 tsconfig / ESLint / 构建配置和统一发布节奏；代价是仓库治理与构建复杂度，所以需要 --filter、拓扑序、构建缓存这些编排能力来把「全量构建」变成「只构建改动的那条链」。

落到我自己的实践：hsa-neu-ai-platform-fe 是 pnpm 10 workspace 单仓，8 个包 + 1 个联调示例；根 package.json 用 --filter / -r 统一构建与发布顺序，内部库用「peerDependencies 声明范围 + devDependencies 里 workspace:*」双写，.npmrc 做 scope registry 分流，发布链用 pnpm build && changelogen --release && pnpm pack 做门禁。

📦 pnpm = Performance + Node

一、包管理器三世同堂：npm / yarn / pnpm 到底差在哪

面试里聊 pnpm，最好先拉一条时间线——很多「pnpm 的优势」其实是前两代包管理器的历史遗留问题：

  1. npm v2 及以前：嵌套安装。每个依赖在 node_modules 里各放一份自己的依赖树。好处是语义干净，坏处是同一个包被重复安装几十上百次，磁盘与安装时间爆炸。
  2. npm v3 / yarn classic：扁平化提升（hoisting）。把依赖树「拍平」放到顶层 node_modules，同版本只留一份——重复问题解决了，但引入了新的病： 你的代码可以 import 一个你从没声明过的包（它只是某个间接依赖，被提升到了顶层）。这就是幽灵依赖。
  3. yarn workspaces（2017）：把「单仓多包」做进包管理器，monorepo 从民间手艺变成官方能力。
  4. pnpm（2017 至今）：换一条路。不提升、不复制——文件存全局 store，用硬链接/符号链接组装 node_modules。既去重，又严格。

安装模型 拍平提升到顶层 node_modules 同 npm（提升更激进）+ 全局缓存 全局 store + 硬链接 + 符号链接，不提升

重复包 同版本去重，异版本嵌套 同左 同内容全局只存一份，跨项目共享
node_modules 体积 大（每个项目一份完整拷贝） 大 小（只存链接与少量元数据）
重复安装同一依赖 重新复制/解压 走缓存后仍要复制进项目 直接建链接，几乎不落盘新字节
workspace 支持 npm 7+ 有 workspaces 字段，生态一般 yarn workspaces（开山之作） pnpm-workspace.yaml，内置且灵活（支持取反排除）
任务编排 需接 lerna/nx 等外部工具 需外部工具 内置 --filter / -r 与拓扑序（但无构建缓存）
lockfile package-lock.json yarn.lock pnpm-lock.yaml（唯一一份，全仓共享）
补充：第三条路线 yarn berry 的 PnP（Plug'n'Play）干脆不生成 node_modules，用 .pnp.cjs 解析表 + zip 包直接解析依赖——最彻底，但与多数存量工具链（老版 jest、部分原生模块、IDE 插件）兼容性代价大。pnpm 也提供 node-linker=pnp，同理属于「可选项而非默认」。回答这类题的姿势：三条路线分别是 「拷贝」「链接」「不建目录」，pnpm 选了兼容性与严格性的最大公约数。

二、pnpm 原理：store、硬链接、符号链接三件套

pnpm 安装一个包时不把文件内容复制进项目，而是分三层组装。理解这三层，80% 的 pnpm 面试题都能推导出来：

  1. 全局 store（内容寻址存储）：所有下载过的包文件，按 内容的 hash 存放在全局目录（如 ~/.local/share/pnpm/store/）。同一份内容 物理上只存一次——A 项目装过 vue@3.5.32，B 项目再装就不再下载、不再落盘。
  2. 硬链接（hard link）：node_modules/.pnpm（虚拟存储）里的文件与 store 里的文件是同一份磁盘数据的两个目录项、同一个 inode。不是复制，所以创建极快、不占双倍空间。
  3. 符号链接（symlink）：项目 node_modules 顶层那些「看起来正常的包目录」， 其实是指向 .pnpm 虚拟存储里对应版本的指针。你 import 'vue' 走的就是这条链接链。

2.3 硬链接与符号链接：从「文件名 ≠ 文件本身」讲起

很多人卡住的点在于：把「链接」想象成 Windows 快捷方式或 npm 的提升，于是永远讲不清。 正确的起点是文件系统的一个基本事实——目录里存的不是文件，是「名字 → 编号」的对照表：

  • 磁盘上的文件内容（字节）由 inode（索引节点）标识；inode 里存着权限、大小、 数据块位置等元数据——inode 是文件的「真身」。
  • 目录项（dentry）只是「文件名 → inode 编号」的一行记录。名字是贴在真身上的标签， 可以不止一个标签。
  • 于是「链接」就有了两种截然不同的玩法：再贴一个标签（硬链接），或者写一张指路条（符号链接）。

维度 硬链接（hard link） 符号链接（symlink / soft link）
本质 同一 inode 的另一个名字（dentry 多了一行） 一个存着目标路径的特殊文件
读它得到什么 就是文件本身——和原名完全平等，没有「谁是原文件」 内核顺着路径打开目标，使用者无感（自动跳转）
复制字节吗 不复制——建链接只是改目录项，毫秒级 不复制——只写几十字节的路径
跨文件系统/跨盘 ✗ 不能（inode 编号只在本文件系统内有意义） ✓ 可以（路径可以指向任何挂载点）
链接目录 ✗ 不能（防目录环，各系统都禁） ✓ 可以
目标/另一个名字删除后 另一个名字不受影响，数据仍在 变成死链（访问报 ENOENT）
pnpm 里的用途 store 文件 ↔ .pnpm 里的文件：同一份字节，跨项目去重 顶层 node_modules/vue → .pnpm/…/vue：只暴露声明过的
为什么两个都要？一句话分工 硬链接解决「字节」：同一内容只落盘一份，建链接零拷贝——这是「快、省」的来源； 符号链接解决「形状」：让项目顶层的 node_modules 只长出声明过的依赖、其余藏进虚拟存储——这是「严格」的来源。 少任何一个，pnpm 的模型都不成立。

2.4 三大操作系统怎么支持？Windows 为什么麻烦

结论先说：Linux / macOS / Windows（NTFS）都原生支持硬链接和符号链接， 这不是 pnpm 自己发明的能力，而是文件系统层的东西。差异在于权限模型和降级策略：

能力 Linux macOS Windows（NTFS）
硬链接（文件） ln a b，同一挂载点内 同 Unix，同卷内 mklink /H / CreateHardLink；同卷内；无需管理员
硬链接（目录） ✗ 禁止（防环） ✗ 禁止 ✗ 禁止 → 用 junction 代替
符号链接 ln -s，原生，无特权 同 Unix，原生 mklink /D；需要管理员或开发者模式（SeCreateSymbolicLinkPrivilege）
目录联接（junction） （用 bind mount） （用 bind mount） mklink /J：指向本地目录，无需管理员
跨文件系统硬链接 失败 EXDEV 失败 EXDEV 失败（跨卷无效）
Node.js API fs.link / fs.symlink 同左 同左，symlink 需声明类型：'junction' | 'dir' | 'file'

pnpm 在 Windows 上的实际策略（面试加分点）

  • 目录链接优先用 junction：junction 指向本地目录时不需要管理员权限、行为稳定—— 所以 Windows 上 node_modules 里的包目录常常是 junction 而不是「真正的符号链接」， 但对 Node 的模块解析来说效果等价（都是路径跳转）。
  • 文件继续用硬链接：store ↔ .pnpm 的去重依赖它；同卷时无需任何特权，速度与 Linux 一致。
  • 跨卷/跨盘自动降级为复制：store 在 D 盘、项目在 E 盘时，硬链接建不了（EXDEV）， pnpm 会把文件复制过去——安装变慢、磁盘翻倍。所以最佳实践是 pnpm store path 与项目放同一块盘。
  • 符号链接特权不足时：开 Windows「开发者模式」即可让普通用户创建 symlink； 完全不支持的环境可退回 node-linker=hoisted（模拟 npm 提升，但失去严格性）。

面试浓缩版（可直接背） 「硬链接是同一个 inode 的另一个名字，不复制字节、只能同盘、不能链目录，删掉一个名字数据还在—— pnpm 用它把 store 和各项目的 .pnpm 连成同一份字节；符号链接是存着目标路径的小文件， 可以跨盘、可以链目录、目标没了会成死链——pnpm 用它把声明过的依赖暴露到顶层 node_modules。 三系统文件系统层都支持：Linux/macOS 原生无特权；Windows 上文件用硬链接、目录优先 junction （免管理员），symlink 需要管理员或开发者模式；store 和项目跨盘时硬链接失败会退化为复制， 所以 store 尽量和项目同盘。」

2.5 灵魂拷问：为什么不能只用硬链接，把 node_modules 拼出来？

一句话答案：硬链接的单位是「文件」，依赖图的单位是「包目录」。 硬链接只能给一个文件再贴一个名字，没法让同一个目录出现在两个路径下； 而 node_modules 的本质是「一堆包目录 + 目录之间的嵌套关系」。所以 pnpm 文件层用硬链接（共享字节），包层用符号链接（拼出依赖图）—— 两层各用各的原语，谁也替代不了谁。

官方的构建过程：先硬链接文件，再用符号链接搭图

pnpm 官方文档（pnpm.io/zh/symlinked-node-modules-structure）把安装分成两步， 原文大意：「node_modules 中每个包的每个文件都是来自内容可寻址存储的硬链接——这是 node_modules 里唯一的『真实』文件。一旦所有包都硬链接到 node_modules，就会创建符号链接来构建嵌套的依赖关系图。」

2.6 pnpm runtime：项目级 Node.js 管理，为什么能取代 nvm

一句话定位：nvm 管的是「你这台机器上全局的 node」，靠 shell hook 和 PATH 切换； pnpm runtime 管的是「这个项目要用的 node」——版本写进 package.json、精确版本和校验和锁进 pnpm-lock.yaml， pnpm install 自动下载，项目的脚本（v12 起连裸 node 也是）自动走这个版本。 版本声明跟着仓库走，而不是跟着某台电脑的 shell 配置走。

用法一：项目里锁定 Node 版本（推荐，团队级）

package.json：devEngines.runtime（pnpm ≥ 10.14）
{
  "devEngines": {
    "runtime": {
      "name": "node",
      "version": "^24.4.0",
      "onFail": "download"
    }
  }
}

声明之后，pnpm 的行为（官方文档描述的流程）：

  1. pnpm install 把 ^24.4.0 这个范围解析成当时最新的匹配版本（比如 24.11.2）；
  2. 把这个精确版本号 + 校验和写进 pnpm-lock.yaml——下次所有人装到的是同一个 Node，不是「某个满足 ^24 的 Node」；
  3. onFail: "download" 表示本机没有就自动下载（还支持 error / ignore 等策略，可用 runtimeOnFail 全局覆盖）；
  4. 项目里的脚本自动用这份本地 runtime跑，和你机器上全局的 node 是谁无关；自 v12 起，项目内直接敲 node xxx.js 也跟随这个钉子（可用 globalShims 关掉，或单次 PNPM_SHIM_BYPASS=1 跳过）。
甚至可以一次钉多个运行时（node + deno）
{
  "devEngines": {
    "runtime": [
      { "name": "node",  "version": "^24.4.0", "onFail": "download" },
      { "name": "deno",  "version": "^2.4.3",  "onFail": "download" }
    ]
  }
}

顺带一提：pnpm 自己的版本也有对应机制——devEngines.packageManager 支持版本范围 （比只能写死精确版本的 packageManager 字段更灵活），解析结果同样进 lockfile （packageManagerDependencies）：

连 pnpm 自身也钉住
{
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": ">=11.0.0 <12.0.0",
      "onFail": "download"
    }
  }
}

用法二：命令行安装/切换（机器级，替代 nvm install / nvm use）

pnpm runtime（别名 rt）常用命令
pnpm runtime set node 22 -g        # 全局安装 Node 22（机器级默认）
pnpm runtime set node lts -g       # 装最新 LTS
pnpm runtime set node latest -g    # 装最新稳定版
pnpm runtime set node nightly -g   # 预发布通道（也支持 rc、rc/22、代号如 argon）
pnpm runtime set deno 2 -g         # 不止 node：deno
pnpm runtime set bun latest -g     # 以及 bun

# 不加 -g 则装进当前上下文；支持的运行时统一是：node / deno / bun

用法三：依赖包声明「我需要什么 Node」（engines.runtime，pnpm ≥ 10.21）

这是给包作者用的：某个依赖对 Node 版本有硬要求，可以在自己的 package.json 里声明， pnpm 会自动为它准备匹配的运行时——CLI 应用会被绑定到所需版本执行，postinstall 也会用指定版本跑。这在 nvm 体系里根本没法表达（nvm 只管你机器的全局 node，管不了某个依赖的偏好）。

依赖包里的声明
{
  "engines": {
    "runtime": {
      "name": "node",
      "version": "^24.11.0",
      "onFail": "download"
    }
  }
}

为什么说它能取代 nvm？逐条对比

维度 nvm / n / fnm pnpm runtime
版本声明在哪 .nvmrc / .node-version（单独文件，靠人记得执行 nvm use） package.json 的 devEngines.runtime——就在清单里，和依赖声明同级，进版本库
精确到哪个版本 范围或别名（lts/*），装完是「当时匹配的某个」 解析后精确版本 + 校验和写入 lockfile，全团队/CI 装到同一个 Node
何时生效 进目录要记得 nvm use；忘了就是全局 node 在跑 pnpm install 自动解析/下载；脚本自动用本地 runtime（v12 裸 node 也跟随）
shell 依赖 要往 .bashrc/.zshrc 写 hook，改 PATH；新开终端/CI 都要初始化 无 shell hook、不改全局 PATH；CI 只需要「装好 pnpm 然后 install」
「谁的版本」 机器级：一台电脑一个「当前 node」，多项目并发时容易串 项目级：每个项目钉自己的，互不干扰；机器级需要时再 -g 装一个默认
可复现性 lockfile 锁了依赖，但 node 本身不进 lockfile——「依赖锁了、运行时没锁」 依赖和运行时一起锁，真正端到端可复现
多运行时 只管 Node（deno/bun 要另装管理器） node / deno / bun 统一同一套机制
给依赖用 ✗ 表达不了「这个依赖需要 node ≥24」 engines.runtime 可按包声明并自动满足
本质差别（面试答到这一层就赢了） nvm 是环境管理器：它假设「Node 是机器上的全局资源」，用 PATH 魔术切换「当前」是谁—— 版本选择发生在你按回车的那一刻，和项目无关。 pnpm runtime 是依赖管理的延伸：它假设「Node 也是这个项目的一份依赖」， 声明进清单、锁定进 lockfile、由 install 分发——版本选择发生在解析依赖图的时候， 自动且可复现。包管理器比 shell hook 更有资格管运行时，因为只有它知道 lockfile 里锁了什么。
实战注意 ① 首次 onFail: "download" 会拉一份 Node 发行版（几十 MB），CI 上记得缓存 pnpm 的 缓存目录（pnpm cache path）；② 老项目想渐进迁移：可以先只用 pnpm runtime set node lts -g 当「更好的 nvm」，再把 devEngines.runtime 补进 package.json；③ 官方从 v11 起安装 Node 不再捆绑 npm/npx/corepack （文件数减半），需要 npm 的话 pnpm add -g npm 单独装——这反而是个加分考点： 「连 npm 都成了可选件」。
面试怎么答这题 「pnpm runtime 能取代 nvm，是因为它把 Node 从『机器的全局状态』变成了『项目的依赖』—— 版本写在 devEngines.runtime 里，pnpm install 解析后把精确版本和校验和 锁进 lockfile，脚本（v12 起连裸 node）自动用这份运行时。相比 nvm：不用 shell hook、 不用记得 nvm use、CI 不用额外初始化、多项目不串版本，而且依赖和运行时一起锁、真正可复现。 它还能管 deno/bun，并通过 engines.runtime 让依赖声明自己的 Node 需求—— 这是 nvm 这类环境管理器在架构上做不到的。一句话：包管理器比 shell 更有资格管运行时， 因为只有它掌握 lockfile。」
为什么快？

命中 store 的包不下载、不解压、不复制，只是创建链接与写元数据；冷启动首次下载后，后续项目安装接近「秒装」。

为什么省？

同内容跨项目只存一份。几十个前端仓库都装 vue@3.5.x，磁盘上只有一份 vue。

为什么严格？

顶层 node_modules 只有你声明的依赖；其余全部藏在 .pnpm 虚拟存储里，由各自的依赖链解析。

逃生舱口

老项目兼容可临时开 node-linker=hoisted（模拟 npm 提升）；不建议长期开——等于主动放弃严格性。

pnpm 10 的新考点 pnpm 10 起默认拦截依赖包的构建脚本（install/postinstall 等），需要在配置里用 onlyBuiltDependencies 白名单显式放行（或 pnpm approve-builds 交互批准）。理由：供应链安全—— 不可信包不该在安装时随意执行任意代码。回答时可顺带一句：这是包管理器近年最重要的安全默认值变化。

三、幽灵依赖（Phantom Dependency）：npm 生态的集体阴影

先看一段「最短破案故事」。你的 package.json 里只装了 webpack，但你的业务代码里写着 import semver from 'semver'—— semver 你从来没装过，可它本地能跑、CI 能跑、上线也能跑。 直到某天升级了 webpack，构建突然报 Cannot find module 'semver'， 报错栈指向你的业务代码，可你一个依赖都没删过。这不是玄学，是 hoisting（提升）埋下的时间炸弹。

定义：代码里 import 了 package.json 里没有声明的包， 却依然能正常运行——因为它只是你某个间接依赖的依赖，被提升到了顶层 node_modules， 恰好「看起来像」你的直接依赖。没声明却可见，像不像一只住在你家的幽灵？

3.1 它是怎么长出来的：安装过程逐步拆解

设定一个最小场景。你的声明很简单，只有 A、B 两个包——注意 C 从头到尾没出现在你的 package.json 里：

你的 package.json（声明层——这是「唯一的事实」）
{
  "dependencies": {
    "A": "1.0.0",
    "B": "1.0.0"
  }
}

但 A 和 B 自己都依赖了 C（这很正常，它们各自的 package.json 里写着）：

间接依赖的声明（你看不见这层，但 npm 会照做）
A@1.0.0 的 package.json → { "dependencies": { "C": "2.0.0" } }
B@1.0.0 的 package.json → { "dependencies": { "C": "2.0.0" } }

npm/yarn 安装时发现 A、B 都要 C@2.0.0，为了不重复安装两份，把 C 提升（hoist）到顶层 node_modules——「去重」的初衷是好的，副作用却要命：

点击图片可放大 · 幽灵诞生的三个条件：有人间接依赖它 + 提升把它放到了你够得着的地方 + 你写了 import

3.2 Node 为什么「配合演出」：解析算法没毛病，提升有毛病

Node 的模块解析（简化版）：从 require/import 那个文件所在目录开始， 逐级向上找 node_modules/包名，找到第一个就停——找不到就一路向上爬到磁盘根。

一次完整的解析（你的 src/user.js 里 import "C"）
/项目/src/node_modules/C          ← ① 没有，继续向上
/项目/node_modules/C              ← ② 有！（C 被提升到这了）→ 命中，解析成功
# 如果这里也没有：
/node_modules/C                   ← ③ 继续向上……一般到项目根就该报错了

「向上找」这个设计本身是为嵌套 node_modules服务的（内层依赖优先，找不到再找外层）， 没毛病。问题出在 hoisting 把「别人的依赖」放到了你够得着的位置—— Node 只认「node_modules 里有没有叫这个名字的目录」，它根本不知道、也不关心 是谁把 C 放在那里的。于是：提升决定了你能看见谁，而你的代码以为「看见的 = 我声明的」。

一个比喻 npm 的 node_modules 像一个开放式货架仓库：为了省空间把所有货物平铺在地上， 你拿自己清单上的货没问题，但也会「顺手」拿到别人的货——而且拿得理直气壮，因为架子上没有标签写「这是谁的」。 pnpm 的 node_modules 像带门禁的货架：你的柜子里只有你声明过的东西，别人的货在别人的柜子里（虚拟存储），你刷不开。

3.3 为什么叫「幽灵」：三个特征

特征 具体表现 后果
不请自来 从没声明，却在 node_modules 顶层可见 依赖图失真：package.json 不再是事实来源，真实可用集 = 声明 ∪ 被提升的集合，没人说得清有多大
来路不明 你说不清 C 是被谁、因为什么带进来的 无法评估风险：不知道它为什么在，也就不知道它什么时候会走
不告而别 只要间接依赖变了、lockfile 重生成、换台机器 install，它就可能消失 时间炸弹：「我什么都没改」却突然崩，且报错指向无辜的业务代码

3.4 真实翻车时间线（最常见的三种）

场景 1换台机器 / CI 挂了
你本地 node_modules 是上次装的，C 还在。同事 clone 后重新 install， npm 版本或提升结果不同，C 没上顶层——他的构建立刻报 Cannot find module 'C'。「我本地是好的」是幽灵依赖案件的标准开场白。
场景 2升级一个「完全不相关」的依赖
把 B 从 1.0 升到 2.0。B@2 不再依赖 C（或换了内部实现）。 C 从顶层消失 → 你 import 的 C 崩了。报错栈指向你的业务文件， 可你升级的明明是 B——故障点和变更点隔着一整层依赖树。
场景 3卸掉「看起来没用」的包
package.json 里发现 A 好像没被 import 了，npm uninstall A。 但其实你代码里的 import C 一直靠 A 的依赖树把 C 带上来—— A 一走，C 也走了。卸包卸出了连环命案。

3.5 同一段代码，npm 和 pnpm 两种命运

业务代码 src/user.js（你从来没有安装过 lodash）
// package.json 里只有 { "dependencies": { "webpack": "^5" } }
// 而 webpack（或它的某个间接依赖）恰好带了 lodash

import debounce from 'lodash/debounce';   // lodash 你从来没声明过

// npm / yarn 下：跑得飞快，测试全绿，没人报警
// pnpm 下：Error: Cannot find module 'lodash'
//          ← 安装完第一次构建就抓住你，而不是三个月后
正确姿势只有一个 用到了就显式声明：pnpm add lodash（或 npm i lodash）。 不要嫌麻烦——多写一行 package.json，换的是「三个月后不炸」。 需要排查时：pnpm why lodash 一眼看到是谁带进来的、版本是多少。

3.6 危害清单 & pnpm 怎么根治

为什么危险

  • 不可复现：本机能跑，CI / 新同事机器挂——取决于间接依赖的版本与提升结果。
  • 升级地雷：间接依赖大版本一升，你「偷偷用着」的 API 没了，报错却指向你的业务代码。
  • 依赖图失真：package.json 不再是事实来源，真实可用集合 = 声明 ∪ 被提升的集合，没人说得清。
  • 删除依赖不等于移除：你以为卸干净了，其实还在 import 别人的依赖。
  • 安全面扩大：你能 import 到的包，理论上也是攻击面的一部分（尤其被供应链投毒时）。

pnpm 怎么解决（回到第二章的结构）

  • 结构上不可见：顶层 node_modules 只有你声明过的包（符号链接）；没声明 → Cannot find module，当场暴露。
  • 别人的依赖关在虚拟存储里：C 只存在于 .pnpm/A@1/node_modules/ 这种「A 自己的视角」下，你的代码解析不到。
  • 立刻可修：报错逼你把用到的包写进 dependencies，依赖图恢复诚实——第一天就修，而不是上线后。
  • 可审计：pnpm why <pkg> 一键看「谁引入了它、为什么」。
  • 兼容开关：.npmrc 里 shamefully-hoist=true 可临时退回 npm 行为（慎用，等于放幽灵回屋）。

3.7 自检与排查：怎么把幽灵揪出来

典型现场：一个「缺失依赖」的排查过程
# 现象：升级某个依赖后，构建突然报 Cannot find module 'semver'
# npm/yarn 下：semver 明明没装，却一直能 import（被提升的幽灵依赖）

pnpm why semver        # 看它被谁带进来的（依赖链）
pnpm add -D semver     # 用到就显式声明——这才是正确姿势
# 若确需全局提升（老插件/二进制场景）才在 .npmrc 打开：
# shamefully-hoist=true   # 等价于把 node_modules 拍平成 npm 的样子
  • 最粗暴的体检：清掉 node_modules 和 lockfile 重新 install，还能跑的 import 都要打问号（前提是安装结果可复现）。
  • 迁移检测器：把项目切到 pnpm 跑一遍 build/test——幽灵依赖会集中报错暴露，一次性清干净再切回来或常驻 pnpm。
  • 工具辅助：depcheck、knip 等可以扫描「代码里 import 了但 package.json 没声明」的包，纳入 CI 定期跑。
  • 预防：新项目直接用 pnpm（严格结构是默认值）；存量项目把「显式声明缺失依赖」当成一次性的技术债清理。
面试金句 幽灵依赖的本质是「依赖声明与运行时可见集不一致」。npm/yarn 用提升换安装效率，付出了语义失真的代价—— Node 的解析算法只看「node_modules 里有没有这个目录」，不看「是谁声明的」，于是被提升的间接依赖就冒充了直接依赖； pnpm 用链接结构保证「package.json 即真相」：顶层只有声明过的包，别人的依赖锁在各自的虚拟存储条目里。 代价是个别不规范的老包要显式补声明或临时开兼容开关——但这是第一天就付的账，不是三个月后连本带利。

四、workspace：pnpm-workspace.yaml 与 workspace: 协议

4.1 workspace 声明：哪些目录算「包」

根目录 pnpm-workspace.yaml（我项目的真实写法）
packages:
  - 'packages/*'        # 8 个库/组件包
  - 'examples/*'        # 联调示例应用（也纳入统一安装与 filter）
  - '!packages/dev-starter'   # 取反：把 dev-starter 排除出本 workspace
  • glob 声明范围；支持 ! 取反排除——这是 pnpm 相比 yarn workspaces 更灵活的一点。
  • 根目录执行 pnpm install 时，所有命中的包共享同一份 lockfile、同一个虚拟 store，依赖版本天然对齐。
  • 配置文件可再放 overrides（强制统一某依赖版本）、catalogs（pnpm 9.5+ 的「目录级版本清单」，多包共用一套版本号）等。

4.2 workspace: 协议——本地链接、发布替换

写法 本地（workspace 内） 发布到 registry 后 适用场景
workspace:* 链接到仓库内的包（任意版本） 替换成精确版本，如 2.17.0 内部库之间最常用
workspace:^ / workspace:~ 同上 替换成 ^2.17.0 / ~2.17.0 发布后希望下游吃补丁更新
link:../pkg 软链接到目录 原样保留（危险） workspace 外的本地引用，慎用
file:../pkg.tgz 安装 tar 包副本 原样保留 不走 registry 的离线分发
高频追问：workspace:* 发布后会不会坏？ 不会——publish 时 pnpm 会把 workspace:* 重写成真实版本号再打 tar 包（pnpm pack / pnpm publish 都会做）。你可以解包验证。所以发布产物里永远看不到 workspace 字样，npm 上的消费者无感知。
关键区别：链接到的是「源码目录」，不是「构建产物」 本地链接后，别人 import 你时走的是你 package.json 的 exports/main 指向——如果指向 ./dist/…，那必须先 build 才能被消费。这就是为什么很多 monorepo 要么用 publishConfig + 源码出口做开发态，要么像我项目一样在发布/联调前显式跑构建链（见第七章）。

五、monorepo：动机、代价与真实目录形态

monorepo（单仓多包）是一种组织形态，不是某个工具：把多个强相关的包放进一个仓库， 用统一的依赖安装、构建、测试、发布流程治理。与之相对的是 polyrepo（多仓多包）。

收益（为什么值得）

  • 原子变更：改接口 + 改所有调用方 = 一个 commit，code review 一次看全。
  • 跨包重构安全：重命名/改签名后全仓编译测试兜底。
  • 一份工具链：tsconfig / ESLint / Prettier / CI 定义一次，全包生效。
  • 依赖版本天然统一：单 lockfile，杜绝「A 仓 vue3.4、B 仓 vue3.5」的幽灵分裂。
  • 复用与拆分自由：先抽包后发版，内部迭代不必走发布流程。

代价（面试必须主动说）

  • 仓库治理：权限边界模糊、历史膨胀、所有人 clone 全量。
  • 构建复杂度：包之间有依赖图，全量构建变慢 → 需要 filter/拓扑/缓存。
  • 耦合风险：改哪儿都牵一发 → 需要清晰的包边界与分层。
  • CI 挑战：不能「全量跑到底」，要用 affected 思维只跑改动链。
  • 版本策略：独立版本 vs 锁步版本，发布顺序要编排。

│  ├─ portal-assistant/  # @hsa-ai/portal-assistant 悬浮窗 → 组合 ui + page-context
│  ├─ drg-insight/       # @hsa-ai/drg-insight

└─ examples/

怎么判断「要不要 monorepo」 三个信号满足两个就上：① 包之间频繁联动变更（改接口要同步改 3 个仓库）； ② 需要共享构建/规范配置且多仓复制粘贴已经失控；③ 存在内部依赖链（A 发版依赖 B 先发）。 反之：包之间几乎零耦合、发布节奏与团队边界完全独立——多仓更省心。

六、任务编排：--filter 圈范围，拓扑序定先后

monorepo 装完依赖只是第一步，真正的日常是「在几百个脚本里，只跑我该跑的那部分」。 pnpm 内置两个维度的编排：范围（filter）与顺序（拓扑）。

6.1 两个核心开关

递归执行：-r / --recursive（默认按依赖图拓扑排序）
pnpm -r build                 # 所有包，按「依赖者后跑」的拓扑序执行
pnpm -r build --parallel      # 并行跑（无依赖关系时提速；注意日志交织）
pnpm -r test --no-bail        # 一个失败不中断，跑完所有再报
pnpm -r --aggregate-output run build   # 各包输出聚合，CI 日志更干净
pnpm -r exec rm -rf dist       # 在每个包目录里执行 shell 命令
过滤执行：--filter（圈定「跑谁」）
写法 含义 我项目里的真实用例
--filter <精确名> 指定一个包 pnpm --filter @hsa-ai/chat build
--filter '<glob>' 按包名通配 pnpm --filter "@hsa-ai/*" build（build:libs）
--filter ./路径 按目录过滤 pnpm --filter ./examples/ai-test-app dev
--filter ...<pkg> 目标包 及其所有依赖（先把地基建好） 发布 ui 前先构建 chat、chat-vue
--filter <pkg>... 目标包 及所有依赖它的包（影响面） 改了 chat → 把用到它的全部重测
--filter ...[<git-ref>] 相对 git 变更涉及的包（affected 思维） CI 上只测改动链：--filter ...[origin/main]
记忆锚点 ... 在前 = 「它的上游（它依赖谁）」，发布/构建前置链用它； ... 在后 = 「它的下游（谁依赖它）」，改动影响面/回归测试用它。

6.2 拓扑序：为什么必须「先地基后大楼」

点击图片可放大 · 这张图直接决定了「改了 chat 之后，CI 要重跑谁」

pnpm 编排 vs 任务缓存 pnpm 的 -r/--filter 解决的是「跑哪些、按什么顺序」，但它没有内容哈希缓存—— 每次都是真跑。要「没改过的包直接复用上次结果」，就得上 Turborepo/Nx 的缓存层（见第九章）。 两者是叠加关系：官方推荐组合就是「pnpm 当包管理器 + turbo 当任务运行器」。

七、真实仓库解剖：hsa-neu-ai-platform-fe 怎么落地

面试里「你实际用过 monorepo 吗」这题，最有力的回答结构是：目录形态 → 一个真实配置细节 → 它解决了什么问题 → 我踩过什么坑。下面 7 块全部来自我维护的真实工程（配置已脱敏），每块配「面试怎么讲」。

7.1 workspace 取反排除：给 dev-starter 做「双向隔离」

根 pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'examples/*'
  - '!packages/dev-starter'    # 取反：根 workspace 不吸收它
packages/dev-starter/pnpm-workspace.yaml（它自己的）
# 本目录自己就是 workspace 根：pnpm 向上查找在这里就停，
# 根目录的 pnpm i 也不会波及本目录 → 双向互不影响
packages: []    # 空数组：只有根项目自己，不含任何子包
面试怎么讲：取反语法 !pattern 是 pnpm workspace 的实用特性。 dev-starter 是脚手架/实验目录，依赖体系与主仓完全不同——根 workspace 排除它（方向一）， 它内部自带 pnpm-workspace.yaml 截断向上查找（方向二），于是两套 install 互不污染， lockfile 也不混。这就是「配置即边界」。

7.2 根 package.json：把编排写进脚本，而不是写进文档

根 package.json（节选）
{
  "private": true,
  "scripts": {
    "build:libs":   "pnpm --filter \"@hsa-ai/*\" build",
    "build:all":    "pnpm -r build",
    "typecheck":    "pnpm -r typecheck",
    "test:core":    "pnpm --filter @hsa-ai/chat build && pnpm --filter @hsa-ai/chat-vue build && pnpm --filter @hsa-ai/ui test",
    "release:ui":   "pnpm --filter @hsa-ai/chat build && pnpm --filter @hsa-ai/chat-vue build && pnpm --filter @hsa-ai/ui release",
    "release:all":  "pnpm --filter \"@hsa-ai/*\" -r release"
  },
  "packageManager": "pnpm@10.32.1",
  "engines": { "node": ">=24" }
}
面试怎么讲：三个点。① --filter "@hsa-ai/*" 用 scope 通配圈定「所有内部库」，examples 不会被误发布；② release:ui 显式写出依赖顺序（先构建 chat、chat-vue，ui 才能拿到它们的类型声明产物）—— 把拓扑约束固化成脚本，新人不用读文档也不会发错；③ packageManager 字段 + engines 锁定 pnpm 10.32.1 / Node ≥24， Corepack 会在执行时校验版本——「团队用同一个 pnpm」是 lockfile 一致性的前提。

7.3 peerDependencies + workspace devDependencies「双写」

这是库包型 monorepo 最核心的依赖模式，也是最常被追问的细节：

packages/ui/package.json（节选）
{
  "name": "@hsa-ai/ui",
  "version": "2.17.0",
  "peerDependencies": {
    "@hsa-ai/chat": ">=1.5.0",           // 声明给「下游消费者」：我需要这些邻居
    "@hsa-ai/chat-vue": ">=1.2.1",
    "vue": ">=3.5.0"
  },
  "devDependencies": {
    "@hsa-ai/chat": "workspace:*",       // 供「本仓库开发/构建/测试」：链接到本地源码
    "@hsa-ai/chat-vue": "workspace:*"
  }
}
面试怎么讲：同一个包写两遍，服务两个不同受众—— peerDependencies 是发布给下游的契约（「装我的人，请自备这些依赖」）， 范围写 >=1.5.0 这种普通语义版本；devDependencies 里的 workspace:* 是给本仓库用的：安装时链接到本地 chat 包，跑测试、起 VitePress 文档、做类型跳转全部指向源码。为什么不写进 dependencies？ 避免把 vue/内部库打进自己的产物——尤其 vue，重复打包会产生两个 Vue 实例，响应式直接失效。
对比：什么时候用 dependencies + workspace:*（运行时内部依赖）
// packages/portal-assistant/package.json
"dependencies": {
  "@hsa-ai/page-context": "workspace:*"   // 内部实现细节，随我一起发，下游无需感知
},
"peerDependencies": {
  "@hsa-ai/ui": ">=2.15.8"                // 由宿主提供的大件 → peer
},
"peerDependenciesMeta": {
  "@hsa-ai/chat": { "optional": true }    // 可选能力：不装也能用基础功能
}
面试怎么讲：判断准绳一句话——「这段代码必须由宿主提供（否则双实例/体积爆炸）→ peer；只是我的内部实现、跟着我发就行 → dependencies + workspace:*；有它功能更强但非必须 → peer + optional」。workspace:* 在 publish 时会被重写成真实版本，所以发布到内网 Nexus 后下游用普通 semver 就能装。

7.4 .npmrc：严格提升 + scope registry 分流

根 .npmrc（节选，令牌已脱敏）
shamefully-hoist=false          # 保持 pnpm 严格结构，主动拒绝幽灵依赖
strict-peer-dependencies=false  # peer 不匹配警告不阻断安装（渐进修复策略）

registry=https://registry.npmjs.org/          # 公网包走官方源
@vitest:registry=https://registry.npmjs.org/  # 部分 scope 强制回官方源

# 医保内网 scope 走公司 Nexus 私服
@ncp-web:registry=http://10.104.1.200/nexus/repository/hsa-neu-ui/
@hsa-ai:registry=http://10.104.1.200/nexus/repository/hsa-neu-ui/
//10.104.1.200/nexus/...:_authToken=<内网令牌·已脱敏>
面试怎么讲：.npmrc 是 pnpm 的「策略层」，三个实战点： ① shamefully-hoist=false 是显式宣言——pnpm 默认就严格，这里写出来是给团队看的 「我们不走回头路」；② 按 scope 分流 registry：公网包走 npmjs、内网组件库走公司 Nexus 私服，一个项目同时吃两套源；③ strict-peer-dependencies=false 体现取舍—— 存量包 peer 声明不规范时，先保证 install 可用，警告逐步收敛。补充一句安全意识： 带 token 的 .npmrc 绝不能出现在对外开源的仓库里。

7.5 tsconfig.base.json：编译约束的单一事实

根 tsconfig.base.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "isolatedModules": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
面试怎么讲：8 个包各自 "extends": "../../tsconfig.base.json"， 再叠加自己的 jsx/vue 差异项。declaration + declarationMap 让下游包拿到 .d.ts 还能「跳转到源码」——这正是 7.2 里「先构建 chat 才能发 ui」的原因：跨包类型解析依赖构建产物。monorepo 的价值在这里落地为 「规范定义一次、处处生效」。

7.6 构建门禁：测试不过，链路就断

packages/ui/package.json 的 scripts（节选）
{
  "build":   "pnpm test && vue-tsc --noEmit && vite build",
  "release": "pnpm build && changelogen --release --path . --push && pnpm pack",
  "typecheck": "vue-tsc --noEmit"
}
面试怎么讲：把质量门禁焊进脚本而不是留给 CI 文档： build 内部先跑 vitest，再类型检查，最后打包——任何一步失败， 根上 build:libs / release:* 的 filter 链就地中断， 坏产物出不了仓库。再配合 git hooks 跑 test:core， 形成「提交时 → 构建时 → 发布时」三道闸。

7.7 exports 子路径 + sideEffects：库包的出口设计

packages/ui/package.json（节选）
{
  "exports": {
    ".":          { "import": { "types": "./dist/index.d.ts",  "default": "./dist/index.js"  },
                    "require": { "types": "./dist/index.d.cts", "default": "./dist/index.cjs" } },
    "./blocks":   { "import": "./dist/blocks.js",  "require": "./dist/blocks.cjs" },
    "./charts":   { "import": "./dist/charts.js",  "require": "./dist/charts.cjs" },
    "./style.css": "./dist/style.css"
  },
  "sideEffects": ["**/*.css", "**/*.scss"],
  "files": ["dist", "README.md", "CHANGELOG.md"]
}
面试怎么讲：三点：① exports 是白名单式入口， 内部文件不再可被 deep import，重构目录不破坏下游；② ./charts 这类 子路径导出让下游按需引（不用整库全量进 bundle）；③ sideEffects 只豁免样式文件——JS 全部可 tree-shake，唯独 CSS 不是纯函数不能被删；④ files 白名单控制 tar 包体积，只发 dist。

八、方案对比：pnpm workspace / Lerna / Turborepo / Nx / Rush

先把问题拆成两层，面试回答会立刻清晰：包管理与链接（谁管 node_modules 和 workspace）是 pnpm/yarn/npm 的事； 任务编排与缓存（谁管构建图、跑得快不快）是 lerna/turbo/nx 的事。两层可自由组合。

方案 定位 强项 短板 / 代价 一句话画像
pnpm workspace 包管理器内置 workspace + 基础编排 安装快且严格；filter/拓扑序开箱即用；单 lockfile 无任务缓存；跨包增量要自己设计或接 turbo 「地基级标配」——几乎所有现代 monorepo 的底座
Lerna 早期 monorepo 事实标准（发版/变更管理） 独立版本策略、changelog、publish 流程成熟 维护几近停摆后由 Nx 团队接手；任务执行已交棒 Nx runner 「上一代王者」——现在多作为发版工具被提起
Turborepo 专注构建缓存的任务运行器 内容哈希缓存（本地 + Remote Cache）；配置极简 turbo.json；与 pnpm 是官配 不做深度代码图分析，affected 粒度较粗 「给 pnpm 插上缓存翅膀」——中小团队性价比之选
Nx 全功能 monorepo 平台（项目图 + 任务图） 精确 affected 计算、插件生态（vite/angular/react）、 generators、IDE 集成 学习曲线陡、概念多、侵入性强，小项目杀鸡用牛刀 「企业级全家桶」——大仓治理的重型武器
Rush Microsoft 的企业级方案 多包管理器支持、变更集（change file）流程、极稳 配置繁琐、社区小、上手成本高 「大厂基建风」——强调流程与合规而非开发体验
选型答题模板 「新起一个库群 monorepo：pnpm workspace 起步；构建一慢、需要「没改就复用」→ 加 Turborepo（成本最低）；当出现跨包影响面精确计算、代码生成器、多团队插件规范等 组织级诉求 → 迁 Nx；存量老仓要走严格的变更审批/多包管理器 → 看 Rush。 本项目是 8 个纯 TS 库 + 单 lockfile + 内网发布，pnpm 自带的 filter 与脚本门禁已够用， 暂未引入 turbo——引入的触发条件是「CI 全量构建超过可接受阈值且重复构建占比高」。」

九、构建缓存与增量：把「全量」变成「只跑改动的链」

9.1 三层增量策略（从便宜到昂贵）

层 手段 粒度 成本
L1 · 变更圈定 pnpm --filter ...[origin/main] / turbo --filter=...[origin/main] 受影响的包 零成本，pnpm 原生
L2 · 任务缓存 turbo 的本地缓存：输入（源码 hash + 依赖包 hash + 环境变量）没变 → 直接回放上次输出 「包 × 任务」 引入 turbo.json 配置
L3 · 远程缓存 turbo Remote Cache / Nx Cloud：团队共享同一份产物，同事跑过的构建你直接下载 跨机器 需要服务端（Vercel/Nx Cloud 或自建）
turbo.json 的心智模型（与 pnpm filter 配合）
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],            // 拓扑：先构建我依赖的包（= pnpm -r 的顺序）
      "outputs": ["dist/**"],             // 哪些文件算「产物」→ 可被缓存回放
      "env": ["NODE_ENV"]                 // 参与缓存 key 的环境变量
    },
    "test": { "dependsOn": ["build"], "outputs": [] }
  }
}
缓存正确性的本质 任务缓存 = 「输入指纹没变 ⇒ 输出必然相同 ⇒ 直接复用」。所以配置里必须诚实回答两个问题： ① 这个任务的输入包含什么（源码、依赖包版本、环境变量、工具版本）；② 输出在哪个目录（dist/**）。 漏报输入 → 缓存脏数据（最难查的 bug）；漏报输出 → 缓存永远 miss（白配）。
一个必须知道的耦合点 本项目 7.5 说过：跨包解析依赖 .d.ts 产物。这意味着「只构建改动的包」的前提是 依赖包的 dist 存在——冷 CI 上必须先全量构建一次（或用缓存回放），否则 filter 增量构建会报 「找不到类型」。--filter ...[ref] 圈出的是「要重跑的」，不是「要存在的」。

十、版本与发布：独立版本、顺序与门禁

10.1 两种版本策略

独立版本（Independent）· 我项目采用

  • 每个包自己的版本号：@hsa-ai/ui 2.17.0、@hsa-ai/chat 1.5.0、@hsa-ai/chat-vue 1.2.1。
  • 只改了 ui → 只发 ui，语义诚实，下游按需升级。
  • 代价：发布顺序要自己保证（依赖先发），变更说明按包各写各的。
  • 工具：changelogen（本项目）、changesets、lerna publish。

锁步版本（Lockstep）

  • 所有包永远同一版本号，任一变更全体 +1。
  • 优点：不存在版本矩阵，永远只有「一套」组合，兼容性问题最少。
  • 代价：改一行也全量发版，通知噪音大。
  • 代表：babel、vue 生态部分包、rush version policies。

10.2 发布流水线（我项目的实际形态）

每包独立发布：build → changelog → 打 tar 包
# packages/*/package.json 中的 release 脚本
pnpm build && changelogen --release --path . --push && pnpm pack
#      │              │                        │
#      │              │                        └─ 产出 tgz，上传内网 Nexus
#      │              └─ 生成 CHANGELOG + 提交版本号 + push
#      └─ 测试门禁 + 类型检查 + 打包（失败即终止，坏产物不入库）

# 根目录按依赖顺序发布 ui（先备齐 chat / chat-vue）
pnpm release:ui
面试怎么讲：发布三问——发什么（files 白名单决定 tar 包内容）、 按什么顺序发（依赖先发；脚本里显式写 chat → chat-vue → ui， 或用 pnpm -r publish 的拓扑序）、怎么知道发了什么 （changelogen 按 conventional commits 生成每包独立 CHANGELOG）。 pnpm pack 本地解包可验证 workspace:* 已被重写、exports 路径正确—— 发前验证 tar 包是很多候选人漏掉的一步。
经典翻车题：workspace 协议泄漏 若发布时忘记用 pnpm publish（比如手抖用 npm publish），workspace:* 不会被重写，下游安装直接报错 Unsupported URL Type "workspace:"。 pnpm 的重写行为是 pnpm publish/pack 的能力，不是 npm 的——工具链必须统一，这正是 packageManager 字段存在的意义。

十一、踩坑清单：这些坑我踩过 / 见过

坑 1「Cannot find module」其实是没声明依赖
pnpm 下报缺模块，先怀疑幽灵依赖暴露（这是好事），用 pnpm why xxx 查链路，显式 pnpm add 补声明——别急着开 shamefully-hoist。
坑 2Windows 上符号链接权限问题
旧版 Windows/未开开发者模式时 symlink 创建失败，pnpm 会退化为 junction/复制。 解决：开「开发者模式」或管理员权限；企业环境可用 node-linker=hoisted 兜底。
坑 3跨包引用指向 dist，忘了先构建
本地改了 chat 源码，ui 却一直跑旧逻辑——因为链接解析到的是 chat 的 dist。要么 dev 模式 watch 构建，要么配 TS 项目引用/源码出口。
坑 4lockfile 冲突与「幽灵 diff」
多人同改依赖时 pnpm-lock.yaml 冲突频发。铁律：别手改 lockfile，改完 package.json 重新 pnpm install 让它整体再生成；CI 用 pnpm install --frozen-lockfile 强制校验。
坑 5peerDependencies 警告风暴
monorepo 里 peer 范围写太严（精确到 x.y.z）会互相打架。库的 peer 用 >=x.y.0 <major 宽松区间；存量包不规范时用 strict-peer-dependencies=false 先保安装，再逐步修。
坑 6同一依赖多版本共存导致「双 vue」
某包锁了 vue@3.4、根上是 3.5 → 两份 vue，prop/响应式不互通。 用根级 overrides / catalog 强制统一，或收紧 peer 范围。
坑 7CI 装依赖慢 / 每次全量下载
没缓存 store 等于自废武功。CI 上缓存 ~/.local/share/pnpm/store（或 pnpm store path 的实际路径）+ node_modules/.vite 等， 安装时间可降一个量级。
坑 8pnpm 10：依赖的 install 脚本被静默拦截
esbuild/protobuf 等带安装脚本的包可能「装上了却不工作」。显式 onlyBuiltDependencies 白名单或 pnpm approve-builds； 升级 pnpm 大版本后先检查这类行为变更。
坑 9filter glob 要加引号
pnpm --filter "@hsa-ai/*" 不加引号会被 shell 自己展开（bash 尤甚）， 结果变成传了一堆路径给 pnpm。养成一律加引号的肌肉记忆。
坑 10把 token 提交进 .npmrc
内网私服需要 authToken 是常态，但仓库一旦外发即泄漏。提交前扫描 _authToken，用 CI 环境变量/本地私有 .npmrc 注入，对外仓库走 .npmrc.example 模板。

十二、面试追问链：把这题聊到加分

Q1 · pnpm 为什么快、为什么省磁盘？（必考）

答：因为不复制。包内容按内容 hash 存进全局 store，同内容全局一份；项目里的 .pnpm 虚拟存储用硬链接指向 store（同一 inode，零字节拷贝）， 顶层 node_modules 再用符号链接指进去。命中缓存的包只是建两个链接 + 写元数据， 所以重复安装接近秒级，磁盘占用也从「每仓一份」变成「全局一份」。

追问预判：硬链接和符号链接的区别？→ 硬链接是同一份数据的另一个名字（两个目录项指同一 inode，删一个不影响另一个）；符号链接是路径的指针（指向没了就成死链）。

Q2 · 什么是幽灵依赖？pnpm 为什么天然没有？

答：import 了 package.json 没声明、却因 hoisting 提升到顶层而能跑的包。pnpm 不提升——顶层只有声明过的包，其余全在 .pnpm 虚拟存储里按各自的依赖链解析，所以「没声明 = 不可见 = 直接报错」，package.json 恢复为唯一事实。代价是个别不规范包要显式补声明，或临时开 shamefully-hoist。

Q3 · workspace:* 发布后变成什么？谁做的？

答：pnpm publish / pnpm pack 时自动把 workspace:* 重写成真实版本（如 2.17.0），再打 tar 包，所以 npm/私服消费者看到的是普通 semver。这个重写是 pnpm 的能力——如果误用 npm publish，workspace 协议会原样带出去导致下游安装失败。可以解包验证。

Q4 · peerDependencies 是干嘛的？为什么你的项目里 peer 和 dev 双写？

答：peer 是「宿主提供」的契约——声明我运行时需要、但不该由我打包的依赖（典型是 vue：双实例会炸）。双写的两行服务两个受众：peer 的 >=1.5.0 发布给下游看；dev 的 workspace:* 让本仓库开发/测试/类型解析链接到本地源码包。不写进 dependencies 是为了不把内部库/框架打进产物。

追问预判：devDependencies 的 workspace:* 发布后呢？→ pnpm 一样会重写，且 devDeps 本来就不被下游安装，无影响。

Q5 · pnpm -r build 是按什么顺序执行的？和 --parallel 什么关系？

答：默认按依赖图拓扑序——被依赖者先跑，保证下游构建时上游 dist 已就绪；同层无依赖关系的包可并行。加 --parallel 则忽略顺序全并行（快但可能踩到未就绪产物）；--no-bail 控制失败是否继续；pnpm 只管顺序与范围，不管缓存——缓存是 turbo/nx 的活。

Q6 · --filter ...pkg 和 pkg... 有什么区别？

答：...pkg（省略号在前）= pkg 加上它的所有依赖（上游链），用于「发布/构建前把地基备齐」；pkg...（省略号在后）= pkg 加上所有依赖它的包（下游链），用于「改了核心库之后圈定回归测试范围」。再加 [origin/main] 可与 git 变更求交集，实现 affected。

Q7 · monorepo 怎么做增量构建？

答三层：① filter + git ref 圈出受影响的包（pnpm 原生，零成本）；② Turborepo 内容哈希任务缓存——输入没变直接回放 dist（要诚实声明 inputs/outputs/dependsOn）；③ 远程缓存让团队共享产物。另有一个冷启动前提：跨包类型依赖 dist，CI 首次必须全量或从缓存恢复，否则增量构建报找不到类型。

Q8 · 独立版本怎么保证发布顺序？

答：依赖先发。手段从轻到重：① 脚本里显式写顺序（我项目 release:ui 先 build chat/chat-vue）；② pnpm -r publish 按拓扑序自动发；③ changesets/Rush 的变更集流程统一管理「这一轮发谁、发什么版本」。发前用 pnpm pack 验产物，发后按 scope 是否存在来判断是否需要 registry 同步等待。

Q9 · pnpm 和 Lerna / Turborepo / Nx 是什么关系？

答：正交——pnpm 解决「装与连」（包管理 + workspace + 基础 filter），turbo/nx 解决「跑与缓」（任务图、增量、缓存），lerna 传统上解决「发与记」（版本与 changelog，现由 Nx 维护）。选型递进：pnpm 起步 → 慢了加 turbo → 组织级图治理上 nx。我项目 8 个包用 pnpm filter + 脚本门禁已够，引入 turbo 的触发条件是 CI 重复全量构建占比高。

Q10 · shamefully-hoist 什么时候该开？node_modules/.pnpm 是什么？

答：.pnpm 是虚拟存储——所有包的真实目录、按「包名@版本」组织，内部互相解析依赖，是 pnpm 严格结构的实现载体。shamefully-hoist=true 会把依赖提升到顶层模拟 npm，仅建议在「工具链不兼容严格结构」的迁移期临时使用（如某些 Electron/老 Vite 插件场景），开久了等于放弃 pnpm 的核心收益；我项目显式设为 false。

Q11 · 你的 monorepo 怎么保证代码质量不随包数失控？

答：配置单源 + 门禁前移。根上一份 eslint/prettier/tsconfig.base 全包 extends（规范定义一次）；每个包 build = test && typecheck && build，根脚本 filter 链自动继承这道闸；git hook 跑 test:core 兜底；CI 用 --frozen-lockfile 锁依赖、按 affected 只跑改动链。质量不靠自觉，靠流水线里焊死的断点。

十三、一页速记卡（进面试间前扫一遍）

  1. 三句话定调：pnpm 管「装」（store + 硬链接 + 符号链接 = 快省严格）；workspace 管「连」（yaml 划范围，workspace: 本地链接/发布重写）；monorepo 管「管」（原子变更 + 统一工具链，代价是编排与治理）。
  2. 结构图在脑中：顶层 node_modules（只有声明的）→ .pnpm 虚拟存储（全版本）→ 全局 store（内容 hash）；实线硬链接、虚线符号链接。
  3. 幽灵依赖 = 声明与可见集不一致；pnpm 靠不提升根治；逃生开关 shamefully-hoist / node-linker=hoisted，慎开。
  4. 双写模式：peer（给下游的契约，宽范围）+ dev workspace:*（给本地的链接）；内部小依赖才进 dependencies + workspace:*；publish 自动重写 workspace:。
  5. 编排口诀：省略号在前建地基（...pkg），省略号在后排影响（pkg...），-r 拓扑序，--parallel 换速度，[ref] 圈变更。
  6. 缓存三板斧：filter 圈范围 → turbo 本地缓存回放 → 远程缓存共享；缓存正确性 = 输入指纹诚实（源码+依赖+环境变量，输出 dist/**）。
  7. 发布三问：发什么（files/exports 白名单）、什么顺序（依赖先发/脚本写死/拓扑发布）、怎么记录（changelogen/changesets 独立 CHANGELOG）；发前 pnpm pack 验包。
  8. 本项目数字包：pnpm 10.32.1 · Node ≥24 · 8 包 + 1 示例 · 独立版本（ui 2.17 / chat 1.5 / chat-vue 1.2）· scope registry 分流内网 Nexus · build = test && typecheck && 打包。
  9. 选型一句话：pnpm workspace 起步 → 慢了加 Turborepo → 组织级图治理上 Nx；Lerna 是上一代发版标准，Rush 是企业流程派。
