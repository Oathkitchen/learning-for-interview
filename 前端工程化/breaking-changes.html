如何处理破坏性升级

什么算破坏性 · 预防优先 · Semver 与版本策略 · 弃用三件套 · 迁移工程 · 放量与回滚 · Monorepo 特有场景 · 追问链（面试向 · 图解版）

〇、30 秒电梯答案

破坏性升级（breaking change）处理得好不好，检验的是「契约意识」。我把它收成一句话： 能不破坏就不破坏；要破坏就先预告、给迁移路径、留回滚口子——把「升级成本」转嫁给发布方，而不是甩给使用方。

具体五步：① 预防——设计上加而不删、默认行为不变、适配器吸收差异； ② 定级——Semver 说清楚什么算 major，宁可保守；③ 预告—— @deprecated + 运行时告警 + 明确移除期限（弃用三件套）； ④ 迁移——迁移指南 + codemod + 兼容开关/双轨期，让升级变成「照着清单改」； ⑤ 放量——beta/canary 通道 + 分阶段 + 回滚预案。 我维护的组件库 monorepo 用独立版本 + peerDependencies 范围 + changelogen 管理这套流程——major 是承诺，不是随手 +1。

🛡 预防：加而不删

新 API 走新增、旧 API 走适配——能用 minor 解决的别动 major。

📣 预告：弃用三件套

文档 @deprecated、运行时 warn、写明移除版本——给用户一个可预期的时钟。

🗺 迁移：路径要平

迁移指南 + codemod + 兼容开关——升级成本由发布方承担到最后一公里。

🔁 放量：可回滚

beta → 试点应用 → 全量；旧 major 维持 LTS 一段时间，回滚有路可走。

一、什么算破坏性升级：先把边界画清楚

判断标准一句话：使用方「不做任何修改」地升级后，代码编译不过、跑不对、或行为悄悄变了—— 这就是破坏性变更。不只是「删了 API」才算，下面这些全是：

类别 例子 隐蔽程度
API 删除/改名 createChat() 改名 createChatClient()；参数顺序对调 低（编译/运行直接报错，好发现）
类型收紧 可选参数变必填；string 收成字面量联合；返回值从 any 变严格类型 中（TS 项目立刻红，JS 项目可能潜伏）
默认行为改变 默认开启自动重试、默认序列化格式变了、CSS 默认主题换了 高（不报错，结果悄悄不对）
事件/数据格式变 SSE 协议字段改名、时间单位 ms→s、错误码体系重排 高（协议层一变，下游全连坐）
Peer 依赖抬升 vue: >=3.2 抬到 >=3.5；react 17→18 中（安装时告警，运行时才炸）
运行时/工具链抬升 Node 16→20、ESM-only（删 CJS 出口）、浏览器基线提高 中（CI/构建期暴露）
副作用与全局状态 注册的全局指令名变了、样式污染范围变了、单例行为变了 高（难排查，见怪不怪）
宁可保守 判不准时默认按破坏性处理（major）。把 minor 当 major 发，用户只是多升了个号； 把 major 当 minor 发，用户会在半夜被叫起来——不对称的代价决定了一边倒的策略。

二、第一原则：能不破坏就不破坏

最便宜的 breaking change 是根本没有的那个。设计期的四条兼容纪律：

2.1 加而不删：扩展点用「新增」表达

反例 vs 正例
// ❌ 破坏性：改函数签名——所有调用点全红
function createChat(options) { /* 旧：options.url */ }

// ✅ 兼容性扩展：新能力走新字段，旧字段继续有效
function createChat(options) {
  // options.url     ← 继续支持（旧）
  // options.endpoint ← 新增别名，内部归一化
  // options.transport ← 全新能力，可选
}

// 删除路径永远是「标记弃用 → 双轨 → 下个 major 才移除」

2.2 默认行为不动：新行为默认关

  • 自动重试、新序列化格式、新渲染策略——默认值是 API 的一部分，改默认 = 破坏。
  • 正确姿势：新行为做成 opt-in（nextBehavior: true）→ 观察采用率 → 下个 major 再翻转默认。
  • 反例：「优化后默认开启缓存」——无数依赖旧时序的用户凌晨炸群。

2.3 适配器吸收差异：让破坏止步于内部

依赖的第三方大版本要升（比如 vue、echarts 大版本），别把「上游的 breaking」转赠给你的用户—— 在你的边界内用适配层消化：对外 API 不变，内部按版本走不同实现。 这正是我 monorepo 里「peerDependencies 声明宽范围 + 内部做兼容」的思路来源。

2.4 导出纪律与「一次性说清」

  • exports 白名单出口（见 CLI/monorepo 页）：内部文件不被 deep import，重构自由度大增—— 减少无意中被依赖的表面积，就是在减少未来不得不 break 的次数。
  • 公共类型显式导出、内部实现不导出：用户能 import 到什么，由你控制。
一句话 「破坏性变更的数量是设计指标——一个 API 稳定的库，major 版本号会自然长得慢； major 频发说明当初暴露了太多本该内部的东西。」

三、Semver 与版本策略：major 是承诺

SemVer（语义化版本）主版本.次版本.修订号 是破坏性升级的社会契约—— 用户看到什么号，就预期什么级别的痛苦。

号位 含义 允许的变更 用户的预期
patch x.y.Z 修 bug 不改 API、不改行为（除非修的就是 bug 行为） 闭眼升
minor x.Y.z 加功能 新增 API、新增可选参数、弃用旧 API（只标不删） 放心升，看一眼 changelog
major X.y.z 破坏性变更 删/改 API、改默认行为、抬 peer/Node 基线 读迁移指南再升

3.1 两个必须知道的细节

  • 0.x 阶段：0.y.z 里 minor 也可以破坏（Semver 允许），所以 0.x 要当「还在定契约」理解—— 从 1.0.0 开始才是正式承诺。内部库起步可以 0.x 快速迭代，对齐后再 1.0。
  • 弃用算什么号：@deprecated 标记是 minor（加了信息、没删能力）； 真正移除才是 major。很多人把「弃用」和「移除」一次做完——那是给自己挖坑。

3.2 版本策略：独立 vs 锁步（与 monorepo 页呼应）

独立版本（我的组件库）

  • ui 2.x、chat 1.x、chat-vue 1.x 各自演进——只破坏了 ui 就只发 ui 的 major。
  • 配合 peerDependencies 范围（@hsa-ai/chat: >=1.5.0）表达兼容窗口。
  • 代价：发布顺序要编排（依赖先发），版本矩阵要想清楚。

锁步版本

  • 全家一个版本号，任一破坏全体 major——语义简单，但「没破坏的包」也跟着跳大版本。
  • 适合强耦合套件（babel 早期、某些设计系统全家桶）。
  • 破坏性升级的「通知噪音」大：用户升级等于全量升级。
peerDependencies 范围就是「兼容承诺」的机器表达
// packages/ui/package.json —— 发布给下游的契约
"peerDependencies": {
  "@hsa-ai/chat": ">=1.5.0",      // chat 的 1.x 全系兼容；2.0 出现时这里才会改
  "@hsa-ai/chat-vue": ">=1.2.1",
  "vue": ">=3.5.0"
}
// 抬升 peer 下限 = 破坏性信号：要么跟着 major 发，
// 要么在 minor 里维持宽范围、内部做兼容（推荐后者能做就做）
面试怎么讲：peer 范围不是随便写的——它是经过测试的兼容矩阵的压缩表达。 我们 chat 1.x 任何版本 + ui 都要能跑，所以 ui 的 peer 写 >=1.5.0； 如果哪天 chat 2.0 不兼容了，正确动作是：先在 chat 2.0 里做适配争取还是兼容（消 major）， 实在不行才在 ui 的 major 里抬 peer。抬 peer 下限和删 API 一样是破坏性变更。

四、弃用三件套与预告节奏：给用户一个时钟

弃用（deprecation）不是「提醒一下」，而是启动一个可预期的倒计时。三件套缺一不可：

件套 做什么 受众
① 文档标记 @deprecated JSDoc + CHANGELOG 写明「替代方案」和「移除版本」 写代码的人 / IDE（删除线提示）
② 运行时告警 调用时 console.warn('[deprecated] use X instead, will be removed in v3')；一次性去重避免刷屏 跑代码的环境 / 真实用户路径
③ 明确期限 「将在 3.0 移除」——期限要可执行，并在 roadmap 里兑现 排期决策者
标准写法
/**
 * @deprecated 自 v2.3.0 起弃用，将在 v3.0.0 移除。
 * 请改用 createChatClient()——支持重试与传输层注入。
 */
export function createChat(url) {
  warnOnce(
    '[deprecated] createChat(url) 将在 v3 移除，请使用 createChatClient({ endpoint })'
  )
  return createChatClient({ endpoint: url })   // 双轨：旧入口转调新实现
}

4.1 预告节奏（沟通也是工程）

  • 提前一个「能被听到的周期」：内部库至少一个 minor 周期；多团队/对外库对齐 major 周期或 3–6 个月。
  • 多通道同步：CHANGELOG（事实来源）→ 团队周会/群公告（人）→ README 迁移章节（常驻）→ Issue/RFC（讨论）。
  • 在旧版本里预告：别只在新版本的 README 写「我们要破坏了」——要在大家还在用的版本里加告警， 否则等于没通知。
反模式：突然死亡 「昨天还好好的，今天升级 minor 全挂」——这会永久消耗信任。信任是升级生态的通货： 一次突然死亡，之后你的 major 都会被「再观望一个版本」。

五、迁移工程：把升级做成「照着清单改」

破坏性升级的良心程度 = 迁移文档 + 自动化程度。按成本从低到高三档：

5.1 迁移指南（最低配置）

  • 变更清单表：旧写法 → 新写法 → 为什么，一表打尽；能搜到关键词（旧 API 名）。
  • 给 Codemod 留好锚点：改动如果是机械的（改名、参数形状），就值得写 codemod。
  • 常见报错对照：「看到 XXX 错误 = 需要改 YYY」——排障路径也进文档。

5.2 Codemod / 自动迁移（推荐配置）

jscodeshift / ts-morph 类工具的标准姿势
# 发布迁移工具包（版本跟着 major 走）
npx @hsa-ai/migrate@3 --from 2 --to 3
# 做的事：
# 1. 扫描源码里的旧 API 调用（createChat( → createChatClient({ endpoint: … })
# 2. 自动改写能确定的，标记需要人工判断的（// TODO(migrate-3)）
# 3. 输出迁移报告：改了多少处、剩多少处、每处指向指南哪一节
codemod 的价值公式 调用点 × 改动复杂度 > 写 codemod 的成本，就写。组件库、工具库这种「被 import 处数很多」的包， codemod 几乎总是划算的——它把「100 个业务方各自改」变成「发布方写一个脚本」。

5.3 兼容开关与双轨期（大版本专用）

  • 双轨实现：新旧 API 同时存在，旧的内部转调新的（见 4 的代码），成本是发布方的，收益是使用方的平滑。
  • 行为开关：legacyMode: true 保留旧行为，让使用方在同一个 major 内先升包、后改行为—— 「升级」与「迁移」解耦成两步。
  • 出口期：移除的 major 发布前，旧入口至少经历「告警 → 告警+文档 → 移除」三个可见状态。
面试怎么讲：迁移工程我按「三档配置」讲：指南是底线、codemod 是标准、 双轨+开关是大版本的豪华配置。判断标准是使用方的修改点数量： 机械改动多就 codemod，行为差异大就双轨/开关。发布方多写一小时，使用方少花一天——这笔账永远划算。

六、放量与回滚：别在发布日当赌徒

破坏性版本上线不是「发完就完」，而是一次受控放量：

阶段 动作 通过标准
beta / canary 3.0.0-beta.1 发 npm dist-tag，内部试点项目先升 试点项目编译/测试/E2E 全绿，迁移文档被验证过一遍
试点推广 挑 1–2 个真实业务升级，收集「指南没写到的坑」 剩余问题都进 FAQ；codemod 覆盖不了的点被记录
正式发布 latest tag 切到 3.x；公告 + 迁移指南置顶 旧 major 被标记为维护态（LTS）
拖尾维护 旧 major 只修严重 bug / 安全问题，设定 EOL 日期 EOL 到期后归档——同样是「说好的期限」

6.1 回滚预案（发布前就要有）

  • 包层面：npm 版本不可删但可打 tag 回退（npm dist-tag add pkg@2.x latest）； 使用方 lockfile 回锁旧版即可——所以不要在 major 里搞不可逆的数据迁移。
  • 业务层面：升级 PR 保持可 revert；配置开关（feature flag）让新旧实现能切。
  • 数据/协议层面：序列化格式要写版本号、双读双写一段时间——这是最贵的破坏面，回滚成本最高。
不可逆变更单独审批 数据库字段改名、存储格式升级、协议字段切换——这些的「回滚」是灾难级的。 处理原则：双写双读过渡期 + 迁移脚本可逆 + 灰度窗口拉长，宁可过渡期丑陋，不要回滚无门。

七、Monorepo 特有场景：包之间怎么「一起破坏」

7.1 跨包破坏：协调发布

  • 先发被依赖方：chat 先发 2.0，ui 再发「兼容 chat 2.0」的版本——顺序反了会出现 「ui 新版要求 chat 2.0 但 registry 还没有」的窗口。
  • workspace:* 的发布重写：本地互链用 workspace:*，publish 时自动替换成真实版本—— 版本矩阵由发布工具保证，不靠手抄。
  • 一次破坏尽量打包成「一个 major 窗口」：别 chat 1 月破一次、ui 2 月破一次、5 月又来一次—— 用户的迁移预算会被打穿。

7.2 peer 抬升的两种姿势

姿势 做法 什么时候用
软抬（推荐） peer 保持宽范围 >=1.5.0，内部做 1.x/2.x 双兼容（适配器） 差异可吸收时——用户零感知，这是首选
硬抬 peer 下限抬到 >=2.0.0，随自己的 major 发布 上游破坏无法兼容（类型体系、运行时不兼容）

7.3 Lockfile 与依赖树层面的破坏

  • overrides / catalog 强制统一版本时，等于全仓一次升级——要当 major 对待（跑全量测试）。
  • pnpm 严格结构下 peer 不匹配会更早暴露（告警/报错），这是好事：把破坏提前到安装期，好过运行时炸。
  • monorepo 内部的破坏可以「原子提交」一次性改完所有调用方——这正是 monorepo 处理 breaking 的天然优势： 破坏性变更可以与全量适配同一个 commit 落地。

八、真实实践解剖：我的组件库怎么管破坏面

环节 我的做法 对应的原则
版本 独立版本（ui 2.x / chat 1.x / chat-vue 1.x）+ Conventional Commits 自动 bump 破坏面隔离：只破谁就只动谁的 major
兼容承诺 peerDependencies 宽范围（@hsa-ai/chat >=1.5.0）+ devDep workspace 本地双写 peer 范围 = 测试过的兼容矩阵
破坏面收敛 exports 白名单 + 内部实现不导出 + index 只 re-export 少暴露 = 未来少破坏
变更记录 changelogen 按包生成 CHANGELOG，breaking 必须在提交信息里声明（feat!: / BREAKING CHANGE:） 预告与事实来源
质量门禁 build = test && typecheck && build；pre-commit 拦 test:core——接口变更测试全红才允许发 测试是契约的守卫
发布顺序 release:ui 先构建 chat、chat-vue；依赖链写进根脚本 协调发布、消灭「窗口期」
用提交约定把破坏性升级「显式化」
feat: 新增 createChatClient 传输层注入        → minor
fix: 修复 [DONE] 哨兵在空流下的解析          → patch
feat!: createChat 改名为 createChatClient    → major（! 标记）
  BREAKING CHANGE: createChat() 移除，请运行 codemod 或按 MIGRATION.md 修改

# changelogen 会把 BREAKING CHANGE 段落提取进 CHANGELOG 的 Breaking 小节
# 用户扫一眼就知道：这个版本要不要读迁移指南
面试怎么讲：我们把「破坏性」做成可机读的显式信号： 提交信息的 ! 与 BREAKING CHANGE 段落 → changelogen 进 CHANGELOG → 用户在升级前一定看得到。再叠测试门禁——接口一改，契约测试红了就发不出去。 破坏性升级不是一次技术决策，是一条「信号 → 预告 → 迁移 → 放量」的流水线。

九、面试追问链

Q1 · 什么是破坏性变更？你怎么判断该不该发 major？

答：使用方不改代码升级后编译不过、跑不对、或行为悄悄变了——就是破坏。 具体包括：删/改 API、类型收紧、默认行为改变、协议字段变化、peer/Node 基线抬升、副作用变化。 判不准时默认按破坏性处理（major）——把 major 发成 minor 的代价是半夜事故，反过来只是版本号保守。

Q2 · 如何降低破坏性升级对用户的影响？

答：五步。① 设计期能不破坏就不破坏（加而不删、默认不变、适配器吸收上游差异）； ② Semver 定级诚实；③ 弃用三件套（@deprecated、运行时 warn、明确移除版本）给用户时钟； ④ 迁移工程（指南、codemod、双轨/兼容开关）让用户照清单改；⑤ beta 试点放量 + 旧 major 留 LTS + 可回滚。 核心是把升级成本从使用方转到发布方。

Q3 · 弃用（deprecation）和移除（removal）有什么区别？

答：弃用是 minor——能力还在，只是打了 @deprecated、加了运行时告警、写了移除计划； 移除是 major——能力没了。两者必须分开，中间隔着迁移期。 一次做完「弃用+移除」等于没给用户时间窗，是突然死亡式变更。

Q4 · 大版本升级你们怎么做迁移支持？

答：三档配置。底线是迁移指南（旧→新对照表 + 常见报错 FAQ）； 标准配置加 codemod——机械改写调用点，输出迁移报告； 大版本豪华配置是双轨实现 + 行为开关，让「升包」和「改行为」分两步走。 我们还把 BREAKING CHANGE 写进提交约定，changelogen 自动汇总进 CHANGELOG 的 Breaking 小节。

Q5 · 组件库的 peer 依赖要不要跟着大版本抬升？

答：能软抬不硬抬。peer 范围是「测试过的兼容矩阵」：如果上游 2.0 的破坏能被适配器吸收， 我们保持 peer 宽范围、内部双兼容——用户零感知；实在吸收不了才在自己的 major 里抬 peer 下限。 抬 peer 和删 API 同级，都是破坏性变更，要走同一套预告+迁移流程。

Q6 · 升级出了问题怎么回滚？

答：分层回滚。包层面：npm dist-tag 把 latest 拨回旧版，用户 lockfile 回锁； 业务层面：升级 PR 保持可 revert、新旧实现走 feature flag； 数据/协议层面最贵：双写双读过渡、迁移脚本可逆、灰度拉长——这类不可逆变更发布前要单独评审。 发布前就写好回滚预案，是 major 发布的准入条件。

十、一页速记卡

  1. 一句话：能不破坏就不破坏；要破坏就预告、给迁移路径、留回滚——成本转嫁发布方。
  2. 什么算破坏：删改 API、类型收紧、默认行为变、协议字段变、peer/Node 抬升；判不准当 major。
  3. 预防四纪律：加而不删、默认行为不动（新能力 opt-in）、适配器吸收上游差异、exports 白名单少暴露。
  4. Semver：patch 闭眼升 / minor 看 changelog / major 读指南；@deprecated 是 minor，移除才是 major；0.x 无承诺。
  5. 弃用三件套：@deprecated 文档 + 运行时 warn（去重）+ 明确移除版本；在旧版本里告警才算通知。
  6. 迁移三档：指南（底线）→ codemod（机械改动划算）→ 双轨/兼容开关（大版本）。
  7. 放量：beta → 试点 → latest → 旧 major 留 LTS/EOL 日期；回滚预案是发布准入条件。
  8. Monorepo：跨包破坏一次 major 窗口打包；先发依赖方；workspace:* publish 重写；能原子提交就原子提交。
  9. 真实工程：独立版本 + peer 宽范围 + Conventional Commits（feat!/BREAKING CHANGE）+ changelogen + 测试门禁拦接口变更。
  10. 金句：「major 版本号是承诺不是数字；破坏性变更是设计指标——major 越频，当初暴露的越多。」
收尾金句 「破坏性升级的最高境界，是用户升完之后只觉得『好像什么都没发生』—— 你多写的适配层、迁移脚本和告警，就是替他们消化掉的那些地震。」
