〇、总览：组件库 = 组件 + 工程 + 治理

写好一个组件和做好一个组件库是两件事。组件库的难点 80% 在工程与治理：目录结构、构建产物、依赖策略、主题体系、 版本发布、文档与门禁。完整链路是一条流水线：

实战复盘 两条路线都走过：基于 Element Plus 脚手架封装内部库，赢在「站在 Element 肩膀上快速交付」；而自建 monorepo（如 @hsa-ai/ui）时， 把「流式协议核心 → Vue 适配层 → UI 组件层」拆成三个包， 让不含 UI 的能力也能被复用——这是单包组件库给不了的。 选型依据：组件库是否要沉淀「与渲染无关的核心逻辑」。

一、架构设计：把「核心逻辑」和「UI」拆开

组件库最常见的腐化：所有逻辑都堆在 .vue 文件里， 换个渲染端（小程序、Web Component、SSR）全部重写。 解法是分层：协议/核心层零 UI 依赖，适配层消化框架差异， UI 层只做渲染与交互。

核心层不认识 Vue 纯 TS 实现（SSE 解析、协议状态机），输出 AsyncIterable 这种框架无关接口， 换 React 只需重写适配层。
适配层薄而稳定 useChat() 只做「协议事件 → 响应式状态」的翻译， 输出 Ref + 动作函数，UI 层与业务层都只依赖这层 API。
依赖方向单向 ui → chat-vue → chat，禁止反向、禁止跨层； 两个核心包（chat ↔ data-query）零依赖，各自独立演进。
外部能力靠注入 库内禁止引入 axios 等运行时 HTTP 依赖， 请求层抽象成 Fetcher 适配器接口，由消费方注入实现。
WARNING · 内部库的隐性需求：宿主环境 公司内部组件库往往跑在受控宿主里（都有 Element Plus、都有统一 token）。这既是优势（可以用 peerDependencies 锁定宿主能力）， 也是风险（宿主升级 = 全公司回归）。所以 Element 系内部库要： peer 范围写区间（如 >=2.13.0 <3）， 并在 CI 里对 Element 高版本做冒烟构建。

二、组件 API 设计：库组件和业务组件的区别

库组件的第一原则：可预测、可扩展、可逃生。 API 一旦发布就是契约，改 props 名称就是破坏性变更。 设计 checklist：

  • 受控 / 非受控双模式：v-model 优先， 同时允许不传直接用（内部维护初始值）。
  • 透传兜底：未声明的属性/事件通过 $attrs 落到内部根元素，消费方能用 el-input 的原生能力 而不用你逐个转发。
  • 插槽留逃生口：默认 + 具名 + 作用域插槽， 「数据我给你，渲染你来定」。
  • 命令式能力用 defineExpose：focus() / validate() / open()，配合 ref 调用。
  • 事件命名带语义：change / submit / error， 载荷用对象 { value, raw }，方便后续扩展字段不破坏类型。
一个合格的二次封装组件（基于 Element Plus）

进阶 · 开放扩展机制：Block Registry 当组件库要渲染开放内容（如 AI 流式返回的文本/表格/图表/表单等 20+ 种区块）时，把「区块类型 → 组件」做成注册表模式： 库内置默认注册表，消费方可以用 useBlockRegistry 注册自定义区块替换或新增—— 组件库不追求穷举所有场景，而是提供可插拔的扩展点。 这是内部组件库长期演化的关键设计。
Registry 模式的最小骨架
// registry.ts：类型安全的注册表
const registry = new Map<string, Component>()

export function registerBlock(type: string, comp: Component) {
  registry.set(type, comp) // 消费方注册自定义区块
}

export function resolveBlock(type: string): Component {
  return registry.get(type) ?? FallbackBlock // 未注册 → 兜底组件
}

三、样式与主题：前缀隔离 + CSS 变量

组件库样式最大的诉求：不污染宿主、不被宿主污染、可换肤。 三板斧：命名空间前缀（BEM）、CSS 变量做主题令牌、SCSS 变量做编译期定制。

主题体系：createTheme + CSS 变量
/* theme/vars.css —— 全部视觉参数收敛为变量 */
.hsa-ai {
  --hsa-color-primary: #409eff;
  --hsa-color-bg: #ffffff;
  --hsa-radius-md: 8px;
  --hsa-font-size-base: 14px;
}
.hsa-ai[data-theme='dark'] {
  --hsa-color-bg: #1a1a1a;
  --hsa-color-primary: #66b1ff;
}
// theme/create-theme.ts：运行时工厂
export function createTheme(options: ThemeOptions) {
  return {
    install(app: App) {
      const cssVar = (k: string, v: string) =>
        document.documentElement.style.setProperty(k, v)
      if (options.primaryColor) cssVar('--hsa-color-primary', options.primaryColor)
      // ...其余令牌
    },
  }
}
BEM + 前缀命名空间 所有类名 .hsa-btn__icon--disabled， 重置样式只作用于 .hsa-ai 作用域内， 与宿主（Element 的 .el-）物理隔离。
覆盖 Element 用官方通道 二次封装时优先用 Element 的 --el- CSS 变量覆盖， 其次 SCSS 变量编译期改主题，避免写死类名深度覆盖 （升级即碎）。
样式单独出口 import '@hsa-ai/ui/style.css'——样式与 JS 分离出口， 消费方决定加载时机，也方便做按需样式。
WARNING · sideEffects 必须声明 样式文件是有副作用的（挂到 DOM），若不声明，构建方 tree-shaking 可能把 import 进来的 css 当死代码删掉： 
"sideEffects": ["**/*.css", "**/*.scss"]

3.4 真实实现复盘：AiThemeProvider 的主题切换链路

上面是通用模式，这里复盘 @hsa-ai/ui 里 真实跑在线上的实现。先补两条 CSS 底层原理：

  • CSS 变量会继承：--xxx 声明在某个元素上， 它的所有后代都能通过 var() 读到—— 所以只要把变量写在一个「根容器」上，整棵子树生效。
  • 同名变量靠层叠覆盖： [data-theme='dark'] 规则与浅色规则匹配同一元素时， 特异性高的赢（[data-theme='dark'] 比无属性选择器多一级， 覆盖浅色值）。

于是「主题切换」可以收敛成一件极小的事： 改根容器上的一个属性，浏览器自动重算整棵子树的所有 var()——组件样式零改动。

Provider 源码精简版（providers/AiThemeProvider.vue）
<script setup lang="ts">
import { computed, onMounted, onBeforeUnmount, provide, ref, watch } from 'vue'
import { createTheme } from '../theme/create-theme'
import { THEME_KEY } from './injection-keys'

const props = withDefaults(defineProps<ThemeOptions>(), {
  mode: 'light',          // 'light' | 'dark' | 'auto'
  tokens: () => ({}),
})

const rootEl = ref<HTMLDivElement | null>(null)
const systemDark = ref(false)

// mode=auto 时跟随系统；否则用显式声明的模式
const activeMode = computed<'light' | 'dark'>(() => {
  if (props.mode === 'auto') return systemDark.value ? 'dark' : 'light'
  return props.mode as 'light' | 'dark'
})

// tokens 对象 → CSS Variables 写到根元素 style 上（品牌定制的入口）
function applyVariables(el: HTMLElement) {
  const vars = createTheme(props.tokens ?? {})
  for (const [key, value] of Object.entries(vars)) {
    el.style.setProperty(key, value)   // 行内 style，特异性最高，压过暗色规则
  }
}

function applyTheme(el: HTMLElement) {
  el.setAttribute('data-theme', activeMode.value)  // ★ 切换就这一行
  applyVariables(el)
}

let mq: MediaQueryList | null = null
function onSystemThemeChange(e: MediaQueryListEvent) {
  systemDark.value = e.matches
}

onMounted(() => {
  if (rootEl.value) applyTheme(rootEl.value)
  mq = window.matchMedia('(prefers-color-scheme: dark)')
  systemDark.value = mq.matches
  mq.addEventListener('change', onSystemThemeChange)
})
onBeforeUnmount(() => mq?.removeEventListener('change', onSystemThemeChange))

// mode / tokens 变化 → 重新写属性，CSS 自动重算
watch([activeMode, () => props.tokens], () => {
  if (rootEl.value) applyTheme(rootEl.value)
}, { deep: true })

// 双通道的 JS 侧：ECharts 等 canvas 组件读不到 CSS 变量，用 provide 注入
provide(THEME_KEY, {
  get mode() { return activeMode.value },
  get options() { return props },
})
</script>

<template>
  <!-- 作用域根：变量声明在这，后代全部继承 -->
  <div ref="rootEl" class="ai-theme">
    <slot />
  </div>
</template>
暗色规则（theme/dark.scss）—— 裸属性选择器即可
/* 在根元素添加 data-theme="dark" 后生效（Provider 自动加） */
[data-theme='dark'] {
  --hsa-color-bg: #1a1a1a;
  --hsa-color-primary: #66b1ff;
  /* ...其余暗色令牌 */
}
职责划分 Provider 只做三件事：算出 activeMode、往根元素写属性和变量、 provide 给 JS 侧。组件与样式完全不感知切换逻辑。
切换的响应式闭环 消费方 :mode="themeMode" → prop 变 → watch 触发 → setAttribute → CSS 层叠重算。全程只动根元素一个属性。
auto 模式 matchMedia('(prefers-color-scheme: dark)') 监听系统主题，事件回调里只改一个 ref， 剩下的交给同一条 watch 链路。
为什么放作用域根而非 :root 变量挂在 :root 会污染宿主全局； 挂在 Provider 的根 div 上，多套系统同页共存互不干扰， 卸载组件即卸载主题。
TIP · 记忆模型 「变量定义在作用域根，消费在任意后代；切换 = 根元素换属性， 层叠覆盖自动生效；canvas 组件读不到变量，再开一条 provide 通道」。

五、依赖治理：dependencies 为空原则

组件库依赖出问题的根源几乎都是「依赖归类错误」。黄金规则：

  • dependencies 必须为空（或极少）：库自身的运行时依赖装进 dependencies 会导致消费方多装一份、版本漂移、体积膨胀。
  • peerDependencies：宿主必然提供的能力 （vue、element-plus、echarts…），只声明版本区间， 不实际安装。
  • devDependencies：peer 的具体版本装在这里， 供本地开发与测试使用。
  • 外部能力适配器注入：HTTP 客户端等抽象成接口 （Fetcher），由消费方传实现，库只认接口不认库。

WARNING · 双实例三大高发场景
  • 库的 dependencies 装了自己的 vue → 组件渲染到另一个 Vue 上，事件全失效。
  • 构建时忘了 external vue → 同上，且产物巨大。
  • peer 区间写太死（如只写 ^2.14.0）→ 宿主小版本升级就 peer 冲突。

六、质量门禁：让 AI 写的代码也不敢乱来

内部库（尤其多人 / AI 协作）必须把「团队品味」变成机器可执行的规则。 一套实践中验证过的门禁组合：

  • 构建前置测试：build = test → vue-tsc → vite build， 测试不过就根本产不出包。
  • pre-commit 钩子：simple-git-hooks 提交前强制跑核心包测试， 紧急逃生用环境变量（保留但不鼓励）。
  • 静态规则：ESLint 禁 any、公共 API 强制显式返回类型、 单文件 ≤ 300 行、index.ts 只做 re-export 不含逻辑。
  • JSDoc 纪律：所有公共导出必须有 JSDoc（语言统一中文）， 文档站和 IDE 悬浮提示都吃这个。

INFO · 测试什么？ 组件库测试性价比排序：纯逻辑单测（解析器 / 状态机，跑得飞快， 占大头）→ composable 测试（@vue/test-utils + effectScope）→ 组件行为测试（渲染关键交互，不求覆盖率数字）→ 视觉回归（内部库可暂缓）。分层架构的另一收益：核心层是纯函数， 测试几乎零成本。

七、版本与发布：内部库也需要 semver 纪律

  • semver 三段式：patch 修 bug / minor 加功能（含新 props）/ major 破坏 API。内部库最容易犯的错：随手 minor 里改了默认值—— 对消费方就是 major 事故。
  • changelog 自动化：单包用 changelogen；monorepo 多包联动用 changesets（能显式声明「这次改动影响哪些包、升什么级别」）。
  • 发布物验证：发布前 npm pack 检查 files 是否干净（绝不能把 src / 测试打进包）； 用 npm publish --dry-run 或 Verdaccio 本地演练。
  • 预发布通道：改动大时发 2.18.0-beta.1， 让一两个先行业务接入验证后再转正。
  • 锁定策略：内部库建议消费方用 固定版本（去掉 ^），升级节奏由组件库团队统一推。
TIP · 联调期免发布 开发阶段用 pnpm link / workspace 直接引用源码包， 或发 0.0.0-dev.x 快照版本；不要为了联调把半成品 patch 版本发上 registry——版本号是不可逆的信用。

八、面试高频问答

Q1：让你从 0 搭一个 Vue 组件库，你的技术选型和步骤？

先问两个问题定架构：是否基于现有 UI 库二次封装？是否有多包复用需求？ —— Element 系内部库：参考 element-plus 仓库结构（packages + play + docs）， Vite library mode 构建，VitePress 文档站，vitest 测试。 自研领域库：pnpm monorepo 分层（核心 / 适配 / UI），tsup + Vite 混合构建， ESM+CJS+多子入口+style.css 出口，dependencies 为空 + peer 声明宿主能力， 测试前置为构建门禁，changelogen/changesets 管理 semver。

Q2：package.json 的 exports 字段解决了什么问题？

它是包的路由表：① 收敛入口（内部文件不再可随意 import，只有声明的子路径可访问）； ② 条件导出（import 走 ESM / require 走 CJS / types 指向 d.ts，TS 的 moduleResolution: bundler/node16 才能正确解析）； ③ 多子入口支持按需加载（如 @hsa-ai/ui/blocks）。 注意：main/module/types 仍保留，兼容老打包器。

Q3：peerDependencies 和 dependencies 怎么选？

判断标准：这个包是否必须和宿主「同一份实例」。 vue、element-plus、状态库必须是同一实例（双实例 = 灾难）→ peer； 库自洽的工具函数库（无实例概念）→ dependencies 也安全， 但原则上能 peer / 注入就不装。配套：peer 的具体版本进 devDependencies 供开发测试， CI 校验 dependencies 白名单。

Q4：组件库怎么做主题定制和暗黑模式？

视觉参数全部收敛为 CSS 变量令牌（颜色/圆角/字号/间距）， 组件样式只引用变量；暗黑模式 = 作用域上加 data-theme='dark' 切换变量值；品牌定制提供 createTheme 工厂或 SCSS 变量编译期覆盖。二次封装 Element 时优先用官方 --el- 变量通道覆盖，避免深选择器 hack。

Q5：内部组件库如何处理「宿主升级 / 破坏性变更」？

四道防线：① peer 版本区间 + CI 对宿主高版本冒烟构建，提前暴露； ② 破坏性变更走 major + 迁移文档（codemod 能自动化最好）； ③ 预发布 beta 通道让先行业务验证；④ 消费方锁死版本， 升级由组件库团队统一推进——版本节奏集中管理是内部库和开源库 最大的策略差异。

Q6：如何让组件库支持按需引入？

三层手段：① 多子入口 exports（scenes/blocks/theme 拆包）； ② ESM + sideEffects 白名单让宿主编译器 tree-shaking（未用组件被摇掉）； ③ unplugin-vue-components 之类的 resolver 做到「模板里写了才 import」。 样式跟随组件而非全局入口，配合 css 代码分割。

九、最佳实践 & 记忆口诀

分层先行 核心逻辑（协议/算法/状态机）抽成零 UI 依赖的纯 TS 包， UI 层只剩渲染——换框架、做测试、多端复用全靠它。
API 即契约 发布前多花一小时设计 props/slots/expose 命名， 好过发布后破坏性变更十次；扩展点（插槽/registry）宁多勿少。
产物自证 每次 release 前 npm pack 检查文件清单； exports 三元组（types/import/require）齐全； external 列表覆盖所有宿主依赖。
治理自动化 测试门禁前置到 build、pre-commit 跑核心包、ESLint 禁 any、 300 行拆分、index.ts 只 re-export——用机器守住团队品味。
记忆口诀 「核心不碰 UI，宿主走 peer；出口 exports 管，样式带前缀； 门禁前置测，发版 semver 惜；扩展点留好，内部库才活得久」。
